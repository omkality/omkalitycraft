# Журналы и диагностика

В лаунчере нет меню диагностики, экспорта или администрирования. После игрового сбоя
он автоматически сохраняет короткий технический отчёт и пытается передать его
доверенному API. Ошибки доставки не открывают окна и не мешают играть. Об этом есть
короткая строка при регистрации. Файлы клиента остаются в переносимой папке.
Серверные журналы и принятые отчёты читает только [утилита владельца](ADMIN.md).
Отдельный Elasticsearch/Loki-сервис пока не нужен; сторонний мод может писать свои файлы отдельно.

## Что сохраняется

| Данные | Назначение | Ограничение |
| --- | --- | --- |
| `userdata/logs/launcher.jsonl` | UTC-время, операция, версия лаунчера/сборки, выбранная RAM, свободная RAM/диск, run ID, exit code; тип и кадры Python-ошибки | 3 файла по 1 МиБ, включая текущий |
| `userdata/logs/<профиль>-game.log` | Объединённые stdout/stderr Java, разделитель запусков, последние сообщения и стек | 3 файла по 8 МиБ, включая текущий |
| `instances/<профиль>/logs/latest.log` | INFO/WARN/ERROR Minecraft, Forge и модов, полные многострочные исключения | DJ2: ротация на 8 МиБ, 3 сжатых архива + текущий файл |
| `instances/<профиль>/crash-reports/crash-*.txt` | Причина сбоя, моды, сущность/блок/чанк и системные сведения, если игра смогла создать отчёт | После остановки: до 10 отчётов / 32 МиБ; самый новый сохраняется даже при превышении |
| `instances/<профиль>/hs_err_pid*.log` | Фатальная ошибка JVM/нативного кода; путь задан явным `-XX:ErrorFile` | После остановки: до 10 / 32 МиБ, самый новый сохраняется даже при превышении |
| `userdata/client-incidents/<id>.json` | Очередь коротких клиентских отчётов; подтверждённые удаляются | До 20 / 2 МиБ / 14 дней, очистка при работе лаунчера |
| Серверный private inbox | Принятые клиентские отчёты, только для владельца | До 14 дней / 20 на игрока / 1000 всего, что наступит раньше |
| `.omk-admin/userdata/diagnostics/diag-*.zip` | Серверный ZIP по команде владельца | До 5 архивов и 64 МиБ суммарно |

У Python-файлов предел считается в байтах. Старые безлимитные файлы с такими же именами
нормализуются до полного хвоста строк при следующей записи. Log4j проверяет размер
на границах событий: один огромный Java event может превысить порог 8 МиБ. Сжатые
архивы обычно существенно меньше порога. Старые штатные архивы `YYYY-MM-DD-N.log.gz`,
`latest-N.log.gz`, `debug-N.log.gz` очищаются **только при остановленной игре**:
до 12 файлов / 32 МиБ. Активные `latest.log`/`debug.log` и файлы других модов эта очистка
не обрезает. Старый DEBUG по 200 МиБ больше не включён новым профилем.

Перед новым запуском текущий stdout-журнал ротируется, чтобы в отчёт не попал стек
предыдущей сессии. Новые crash-файлы определяются относительно снимка до запуска,
а не только по времени — старый файл с будущей датой после коррекции часов пропускается.
Чтение stdout идёт блоками 8 КиБ, без безразмерной очереди и истории в ОЗУ.
Строка длиннее 32768 символов пропускается целиком с короткой отметкой; это не
обычное ограничение длины всего stack trace — его отдельные строки сохраняются.
При отказе диска канал продолжает вычитываться: не даём Java заблокироваться на
заполненном pipe. Лаунчер показывает фактическую ошибку записи. Последний вывод
дочитывается до закрытия скрытого окна лаунчера.

## Автоматические отчёты клиента

При ненулевом exit code или новом crash-report лаунчер собирает версию сборки и Minecraft,
launcher/platform, выбранную RAM, код завершения, UUID и короткий стек. Новый Minecraft
crash-report обрезается до секции System Details; из fatal JVM-файла берётся только
краткая причина/VM/проблемный frame, **не** окружение или командная строка. При отсутствии
отчёта сохраняются выбранные строки исключений, без `[CHAT]`/GuiNewChat и обычного stdout.
Текст ограничен 32 КиБ; запрос — 128 КиБ, сохранённый объект — 96 КиБ максимум.
Токены и локальные пути очищаются до записи в очередь, сервер дополнительно очищает
bearer token из текста. Принятый отчёт удаляется из очереди только после подтверждения ID.

`POST /reports/client` включён только при явной настройке сервера. Доступ — по игровому
токену; настоящий Drasl `/minecraft/profile` подтверждает UUID и имя. Чужой UUID
отклоняется. Ограничения: 20 запросов/минуту/IP на worker и 3 новых отчёта/час/аккаунт; одинаковый
ID с тем же содержимым идемпотентен. При 401/429/сбое сети отчёт остаётся локально;
автоповторы не создают бесконечный цикл. При следующем входе отправляется максимум один
ожидающий отчёт своего UUID. Обновлять аккаунт или токены ради диагностики не требуется.

**Срок inbox — 14 суток от получения сервером**, дополнительно действуют лимиты количества.
Expired записи не выдаются. Физическая очистка — при записи, старте сервиса и каждый час;
при выключенном API — после следующего старта. Есть `omk admin ... reports prune`.
SQLite-файл ограничен 128 МиБ, использует повторно освобождённые страницы, WAL/checkpoint
и secure_delete; временный WAL учитывается отдельно. Это отдельное закрытое хранилище,
не в CDN и не в папке Forge. Игрокам недоступны list/get/export: таких HTTP-методов нет.

Доставка проверена на loopback, публичный сервис ещё не развёрнут. При падении самого
лаунчера/ОС до сбора отчёта, удалении его папки, отсутствии сети или истечении токена
автоматическая доставка не гарантируется. Полный raw crash-report остаётся локально
по описанной выше ротации. Отчёты не доказывают честность клиента и не используются
как основание автоматического бана.

## Серверный ZIP — только владельцу

```powershell
uv run omk admin --config .omk-admin/operator.toml diagnostics dj2
```

ID должен быть в allowlist конфигурации владельца. Команда читает выбранный сервер,
не останавливает его, не меняет мир/БД/RCON и сохраняет ZIP в закрытую `.omk-admin`.
Живой журнал может измениться во время чтения: архив не является world-backup.
Игроки этой команды и серверных файлов не получают. При необходимости локальная
операторская библиотека может разбирать клиентские файлы с явным доступом владельца;
лаунчер не предоставляет удалённого чтения произвольных файлов компьютера игрока.

В ZIP входят до трёх последних файлов каждой категории: наши журналы, текущие
`latest.log`/`debug.log`, crash-report и `hs_err_pid*.log` из корня выбранной игры/сервера.
Общий бюджет текста 16 МиБ плюс небольшой JSON/ZIP overhead, один фрагмент до 2 МиБ.
Приоритет — crash-report/JVM, затем лаунчер и игровые логи. Большой crash-report/JVM
сохраняется началом и концом, обычный журнал — хвостом. Обрезка указана в `diagnostic.json`.
Сжатые сторонние журналы не распаковываются. Обход ограничен 1000 записями на каталог.

**Не собираются:** session/account-файлы, пароли, `.env`, конфиги сервера/RCON, ключи,
миры, NBT игроков, приваты, скриншоты, моды, дампы heap/core и произвольные соседние файлы.
Ссылки и Windows junction, в том числе в родительских каталогах, пропускаются.
Запись/ротация своих журналов через ссылки также запрещена.

Текущие access/client tokens удаляются из stdout до записи. При экспорте снова
удаляются известные токены, типичные JSON/CLI/URL credential-поля, Authorization,
Bearer/Basic, JWT и Session ID; пути переносимой папки и домашнего каталога заменяются.
В Python-ошибках сохраняются тип, errno и расположение кадров, **без** локальных
переменных, строк исходника, HTTP-body и произвольного текста исключения.

Это не обещание автоматического распознавания любого секрета в любом стороннем формате.
Собственные Java crash-report/latest.log могут содержать чувствительный текст.
Операторский ZIP может содержать ники, чат, адрес сервера и координаты; короткий
автоматический отчёт может содержать текст исключения/координаты игрового сбоя.
Перед дальнейшей передачей просмотреть содержимое. Raw-логи, inbox и ZIP не публикуются в Git.

## Какие сбои различать

| Симптом | Что нужно для разбора | Ограничение |
| --- | --- | --- |
| Не стартует Java / нет файла / запрет записи | Событие запуска, errno, версия, свободный диск, launcher log | Не делать вывод «нужна новая Java» только по exit code |
| Java heap OOM / GC overhead | Выбранный Xmx, свободная RAM до запуска, Java-стек и последние логи | Автоматический heap dump выключен: он может быть гигабайтным и содержать токены |
| Падение LWJGL/OpenGL/драйвера/JVM | `hs_err_pid`, crash-report, последний stdout | При SIGKILL/убийстве ОС JVM может ничего не записать |
| Падает только в месте/при входе игрока | Crash-report с dimension/entity/block/chunk, время и описание последнего действия | Мир не менять автоматически; сначала копия/backup и воспроизведение отдельно |
| Падает только у одного игрока | Та же версия сборки, ремонт SHA256, его crash-report и серверный фрагмент того же времени | «Мод указан первым в стеке» не всегда означает виновный мод |
| Сервер висит, TPS падает, лог спамится | Время, измерение, TPS, краткая запись профилировщика/дамп потоков | Обычный лог не заменяет профиль; DEBUG/TRACE не держать постоянно |
| Повреждён регион / ошибка NBT / неудачный save | Стек чтения/записи и состояние диска + резервная копия | Не удалять регион, playerdata или ticking entity без проверенного плана восстановления |
| Клиент потерял соединение | Серверная причина отказа + клиентский хвост того же времени | Ошибка клиента не доказывает падение сервера |

К разбору полезно приложить 2–3 предложения: что делал игрок, примерное время с часовым поясом,
повторяется ли сбой, известное измерение/координаты. Запись игры или мира для обычного
первичного разбора не нужна. Логи не являются полноценным журналом откатов построек.

## Java logging и сервер

Адаптер `launcher/log_policy.py` задаёт bounded Log4j-конфиг для Minecraft 1.12.2,
с `%msg{nolookups}`, именем logger и stack trace. Не меняет конфиги неизвестных версий.
Новый Forge-стенд использует тот же адаптер и ограниченный Python pipe-collector.
Лабораторный `max-tick-time=0` нельзя считать готовой эксплуатационной политикой:
перед публичным запуском отдельно настроить watchdog, профиль TPS и дампы зависаний.

В исходном клиентском classpath обнаружен Log4j **2.8.1**, Forge-server manifest
ссылается на **2.15.0**. Проверенная замена в отдельном стенде — Java 8 Log4j **2.25.5**,
ветка с maintenance-исправлениями. Версии/источники/размеры/SHA256 закреплены в
[runtime-профиле](../profiles/runtime/log4j-java8.json). Это обновление библиотеки
логирования, не обновление DJ2, квестов или игровых модов.

Подготовка **новой staging-копии**, не работающего сервера/клиента:

```powershell
uv run python scripts/stage_logging_runtime.py --files .local/new-release/files --launch-profile .local/source-launch.json --output-profile .local/new-launch.json
```

Скрипт скачивает только закреплённые API/Core, проверяет хеши и создаёт новый профиль
classpath. Старые версии исключаются из classpath; лишние старые JAR в staging убрать
при подготовке из allowlist до подписи. Затем обычный `omk release pack` подписывает
весь payload. Лаунчер во время запуска **не** скачивает библиотек в обход подписи.
Источник сервера и старый подписанный релиз не редактируются.

Drasl lab Docker использует штатный `local` driver: 3 файла по 10 МБ со сжатием.
Для будущего VPS такую же политику нужно явно применить к CDN/auth/game-контейнерам;
она не меняет уже запущенные контейнеры. CDN access-log должен содержать status,
latency и request ID, без Authorization, query/body и токенов; конфигурация публичного
reverse proxy/сервисов пока не развёрнута. Мониторинг свободного диска, алерты падений,
сбор thread dump при зависании и retention бэкапов — отдельный эксплуатационный этап.
Не удаляем миры/бэкапы ради освобождения места под логи.

Основание: [Log4j rolling appenders](https://logging.apache.org/log4j/2.x/manual/appenders/rolling-file.html),
[Apache security advisories](https://logging.apache.org/security.html),
[Log4j release notes](https://logging.apache.org/log4j/2.x/release-notes.html),
[Docker local logging](https://docs.docker.com/engine/logging/drivers/local/),
[OWASP logging guidance](https://cheatsheetseries.owasp.org/cheatsheets/Logging_Cheat_Sheet).

## Предыдущая проверка ротации (dev3)

[Отчёт 30 октября](validation/logging-2026-10-30.json): 170 локальных тестов прошли,
один symlink-тест пропущен на Windows без привилегий. Настоящий Java 8 записал
40000 сообщений и исключение: ротация, стек, кириллица, пробелы в пути, буквальный
`${java:version}` и отсутствие ошибок Log4j проверены. Повторяемый тест:

```powershell
uv run python scripts/probe_logging.py --java PATH_TO_JAVA8 --javac PATH_TO_JAVAC
```

Forge прошёл 11 протокольных сценариев и настоящий вход полноценного клиента DJ2
с Log4j 2.25.5 / UTF-8. Экспорт клиента и остановленного сервера прошёл; известные
тестовые токены не найдены в собранном выводе/ZIP. Подписанный локальный релиз
`2.21.3-omk.4` содержит 6282 файла и не использует старый Log4j в classpath.
Это не новый публичный релиз; исходный сервер не обновлялся.

## Изменение интерфейса в 0.3.0.dev4

По уточнению владельца меню экспорта полностью удалено из лаунчера. Предыдущее
описание/снимок UI относится к dev3. Актуальный административный интерфейс и выдача
приглашений — [ADMIN.md](ADMIN.md). Raw-журналы продолжают ротироваться **по объёму**,
а не обещают фиксированные 14 дней; 14 дней относятся к коротким отчётам/очереди.

Текущие проверки dev4: [211 unit/UI и 13 Drasl/HTTP/CLI сценариев](validation/operator-tools-2026-10-30.json).
IP берётся из соединения: произвольным X-Forwarded-For не доверяем. Настройку trusted proxy
и общего edge rate limit выполняем при развёртывании; квота аккаунта общая через SQLite.
