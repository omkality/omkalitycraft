# Проверка безопасной ротации резервных копий

Добавлена **лабораторная транзакция хранения архивов**, а не готовый планировщик
резервирования работающего Minecraft. FTB Backups и исходный сервер не изменены.
Новый механизм пока вызывается только тестами. Нет команды, которая принимает путь
к рабочим мирам/прежним FTB-копиям и начинает их удалять.

## Что проверяет новый механизм

1. Принимает закрытый ZIP и независимый полный перечень исходных файлов с размерами
   и SHA256. Перечень из самого ZIP не доказывает, что архив содержит весь мир.
2. Проверяет состав, пути, коллизии имён, типы файлов, размеры, CRC и SHA256 каждого
   файла. Отказывает при пропущенном/лишнем файле, дубликате, ссылке или повреждении.
3. Под блокировкой проверяет предыдущие копии, лимит числа/байтов, staging и свободный
   резерв. Существующие архивы не удаляются ради освобождения места под попытку.
4. Копирует в отдельный `pending-*`, выполняет `fsync`, перечитывает ZIP и хеши,
   записывает manifest. Затем переименовывает каталог в `snapshot-*` на той же ФС.
   На Linux синхронизируются также каталоги до перехода к удалению старого.
5. Только после публикации новой проверенной копии выполняет ротацию старейших.
   Сохраняет новую и непосредственно предшествующую проверенную копию. Если бюджет
   не вмещает обе — отказывает. Самая первая копия временно одна: до открытия сервера
   нужны минимум две пригодные копии и проверенное восстановление.

Лимит хранения включает ZIP и manifest; staging должен вместить новую пару **сверх**
предыдущих копий. Перед записью проверяется физическое свободное место с резервом
и дополнительными 64 КиБ на служебные расходы. Это не жёсткая квота всей ФС:
параллельная запись мира/логов всё равно может вызвать ENOSPC.

Промежуточный `retired-*` обозначает старую копию, уже исключённую из истории после
публикации новой. Удаляются только два известных обычных файла и пустой каталог;
рекурсивной очистки, принятия чужих каталогов и автоматического удаления неизвестных
файлов нет. Хранилище создаётся только в **новом** каталоге.

После прерывания `pending-*`/`retired-*` либо превышение лимита уже опубликованными
копиями блокируют дальнейшую запись. Это намеренно: повторные попытки не должны
накапливать staging. Нужен осмотр владельца и проверка последних двух копий; готовой
команды автоматического исправления/удаления таких остатков пока нет.
Блокировка ОС освобождается при смерти процесса и сама не остаётся «зависшей».

## Воспроизводимый Linux-стенд

```text
docker pull python:3.14.2-slim@sha256:1a3c6dbfd2173971abba880c3cc2ec4643690901f6ad6742d0827bae6cefc925
uv run python -m omk lab backup-safety
```

Это официальный Python 3.14.2 slim по тому же digest, что в `Dockerfile.api`.
В контейнер монтируются read-only **четыре файла исходников** из временной папки,
не весь проект. Миры, `.env`, пароли, исходные бэкапы и Docker socket не подключаются.
Нет сети, портов и дополнительных capabilities; rootfs read-only. Данные только в
одноразовых tmpfs 64/16/128 МиБ, память процесса ограничена 512 МиБ, CPU — одним ядром.
Удаляется только контейнер с собственным случайным именем и совпавшей ownership-меткой.
При недоступном Docker очистка не объявляется успешной без доказательства.

Проверки:

- Четыре публикации, ротация до последних двух, возврат трёх синтетических файлов
  в новый пустой каталог и побайтная проверка.
- Настоящий ENOSPC на tmpfs **16 МиБ**: другой лабораторный writer занимает место
  после успешного preflight. Ошибку выдаёт реальная запись ZIP; она не подменена mock.
  Обе прежние копии остаются побайтно неизменными, повтор не создаёт новый staging.
- Настоящий SIGKILL дочернего процесса в четырёх точках: частично записанный ZIP,
  опубликованная новая копия до ротации, начало ротации, удалённые данные старой копии
  до удаления её manifest. Проверены читаемость не менее двух копий, освобождение
  блокировки ОС и отказ дальнейшей записи до осмотра владельца.

Unit-тесты дополнительно проверяют нехватку бюджета для двух копий, неверные пути,
CRC/хеши/состав, повреждённую прошлую копию, ошибку удаления, изменение входного ZIP,
ошибочную конфигурацию и границы удаления Docker-контейнера. Этот Docker-сценарий
добавлен в Linux CI; unit-тесты исполняются также на Windows/macOS.

Отдельно через этот же механизм прошёл архив ранее чисто остановленного полного
Linux DJ2-стенда. Независимый перечень взят из сохранённого TAR, а не из полученного
ZIP: 270 файлов / 7051853 байта. После трёх публикаций остались копии 2/3, все файлы
развёрнуты в пустой каталог и сверены по SHA256. Исходный TAR не менялся. Minecraft
в этом опыте не запускался — это проверка архивного round trip на настоящих данных
лабораторного мира, не новая проверка игрового восстановления.
[Обезличенные результаты](validation/backup-safety-2026-11-01.json).

## Ограничения и следующий этап

Это проверка сохранности архивов при файловых отказах и смерти процесса. Она
**не доказывает** восстановление Minecraft после обрыва записи мира, исправность
всех машин/сущностей или сохранение данных при потере питания/самого диска. tmpfs
подходит для безопасного ENOSPC/SIGKILL, но не моделирует power-loss и durable-диск VPS.
Windows-проверки не объявляются доказательством Linux durability или наоборот.

Текущие защитные пределы — 20000 файлов, 512 МиБ распакованных данных, 8 МиБ manifest.
Они относятся к маленькому стенду, а не к будущим большим мирам. API хранилища не
защищает от администратора/процесса с правом изменения его каталога; нужны отдельные
права доступа и копия вне диска VPS.

До эксплуатации требуется адаптер остановки/сохранения Forge с подтверждённым
барьером записи и независимым перечнем всех данных. Полный возврат должен учитывать
измерения, FTB/инвентари, актуальные bans/OP/whitelist/ранги и внешнюю авторизацию.
Затем — планировщик с env-политикой из `omk storage plan`, bounded журналом отказов,
проверкой восстановления и внешним хранением. Один механизм должен владеть ротацией:
не оставлять одновременно независимую очистку FTB и новую очистку тех же архивов.
До этого рабочий FTB config не меняем и retention решённым не объявляем.
