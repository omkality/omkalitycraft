# Владение тестовыми окнами Qt

Расследование [#71](https://github.com/omkality/omkalitycraft/issues/71), 4 ноября 2026.
Изменения относятся к стенду GUI, код приложения и версия Qt не менялись.
[Счётчики, версии и hashes](validation/qt-widget-lifetime-2026-11-04.json).

## Что воспроизведено

В старом тесте предупреждения функция создавала локальное окно, регистрировала его
в `qtbot` и возвращалась. В pytest-qt 4.5.0 `addWidget` хранит слабую ссылку;
после возврата функции plugin ещё вызывает `processEvents`, прежде чем закрыть окна.
Сборщик мусора мог уничтожить Python-owned окно во время обработки оставшейся
отрисовки. Воспроизведены Windows abort и Linux SIGSEGV со стеком QWidget repaint.

Эта последовательность проверена по закреплённым первичным исходникам:
[регистрация/закрытие widgets](https://github.com/pytest-dev/pytest-qt/blob/4.5.0/src/pytestqt/qtbot.py),
[порядок CALL/teardown](https://github.com/pytest-dev/pytest-qt/blob/4.5.0/src/pytestqt/plugin.py).
В обычном `run_launcher` главное окно остаётся в локальной переменной на всё время
`app.exec()`. Воспроизведённый тестовый дефект сам по себе не доказывает такой же
сбой обычного пользовательского запуска или неисправность компьютера.

Предыдущее разделение HTTP и отображения предупреждения уменьшило воспроизводимость,
но не доказало причину. Отдельный контроль со свежим исключением и прежним HTTP
по-прежнему упал. Гипотеза «достаточно убрать traceback» не принята как полное исправление.

## Адресное исправление

Проектная fixture `qtbot` делегирует штатную регистрацию pytest-qt и дополнительно
держит сильные ссылки на зарегистрированные окна до teardown. Закрытие/`deleteLater`
по-прежнему выполняет pytest-qt. После этого список очищается; обе формы API,
`addWidget` и `add_widget`, поддерживаются. В двух новых тестах окно переживает
выход создающей функции и принудительную сборку мусора до штатного закрытия.
На прежней fixture оба теста провалились, с исправлением оба прошли.

Заодно исправлен вызов `waitExposed`: это context manager, поэтому показ окна
находится внутри `with`. Простое обращение к методу не ожидало показа окна.
[Контракт API](https://pytest-qt.readthedocs.io/en/4.5.0/reference.html#pytestqt.qtbot.QtBot.waitExposed).

## Контроли до/после

Python 3.14.2, PySide6/Shiboken6 6.11.0, pytest-qt 4.5.0. Старый source —
`0c8ed5d`, разделение fixture — `5a064c1`; входы экспортированы из Git в новые
локальные папки. Все аккаунты — test doubles, token store — временный.

| Контроль | Windows | Linux Docker |
| --- | --- | --- |
| Исходный тест, обычный GC | 60 прошли | 60 прошли |
| Исходный тест, усиленный GC | abort 3 | В этом прогоне 60 прошли |
| Только свежий error, прежний HTTP/отрисовка | abort 3 | SIGSEGV 139, OOM false |
| Только удержание окон, весь прежний тест/HTTP сохранён | 60 прошли | 60 прошли, OOM false |
| Текущая fixture, весь GUI-набор трижды с усиленным GC | 132 прошли | 132 прошли, OOM false |

Различие нормального и усиленного режимов показывает зависимость от времени GC;
ошибка не объявляется воспроизводимой при каждом запуске. Контроль только обновления
PySide6 до 6.11.3 в отдельном Linux-образе тоже дал SIGSEGV на дефектной fixture.
Эта версия не устанавливалась в окружение проекта и не принята как решение.

Первым двум минимальным Linux-образам не хватало системных GL/font библиотек: Qt
не импортировался, эти попытки не считаются тестами приложения. После исправления
образа заранее проверен настоящий старт QApplication. Контейнеры ограничены двумя
CPU/2 ГиБ и сетью loopback без внешнего доступа; mount исходников read-only.
Краши не создают core dumps. Собственные контейнеры удалены, другие сервисы не тронуты.

## Постоянная регрессия

В Desktop CI Windows/Linux/macOS после обычного полного набора запускаются три
прохода GUI с `OMK_TEST_QT_GC_STRESS=1`. Fixture задаёт thresholds `(20, 2, 2)`
и восстанавливает прежние значения после сессии. Этот флаг читается только тестами:
GC приложения не отключается и не перенастраивается.

Для локального повтора в отдельном PowerShell-терминале:

```powershell
$env:QT_QPA_PLATFORM = "offscreen"
$env:OMK_TEST_QT_GC_STRESS = "1"
uv run pytest --keep-duplicates tests/ui tests/ui tests/ui -v
```

Это регрессия владения окнами, не доказательство отсутствия всех ошибок Qt и не
новая приёмка Minecraft. Игровые вход/выход, renderer Linux/macOS и открытые задачи
сборки сохраняют собственные критерии.
