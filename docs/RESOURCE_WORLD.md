# Ресурсный мир DJ2

Это отдельный локально проверенный серверный этап #32. Рабочие сервер/сборка и player release
пока не переключаются. Безопасный административный вайп, очистка старых точек
телепортации и проверка настоящего графического клиента остаются в #32.

## Устройство

Just Enough Dimensions (JED) регистрирует отдельное обычное измерение Forge 1.12.2.
Генерация штатная, без подмены папок другого мира. Профиль DJ2 выбирает ID **-18000**;
известные статические ID сборки и положительные ID динамических RFTools-миров
не используются. Любое фактическое несовпадение провайдера отклоняет старт.
Общая интеграция JED/FTB находится в приватном Core **0.3.5**, параметры DJ2 —
в JSON/конфигурации. DJ2Fix **0.1.3** согласует позднюю регистрацию JED с фильтрами
генерации Thaumcraft, сохраняя разделение общего Core и исправлений сборки.

JED требуется **на клиенте и сервере**. Закреплён
`1.6.0-dev.20211009.214847`, SHA256
`6840d8ad69059f90c4288c317bf88284a4ccd716d06cc0aa0d37d20b2693dd8f`.
Источник — [официальный проект JED](https://modrinth.com/mod/just-enough-dimensions),
[исходный код](https://github.com/maruohon/justenoughdimensions/tree/b3929ed6b0775954dd3eba463de9b528ba4a3769).
Версия, URL и SHA также в
[`resource-world.json`](../profiles/server-defaults/dj2/resource-world.json).
Одна давняя дата публикации не доказывает совместимость; для принятия нужны
нативные проверки нашей сборки, сохранений и клиента.

У ресурсного мира собственные seed, WorldInfo и граница. Профиль запрещает
замену/удаление существующих измерений, временные автоматически удаляемые миры,
подмену конфигурации сохранённой копией и перенаправление штатных команд JED.
Для Underground Biomes в копию `IncludedDimensions` добавляется ресурсный ID;
исходная конфигурация сборки не редактируется. Иначе обычный ландшафт сам по себе
ещё не означает, что в нём есть нужная модовая генерация руд.

Для особых ресурсов подготовлены копии правил CoFH, Extreme Reactors, Natura,
Integrated Dynamics и Thaumcraft Fix. Переносятся также запреты основного мира;
ограничения сюжетных измерений автоматически не расширяются.
[Состав, правила, поздний кэш Thaumcraft и границы проверки](RESOURCE_GENERATION.md).

## Команды игрока

| Команда | Назначение |
|---|---|
| `/resource` | Вход в проверенную безопасную точку ресурсного спавна. |
| `/spawn` | Штатный возврат FTB в основной мир. |
| `/rtp` | Поиск точки в текущем разрешённом мире, включая ресурсный. |

`/resource` использует реальную команду FTB `/spawn` для проверки прав и её
таймер SPAWN: одни warmup/cooldown, история телепортаций и отмена при движении
или уроне. Дополнительного набора таймингов/ролей нет. Незавершённый `/resource`
не позволяет параллельно поставить второй такой запрос или `/spawn`.
Права проверяются повторно перед переносом. Настройки:
`command.ftbutilities.spawn`, `ftbutilities.spawn.warmup`,
`ftbutilities.spawn.cooldown`. RTP сохраняет собственный штатный таймер FTB.

Основной спавн защищает квадрат X/Z **-300…300**, ресурсный — **-100…100**.
FTB выравнивает защиту до целых чанков: соответственно -304…303 и -112…111.
Точку входа Core выбирает в защищённой зоне, без сноса блоков/деревьев. Перед
выбором учитывается генерация соседних чанков; перед каждой телепортацией
безопасность проверяется снова. Если место перекрыто, сервер ищет другую безопасную
точку внутри проверенной server-owned зоны с тем же ограничением загрузки чанков.
Препятствие, включая могилу игрока, сохраняется. Если подходящего места нет, игрок
остаётся на месте; обычная преграда не переводит адаптер в аварийное состояние.
Это ограниченный поиск точки входа, а не предгенерация мира.

Временные загрузки пустого ресурсного мира отпускаются через штатную очередь
Forge. Принудительные загрузки модов сохраняются; занятый игроками мир не
разгружается принудительно. Это не собственный механизм сохранения чанков.

## Подготовка владельцем

Просмотр ничего не записывает:

```text
omk policy dj2-resource
omk policy dj2-resource --source-config PATH_TO_STOPPED_COPY/config
```

Создание **новой** папки с проверенными конфигурациями:

```text
omk policy dj2-resource --source-config PATH_TO_STOPPED_COPY/config --output NEW_STAGING_BUNDLE
```

Это подготовка для проверки и последующего применения в отдельной остановленной
копии. Команда не скачивает JAR, не меняет работающий сервер/миры, не запускает
контейнер и не выполняет вайп. Существующая выходная папка отклоняется.
`bundle.json` с SHA каждого файла появляется только после успешной полной записи;
папку без него нельзя применять. Без `--source-config` подготовка генератора
помечена как незавершённая. `ready_for_players` остаётся `false` до общей приёмки.

| Переменная окружения | По умолчанию | Правило |
|---|---:|---|
| `OMK_DJ2_RESOURCE_DIMENSION` | -18000 | -32000…-2, вне известных ID DJ2 и текущего RTP-профиля. |
| `OMK_DJ2_RESOURCE_SEED` | 0 | Целое signed 64-bit. |
| `OMK_DJ2_RESOURCE_DIAMETER` | 16384 | Начальный диаметр 512…100000; должен вмещать spawn/RTP. |
| `OMK_DJ2_RESOURCE_SPAWN_RADIUS` | 100 | 16…512; лимит суммарной защиты — 10000 чанков. |
| `OMK_DJ2_RESOURCE_SEARCH_CHUNK_LOADS` | 64 | 16…64 прямых загрузок чанков при выборе точки входа. |

Также действуют существующие env-настройки основного спавна, RTP и квоты территорий.
Подготовка отвергает противоречия до создания папки. Диаметр задаётся только при
создании мира: изменение seed/ID/env не является процедурой миграции или вайпа.
Сохранённая граница не уменьшается при обычном рестарте от прежнего default.
Профиль сервера, где эта функция обязательна, должен требовать возможности
`ftb.resource`, `ftb.spawn`, `ftb.rtp`, `ftb.territories`.

На стенде увеличение выполняется из консоли владельца командой
`jed worldborder -18000 set 32768`, когда ресурсный мир загружен. Она адресует
именно это измерение; ванильный `worldborder`, даже внутри `execute`, для такой
операции не подходит. Команда не меняет seed и заданный максимум RTP. Для рабочего
сервера ещё нужна общая приёмка #32/#33 и согласованный storage-бюджет #38.

## Данные, аварии и восстановление

При `level-name=world` в постоянном Docker volume находятся:

- `world/DIM-18000/` — чанки, сущности и `jed_level.dat` ресурсного мира;
- `world/DIM-18000/.omk-resource.properties` — внутренний маркер принадлежности;
- `world/omk-resource-world.properties` — такая же запись вне папки измерения;
- `world/data/ftb_lib/` — штатные команды/игроки/приваты FTB;
- `world/playerdata/` — штатные данные игроков; Drasl хранится отдельно.

В лабораториях корень называется `lab-world`. Обе записи содержат только schema,
identity, ID и seed, без паролей или сессий. Рекурсивный снимок остановленного
мира включает их вместе с DIM/FTB/playerdata. Нового backup-планировщика нет.

Если есть внешняя запись, но пропала папка измерения, сервер отказывается
создавать новый мир. Неизвестная существующая папка без записи также не
присваивается автоматически. Несовпадение записей, артефакта или конфигурации
отклоняет старт. Частично прерванное первичное создание требует проверки владельца.
При runtime-ошибке вход закрывается, журнал получает одну запись с исключением;
выход через штатный `/spawn` сохраняется. Возобновление — после проверки данных
и рестарта. Маркеры нельзя просто удалять ради обхода ошибки: нужен разбор
сохранения и согласованный план восстановления/вайпа.

До первого запуска людей остаются: графический клиент с JED, квестовый прогресс
после сброса, безопасный `omk`-вайп с backup и эвакуацией,
включая игроков, вышедших из игры в ресурсном измерении,
устранение устаревших homes/claims/portals после вайпа и отрицательные сценарии
всей процедуры. Массовая предгенерация выполняется позже (#37).

### Контракт безопасного сброса

Доступен первый read-only шаг — [owner inspection](RESOURCE_RESET_INSPECTION.md):
сводка известных player/FTB/JED ссылок в остановленном источнике, без записи мира.

Это план следующего этапа #32, а не уже доступная команда. Сброс готовится
в **новом Linux Docker volume** из свежего проверенного снимка остановленного
сервера. Исходный volume и архив сохраняются; удаления DIM в работающем сервере
и автоматического переключения на новую копию не будет. Используется существующий
owner cold-backup, без второго расписания копирования.

План должен закреплять исходный lifecycle checkpoint, SHA снимка, конфигурации,
двух маркеров и allowlist измерений. На первом этапе разрешён только ресурсный
мир; основной мир, неизвестный ID, изменившийся источник и незавершённая прежняя
операция отклоняются. Старая DIM и её внешняя запись не переносятся в новую
копию только после записи плана; остальные файлы сравниваются с исходным снимком.

До проверки запуска новой копии нужны отдельные адаптеры:

- игроки, включая вышедших в ресурсном мире: перенос в проверенную безопасную
  точку основного мира; сохранение вещей, опыта и квестов, проверка резервных
  player NBT и точек возрождения;
- FTB: только ресурсные homes, warps, claims и ссылки возврата; права, команды,
  членство и данные остальных измерений сохраняются;
- JED и модовые телепорты: разбор сохранённых ссылок на старую DIM. Неизвестная
  ссылка требует проверки адаптера; массовая замена всех чисел с ID измерения
  недопустима. Проверка одних homes не подтверждает безопасность порталов.

Частичная запись не считается завершённым сбросом и не повторяется поверх той
же копии. Нужны журнал и независимая проверка результата после прерывания.
Приёмка в Docker включает нехватку места, неверный ID/маркер, смену источника,
повтор и прерывание операции, вход online/offline игроков, отсутствие старых
переходов, сохранность других миров и квестового прогресса. До этой приёмки
`ready_for_players` остаётся `false`.

Генерация и переходы/смерть/restart с двумя квестами на текущей паре описаны
[отдельно](RESOURCE_GENERATION.md): 78 условий полной DJ2, 94 общего Core без DJ2Fix,
сохранения и могила проверены независимо. Это не полное прохождение сборки.

Предыдущая приёмка основы 0.3.4: 98 условий полной DJ2 и 90 минимального Forge, по два старта;
десять отдельных контролей, включая восемь ожидаемых отказов. Условия включают
подготовку и метаданные. Независимое чтение TAR/Anvil/NBT — 71 + 60 проверок;
[протокол, SHA и границы проверки](validation/dj2-resource-foundation-2026-11-07.json).
Это протокольные игроки на настоящем сервере, без проверки рендера клиента.
