# История ресурсов сервера

Приватный Python-сервис для Linux/cgroup v2. Не устанавливается автоматически,
не добавляет игрокам команды или экран в лаунчер. Конфигурация Docker находится
в `deploy/metrics/`; исходники — `omk/resource_metrics.py`, `resource_store.py`
и `resource_history.py`. На VPS включаем только после аудита владельца.

## Что записывается

- CPU всей Linux VM: полезная занятость, `iowait`, отдельно `steal` и число
  логических CPU. Guest-счётчики повторно не прибавляются.
- Память: total, available, used = total − available; swap, major faults,
  swap-in/out и kernel OOM. `available` учитывает возвращаемый файловый cache.
- PSI CPU/memory/I/O: `some`/`full` за последние десять секунд, если есть у ядра.
- Разрешённые диски: чтение/запись, среднее время завершённых операций,
  занятость и in-flight. Это среднее, **не p95/p99 задержки**. Секторы diskstats
  считаются по 512 байт независимо от физического сектора устройства.
- Разрешённые сетевые интерфейсы: байты, ошибки, drops и скорости.
- Указанные файловые системы: общий/занятый/доступный размер и свободные inode.
  Это статистика всей ФС, **не обход файлов и не размер одной папки**. Две папки
  на одном диске не означают два независимых запаса свободного места.
- Указанные cgroup сервисов: populated, memory.current, memory.max (если конечен),
  swap, CPU в ядрах, throttling (если счётчик предоставлен), OOM и kernel block I/O.
  `cpu_cores=1.0` означает в среднем одно полностью занятое логическое ядро;
  потребление может быть больше единицы. memory.current включает cache,
  **это не Java heap и не RSS процесса**.

В каждой записи: UTC Unix timestamp, host boot UUID, новый UUID процесса
сборщика, sequence, hash конфигурации, объявленные владельцем версии сервисов
и fingerprints наблюдаемых cgroup. Версии не извлекаются из Docker image и
не доказывают, что именно такой JAR сейчас запущен.

Имена игроков, чат, IP игроков, environment/argv процессов, Docker inspect,
секреты Drasl и содержимое миров не читаются. У сервиса нет сети, портов,
Docker socket, host PID namespace и расширенных capabilities. Счётчики CPU,
памяти, PSI, диска, сети и boot ID смонтированы отдельными readonly файлами;
весь host `/proc` не монтируется. Корень cgroup доступен readonly, обход
ограничен одним уровнем внутри явного allowlist.

## Данные и ограничения размера

В named volume `history`:

```text
/history/history.sqlite3
/history/.writer.lock
/history/history.sqlite3-journal   # только во время транзакции/после её обрыва
```

Каталог 700, файлы 600; сервис работает как UID/GID 10001. Первый запуск нового
volume наследует владельца каталога из image. Чужие файлы, symlink/hardlink и
неизвестная версия схемы приводят к отказу; утилита не удаляет их «для починки».

По умолчанию замер раз в 30 секунд, подробности **до 7 дней**, часовые сводки
**до 180 дней**. SQLite main DB ограничена `max_page_count`: **64 MiB**.
Это верхние сроки, не гарантия хранения всего периода: при заполнении раньше
удаляются самые старые подробности, затем старые сводки. В часовой сводке для
каждой метрики хранятся число доступных измерений, min/max и сумма; mean —
обычное среднее доступных samples, не среднее с весом по времени. Пропущенное
значение в среднее не попадает. Metadata и payload не имеют неограниченной
кардинальности; одна запись до 128 KiB, одна часовая сводка до 256 KiB.

Используется DELETE journal с `synchronous=FULL`, без WAL и фонового VACUUM.
Во время записи rollback journal может занимать примерно ещё одну базу.
Для бюджета считаем **2 × DATABASE_MIB + 1 MiB**, плюс настроенный свободный
резерв. На default 64 MiB это 129 MiB логического бюджета, не отдельная квота ФС.
Существующую базу большего размера автоматически не ужимаем. Нельзя уменьшать
budget ниже существующего файла: сначала сохранить/отдельно архивировать историю.

Детали и часовой агрегат публикуются одной SQLite-транзакцией. После обрыва
незавершённая пара откатывается. Retention выполняется отдельной транзакцией:
обрыв может удалить уже истёкшую историю без добавления нового sample, но не
создаёт неполную пару. Один store допускает только одного writer через OS lock;
параллельные read-only отчёты имеют timeout. При дефиците свободного места writer
останавливается с фиксированной ошибкой и не чистит миры, бэкапы или чужие логи.

Это не аудит действий и не неизменяемое доказательство. Данные устаревают и
вытесняются. При необходимости продолжительной истории увеличиваем env budget
или сохраняем согласованную копию через SQLite backup API. Копировать живой
`history.sqlite3` простым `cp` для резервной копии нельзя; остановленная копия
допустима. История ресурсов не заменяет бэкап игры/аккаунтов и не создаёт второй
world backup writer.

## Настройка

`deploy/metrics/example.env` содержит deploy overrides, `config.example.json` —
образец разрешённых источников. Значения interval/retention/DB/reserve проверяются
до запуска; невалидные значения не подменяются молча defaults. Порты отсутствуют.
Лимиты CPU/RAM/PIDs, Docker log rotation, restart и health interval тоже в env.
Пути `/history`, `/host`, `/cgroups`, `/storage` — внутренний контракт контейнера.

Для VPS задаём свободный резерв **всего проекта**, не только мониторинга:
пример использует 24576 MiB. Внутренняя библиотека по умолчанию оставляет 1024 MiB;
это не готовая конфигурация целого production-сервера.

До запуска владелец задаёт реальный диск (`lsblk`), интерфейс (`ip link`) и
cgroup. Образец с пустыми `disks/interfaces` не собирает эти два раздела.
Не угадываем `vda`/`eth0` или расположение cgroup по названию VPS. Отсутствующий
разрешённый источник отмечается `unavailable`; неизвестные устройства не сканируются.

Для сервиса удобно использовать постоянный cgroup parent, но он должен быть
выделен только этому логическому сервису. На cgroupfs пример parent `omk-dj2`;
на systemd используем существующую выделенную slice и её фактический путь,
например `omk-dj2.slice`. Это разные настройки драйверов. Exact leaf тоже
поддерживается, но после пересоздания Docker-контейнера его путь нужно обновить.
Parent даёт совокупную статистику детей; его memory.max может быть unlimited,
даже если дочерний контейнер имеет свой лимит. **Не выдавать это за отсутствие
лимита у дочернего контейнера.**

Для config bind нужен отдельный файл, читаемый UID 10001 (например владелец
10001, mode 400). Не меняем владельца всего `.omk-admin` и не монтируем папку
с credential files. Новый history volume создаёт Docker. Project bind readonly
используется только для statvfs, код не обходит его содержимое.

После аудита, на Linux, с подготовленными private env/config:

```sh
docker compose --env-file /opt/omk/.omk-admin/metrics.env -f deploy/metrics/compose.yaml config --quiet
docker compose --env-file /opt/omk/.omk-admin/metrics.env -f deploy/metrics/compose.yaml up -d --build
```

`restart=unless-stopped` действует только после явного запуска сервиса. Наличие
volume или строки в конфиге не доказывает, что сборщик работает. Healthcheck
проверяет **свежую committed запись**, а не существование SQLite. У Docker health
нет автоматической починки зависшего процесса: unhealthy нужно видеть владельцу;
обычный exited процесс перезапустится по restart policy.

## Читать отчёт

Типизированный read-only Python API для владельца и будущей TUI:

```python
from pathlib import Path
from omk.resource_store import hourly_report

report = hourly_report(
    Path("/history/history.sqlite3"),
    since=1794528000,   # Unix UTC; подставить нужный период
    until=1794614400,
    max_rows=1000,
    max_bytes=2 * 1024 * 1024,
)
```

`since/until` выбирают пересекающиеся **целые часы**, что явно указано в результате.
Записи разных host/config не склеиваются. При лимите строк/байтов `truncated=true`;
для продолжения делим период. Нет HTTP endpoint и новой группы игровых/omk-команд.
Все права на хранилище остаются административными.

Первый замер, смена boot/source fingerprint, уменьшение счётчика и пауза больше
трёх интервалов не дают rate; возобновляется baseline. Rate не мостится через
замеченное исчезновение источника. Рестарт самого collector начинает новый UUID.
Дети cgroup сравниваются по именам/inode; события, целиком прошедшие между двумя
замерами, не гарантированно различимы. Для сетевых интерфейсов/дисков видны только
имя и счётчики; незамеченную hot replacement с большими counters распознать нельзя.
При переводе часов назад append отказывает, без выдуманной непрерывной истории.

Docker Desktop показывает ресурсы **его Linux VM**, не Windows/macOS host.
Это не доказательство нагрузки уже купленного RX-4. На VPS наблюдаем саму Linux VM.

## Граница готовности #146

Эта часть закрывает host/cgroup/storage history. Для решения «поместится ли ещё
одна сборка» нужны также **настоящие TPS/MSPT, online, Java heap/GC и интервалы
жизненного цикла игрового сервера**. Этот сервис их не выдумывает и не выводит
из CPU%. Игровой адаптер и финальная корреляция остаются в issue #146. Пока их
нет, одного графика свободной RAM недостаточно для такого решения.

Проверки и точные границы опыта: [протокол](validation/resource-history-2026-11-13.json).
