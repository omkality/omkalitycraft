# Реестры мира при обновлении DJ2

При переходе 2.21.3 → 2.23.4 недостаточно запустить свежий мир. Удалённый мод или
переименованный предмет может затронуть старые контейнеры, playerdata и механизмы.
Проверка относится к #49; кандидат пока не принят, рабочий payload не переключён.

Владелец ранее разрешил начать публичные миры с нуля, без переноса прежних миров.
Поэтому первый запуск может использовать **fresh 2.23.4 после его полной приёмки**.
Конверсия старых предметов в #61 нужна для сохранения source-мира и остаётся
отдельной работой перед такой миграцией; она не должна откладывать проверку нового
клиента. Отказ/возврат уже отрепетированы. Это не разрешение автоматически вайпать
будущие миры игроков вместо обновления: после открытия для них обязателен полный
путь миграции с проверкой сохранности и отдельным решением владельца.

## Предварительная команда владельца

```powershell
uv run omk upgrade registry-audit --source old-level.dat --target fresh-level.dat
```

Оба файла — `level.dat` из **остановленных лабораторных копий**: source со старой
сборкой и fresh target с новой. Для собственного мира сначала сделать проверенный
полный снимок после безопасной остановки и читать его копию. Команда не определяет
состояние сервера и не делает snapshot сама; не направлять её на живой мир.
Сжатый и распакованный NBT ограничены каждый 2 МиБ. Отклоняются повреждённый gzip,
неполный набор основных реестров, неоднозначные mappings и пути через links/junctions.
Это ограниченный инструмент текущего стенда, а не универсальный парсер миров любого размера.

JSON содержит SHA256 сжатых входов и все сохранённые группы `FML/Registries/*/ids`.
Основные blocks/items/entities/biomes обязательны. Имена сравниваются буквально:
старые Galacticraft-биомы с пробелом и имена групп с несколькими `:` допустимы.
Числовые ID могут массово поменяться при нормальном remapping; само по себе это
не означает потерю блока или вещи. Пропавшие имена и исчезнувшая группа требуют
проверки: exit 1, `requires_registry_review=true`. Ошибка чтения тоже даёт exit 1,
но отдельное поле `error`, а не якобы пустой diff.

До 100 имён каждого added/removed изменения выводятся с полным `count` и явным
`truncated`. Exit 0 означает только отсутствие пропавших имён в этом сравнении.
`upgrade_accepted` **всегда false**: aliases, datafixers, реальные блоки/NBT, рецепты,
квесты, измерения, клиент и перевод команда не проверяет. Отсутствующий ID иногда
имеет штатную замену; одинаковое имя также не гарантирует одинаковый смысл/NBT.

## Что обнаружено на точных версиях

Сравнение двух Linux Docker-снимков Core 0.2.8 охватило 46 групп. В основных реестрах:

| Реестр | Source | Target | Пропало имён | Добавлено |
| --- | ---: | ---: | ---: | ---: |
| Блоки | 5786 | 5796 | 6 | 16 |
| Предметы | 10236 | 10227 | 35 | 26 |
| Сущности | 917 | 920 | 0 | 3 |
| Биомы | 160 | 160 | 0 | 0 |

Это снимки **разных свежих миров**, предварительная оценка реестров, а не успешная
миграция. Полный обезличенный diff и SHA256 сохранены в [отчёте](validation/dj2-registry-audit-2026-11-03.json).
Другие изменения есть в реестрах рецептов Bewitchment и интеграции EnderIO;
они тоже перечислены, но число пропавших имён нельзя превращать в число потерянных вещей.

В официальном target `groovy/preInit/mappings.groovy` вызов `Fixer.init()` стоит
под условием `!isDedicatedServer()`; комментарий автора сообщает о проблеме на серверах.
Часть отсутствующих item mappings обработчик помечает `ignore()`. Это подавляет
ошибку mapping, но само по себе не конвертирует NBT предмета.

Авторские классы содержат преобразования ActuallyBaubles, кристаллов MATC, Natura,
MorphTool → Omniwand и старых wireless AE2 terminal/card. Для Storage Drawers Extras
сам файл сообщает об отсутствии рабочего datafixer. Нельзя вслепую включить все
конвертеры на сервере или принудительно подтвердить потерю ID ради успешного старта.

Источник — точный [официальный server pack 2.23.4](https://github.com/Divine-Journey-2/Divine-Journey-2/releases/download/2.23.4/Divine_Journey_2.23.4_Server_Pack.zip),
SHA256 `692c820a636ab59a050ba560235e3af9852f598d18f5dad931271e4cbd729831`.
Код сборки не копируется в публичный репозиторий.

## Нативная репетиция отказа и возврата

На новом стенде пройдены **50 условий игрового сценария и 12 независимых проверок
остановленных снимков**. [Отчёт с hashes и результатами фаз](validation/dj2-migration-rejection-rollback-2026-11-03.json).
Каждая фаза — отдельный новый Docker volume; лимиты 4 CPU / 6 ГиБ контейнеру /
4 ГиБ Java heap, тот же закреплённый Linux Java image и Core 0.2.8. Drasl остаётся
одним временным сервисом на все три фазы, поэтому UUID не меняется.

1. На source 2.21.3 протокольный игрок создаёт FTB team/claim/home. Консоль завершает
   один известный квест и готовит инвентарь, сундук с 15 именованными legacy-вещами,
   настоящий блок Storage Drawers Extras и работающие AE2/EnderIO/Thermal.
   Clean-stop даёт полный архив: 266 файлов, 6 767 210 распакованных байт; hash/readback
   проверены. Это только специально созданный мир, не старый сервер владельца.
2. Копия полного мира помещается в новый runtime 2.23.4, без старых recipes/scripts.
   Первый exploratory запуск без заранее выбранного ответа остановился в
   `FMLServerHandler.queryUser → StartupQuery.confirm → GameData.injectSnapshot`.
   Стеки сняты через SIGQUIT; OOM нет. Небезопасный ответ не отправлялся. После
   неуспешной отмены через консоль владелец стенда остановил только свой контейнер
   (exit 143); его volume сохранён для разбора. Это не clean-stop и не успешная миграция.
3. В полном повторе Linux-стенд использует `-Dfml.queryResult=cancel`. Target
   отказывает до `Done`, примерно за 114 секунд вместе с подготовкой/загрузкой,
   без интерактивного таймаута, OOM и подтверждения удаления mappings. Exit 0 в этой
   фазе означает завершение процесса после отмены, **не готовый игровой сервер**.
4. Исходный архив, чей hash не изменился, запускается на 2.21.3 в третьем volume.
   Игрок с прежним UUID получает свой инвентарь и может выполнить `/home backuporigin`.
   Все 15 вещей с marker/count, блок ящика, AE2 с семью именованными алмазами,
   энергия/лимиты двух EnderIO-блоков и результат плавки Thermal проверены в игре.
   Возврат завершён clean-stop; source/rollback volumes удалены только после
   проверенного экспорта. Временная авторизация удалена после всех фаз.

Чтение сохранённых NBT/JSON отдельно подтвердило полное равенство NBT сундука и
ящика, инвентаря игрока, claims, идентичности/состава команды, завершения квеста 1
тем же UUID и имён/чисел реестров. Набор папок измерений сохранён, но это не проверка
игры в каждом измерении. Проверка содержимого ящика использовала пустой fixture;
перенос заполненного модового хранилища на target ещё не доказан.

Первый pilot не принят: helper от другого recovery-сценария ожидал в соседнем
сундуке золото, хотя этот source содержал железо. Ошибка теста исправлена; весь
цикл заново пройден на новых данных. Его частичные условия не прибавлены к 50/12.

## Что ещё блокирует принятие

Необходимы отдельные доказательства конверсии количества/NBT/вложенных инвентарей,
FTB claims/home/team, прогресса BetterQuesting и всех измерений. Возможная потеря
энергии/привязки терминала по дизайну авторского конвертера требует явного решения.
Нужны несколько принятых запусков target, настоящий клиент и перевод. Безопасный
возврат source не доказывает безопасную миграцию в target. Работа продолжается в
[#61](https://github.com/omkality/omkalitycraft/issues/61) внутри #49; read-only diff
и эта репетиция отказа/возврата не закрывают полную приёмку обновления.
