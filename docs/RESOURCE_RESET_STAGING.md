# Копия данных для сброса ресурсного мира

Следующий слой после [read-only inspection](RESOURCE_RESET_INSPECTION.md) —
внутренний Linux worker `omk.resource_reset_stage`. Он строит **новую копию данных**
из свежего проверенного backup, не меняет источник и не запускает сервер.
Owner CLI пока предоставляет только `resource-resets inspect`: рабочей команды
сброса и автоматического переключения томов ещё нет.

## Что делает подготовка

1. Проверяет закреплённые FTB/JED, Core resource policy, SHA JED-конфигурации,
   allowlist ID и обе записи принадлежности ресурсного мира.
2. Требует последний сохранённый snapshot существующего managed backup store.
   Полный inventory текущего мира должен точно совпадать с проверенным архивом.
   Незавершённая публикация, неизвестные файлы, другой snapshot или изменившийся
   мир приводят к отказу до записи кандидата.
3. Строит план с operation ID, SHA архива, inventory/runtime источника,
   resource identity, координатами кандидата эвакуации и ожидаемым SHA результата.
   Планирование не пишет ни в source, ни в backup, ни в target.
4. В пустом target сначала эксклюзивно записывает план. Из архива копируются
   остальные файлы мира; `DIM-18000/` и внешняя запись
   `omk-resource-world.properties` в новую копию не попадают. Исходная DIM и
   полный backup сохраняются. Seed/config этим шагом не меняются.
5. Меняет только рассмотренные записи ниже. Все остальные файлы сохраняются
   byte-identical; изменённые NBT проходят readback, полный target — сверку inventory.
   Только затем появляется durable receipt завершённой подготовки.

Source и backup монтируются read-only, запись разрешена только в новый target.
Helper работает без сети, Docker socket и дополнительных capabilities, с pinned
Python image. Контроллеру будущей рабочей операции ещё предстоят ownership/lifecycle
проверки и общая owner-блокировка на всём протяжении процедуры.

## Рассмотренные изменения

**Обязательное правило для вайпа любого мира:** убрать все его приваты, дома и
публичные варпы у всех игроков. Другие измерения/серверы, членство в командах,
права и ранги сохраняются. Также очищаются известные death/back ссылки, чтобы
возврат не вёл в прежнее состояние мира.

FTB 5.4 фильтрация вынесена в общий `omk.ftb_dimension_references`: он работает
по переданному dimension ID, включая 0, положительные сюжетные и динамические ID.
Трёхэлементные legacy позиции относятся к основному миру. Политика допустимости
самого вайпа остаётся отдельно: data staging сейчас разрешает только проверенный
ресурсный ID; команды сброса остальных миров ещё предстоят. Для GTNH/других
версий хранилища нужны соответствующие адаптеры с тем же правилом очистки.

| Данные | Действие |
|---|---|
| Player NBT и `.dat_old`, сохранённые в ресурсе | Dimension 0 и заданная позиция кандидата; обнуление скорости/накопленного падения, portal cooldown. UUID, здоровье, вещи, опыт и capabilities сохраняются. |
| Выбранное ресурсное измерение респавна | Снять `HasSpawnDimensionSet` и убрать ресурсный `SpawnDimension`. Координаты кровати **основного мира** `SpawnX/Y/Z/Forced` сохраняются. |
| Forge `Spawns` | Убрать только элементы с ресурсным `Dim`; кровати остальных измерений сохраняются. |
| FTB homes, warps, legacy death/back и teleportTracker | Убрать только ссылки на ресурсный ID, включая fake player. |
| FTB claimed chunks | Убрать только ресурсное измерение; остальные чанки, признаки forced loading, команды и права сохраняются. |
| JED current/legacy player dimensions | Поменять только ресурсный Dimension на 0; GameMode/HardcoreDead и остальные поля сохраняются. Дубли UUID и смешанный формат отклоняются. |
| Неизвестные модовые файлы и NBT | Сохраняются. Это не означает, что их межмировые ссылки безопасны после сброса. |

Игрок на транспорте (`RootVehicle`/старый `Riding`) в ресурсе требует отдельного
адаптера; его данные не удаляются ради продолжения операции. Некорректный формат
или превышение рассмотренных лимитов также приводит к отказу.

Формат respawn сверен с [Forge 1.12.x EntityPlayer patch](https://github.com/MinecraftForge/MinecraftForge/blob/1.12.x/patches/minecraft/net/minecraft/entity/player/EntityPlayer.java.patch),
FTB — с закреплёнными JAR и локальным upstream, JED — с
[закреплённым исходником](https://github.com/maruohon/justenoughdimensions/blob/b3929ed6b0775954dd3eba463de9b528ba4a3769/src/main/java/fi/dy/masa/justenoughdimensions/event/DataTracker.java).

## Прерывание, место и повтор

Используются переданные лимиты существующего backup policy: staging/reserve и
максимальный распакованный мир. Перед записью считаются несжатый объём результата,
запас под файловую систему и фактическое свободное место target.

Эксклюзивный файл плана допускает одного writer при гонке. Непустой target,
включая частичный результат прерванной попытки, не принимается для нового stage.
Никакого повторного извлечения поверх старых данных или автоматического удаления
такой копии worker не делает. `verify` заново проверяет source, backup, план и
каждый файл результата: одного receipt недостаточно. Успешный verify подтверждает
только подготовленные данные.

В новом target находятся `.omk-resource-reset-plan.json`,
`.omk-resource-reset-staged.json` и каталог мира (`world/` в обычном развёртывании,
`lab-world/` на стенде). Полный архив и исходный мир остаются в своих Linux volumes.
Новых scheduler или backup writers нет.

## Что ещё блокирует запуск

Результат всегда содержит `promoted=false`, `ready_for_start=false`,
`landing_verified=false`, `portal_adapters_reviewed=false`. Координаты имеют
проверенный формат, но collision/safety точки должен подтвердить игровой сервер.
Не рассмотрены все ссылки в модовых порталах, предметах и shared saved data.
Здесь нет runtime deployment, подключения к Drasl, старта Minecraft или cutover.

До рабочей owner-команды нужны безопасная эвакуация online/offline игроков,
политика модовых переходов, сверка актуальных runtime/access/ranks, запуск новой
копии и проверка сохранности квестов/предметов/других миров в настоящем Forge.
Ручное удаление DIM или изменение маркеров не заменяет эти этапы.

## Доказательства текущего этапа

Исходные данные — архив штатно остановленного DJ2 2.23.4/Core 0.3.5/DJ2Fix 0.1.3
из [графического опыта](RESOURCE_CLIENT.md). Сам data worker проверяет три FTB/JED
артефакта и resource-конфиги; это не запуск полного игрового runtime.

На принятой копии: из 320 файлов осталось 301; исключены ровно 19 файлов
ресурсного дерева/внешнего маркера. Изменились ровно три записи: offline игрок,
его ресурсный home и server claims спавна. 1444 чанка основного спавна сохранены;
196 ресурсных claims убраны. Остальные сохранённые файлы, включая основной мир,
BetterQuesting и Astral data, совпали побайтно.

Docker-проверки включают read-only source/store, реальную маленькую tmpfs,
конкурирующих writers, принудительное завершение worker посреди извлечения,
отказ повтора/незавершённой копии и выявление подмены region-файла.
`.dat_old`, кровати, непустые warps/back и current/legacy JED проверены на
синтетических данных; в native архиве таких непустых записей не было.
После сброса Minecraft в этом этапе не запускался; byte-identical QuestProgress
не является проверкой игрового прогресса после restart.
