# Общий Core и исправления сборки

Серверная интеграция Forge 1.12.2 разделена на два приватных артефакта:

| Компонент | Назначение |
| --- | --- |
| OmkalityCore 0.3.2 | Проверка заявленного client mod list, административные операции с подключениями, диагностика, API расширений и необязательная интеграция FTB |
| OmkalityDJ2Fix 0.1.1 | Проверенная для DJ2 композиция патчей ванильных механизмов, Twilight Forest и WR-CBE |

Core не содержит bootstrap MixinBooter, конфигураций mixin или классов патчей TF/WR.
Он загружается на минимальном Forge без этих модов и без FTB. Авторизация остаётся
в Drasl + authlib-injector; проверка заявленного списка не доказывает содержимое
изменённого клиентского процесса.

FTB остаётся владельцем claims, полномочий, домов и таймеров. Проверенная реализация
подключается для поддерживаемого сочетания версий, Iron Chest необязателен.
При выключенных владельцем FTB-приватах общий Core и интеграция мута работают,
а источник данных о приватах остаётся неактивным. Явная конфигурация spawn/RTP требует
активных claims. Неподдерживаемое сочетание не выдаётся за работающую защиту.

## Версии и требования профиля

DJ2Fix 0.1.1 требует Core версии `[0.3.2,0.4.0)` и API 1. Core не импортирует DJ2Fix;
исправления регистрируются через небольшой интерфейс расширения. Подготовка
WR-CBE выполняется перед остальными интеграциями, затем включаются защиты мира.
Чтение владельца территории — общий интерфейс с реализацией FTB. Его представление
используется только в рамках одной нативной операции, не сохраняется как кэш claims.

Core 0.3.2 добавляет общий необязательный сервис прав размещения игрока. DJ2Fix 0.1.1
использует его перед записями одной проверенной механики роста; поздний rollback не
применяется. [Правило, отклонённый кандидат 0.3.1 и проверки](DJ2_PLANT_PLACEMENT.md).
Оригинальная приёмка разделения ниже относится к сохранённой паре 0.3.0/0.1.0;
новые результаты публикуются отдельным протоколом, старые не переписываются.

Файл владельца `config/omkalitycore-profile.properties` содержит:

- `schema=1` и идентификатор профиля;
- `required.extensions`: обязательные расширения с точными версиями;
- `required.capabilities`: возможности, которые должны действительно включиться.

Отсутствующее или несовместимое обязательное расширение отклоняется при запуске.
Отсутствующая обязательная возможность также отклоняет запуск. Forge может успеть
напечатать `Done` до ошибки позднего mod callback: это сообщение само по себе не
является приёмкой работоспособности. Стенд дополнительно проверяет процесс и fatal-log.

Для generic-профиля файл необязателен. Для DJ2 требуется явный профиль и DJ2Fix.
В приватном соседнем проекте находятся:

- `packs/dj2/profile.properties` — требует также настроенные spawn/RTP;
- `packs/dj2/lab-profile.properties` — намеренно оставляет spawn/RTP ненастроенными
  для старых изолированных boundary-фикстур. Не является production-политикой.

Миры, радиусы, задержки, квоты и одобренный client mod list остаются внешними данными.
Новая сборка с теми же поддерживаемыми интеграциями переиспользует Core, но проходит
собственную приёмку. Иная версия Minecraft, включая GTNH 1.7.10, требует отдельной
реализации под свой loader/API.

## Сборка и лаборатории

Оба серверных JAR собираются в одном приватном проекте `../omkalitycore`.
Повторно используемые алгоритмы находятся в `patches/src`, композиция DJ2 —
в `packs/dj2`, необязательная реализация FTB — в `integrations/ftb/src`.
Классы Core не дублируются в DJ2Fix. Старый Core 0.2.11 сохранён как контроль.
Исходники, JAR, полные фикстуры и modpack payload в публичный репозиторий не входят.

`build.py --target core` не требует MixinBooter; FTBLib нужен компилятору для
необязательной интеграции, пользователю без FTB он не навязывается.
`--target dj2` собирает исправления против готового Core, default `all` — оба JAR.
Сборка проверяет закреплённые входные SHA256 и раздельный состав выходов.

Лабораторные команды поддерживают явные `--pack-fix` и `--server-profile`, включая
`dj2-claims`, `dj2-account-recovery`, `dj2-linux`, `dj2-mcp`, RTP/spawn/crash/recovery
стенды. Для модульного Core подготовка DJ2 отклоняет отсутствующую пару до копирования.
Старые монолитные контрольные опыты остаются доступны с прежними входными параметрами.

```text
uv run omk lab dj2-claims --suite all --server-source PATH_TO_ISOLATED_DJ2 --agent PATH_TO_AUTHLIB --core PATH_TO_CORE --pack-fix PATH_TO_DJ2FIX --server-profile PATH_TO_REVIEWED_LAB_PROFILE --mods-json PATH_TO_APPROVED_CLIENT_MODS
```

Состав клиента и сервера задаётся отдельно. Эти два JAR — серверные; существующий
клиентский сетевой адаптер пока не объединён с ними и не изменён. Различие физических
сторон описано в [документации Forge](https://docs.minecraftforge.net/en/1.12.x/concepts/sides/).
Игровую работу клиентских сборок и всех ОС серверные протокольные тесты не доказывают.

## Отчёты и ограничения

[Обезличенный протокол разделения](validation/core-pack-split-2026-11-06.json)
привязан к конкретным SHA256 обоих JAR.
Native проверки выполняются только в свежих Linux Docker volumes; графический
клиент этим этапом не объявляется проверенным. Рабочие миры, подписанные player
releases и действующие профили не переключаются.

| Проверка новой пары | Условия | Независимое чтение сохранений |
| --- | ---: | ---: |
| Минимальный Forge: 4 рабочих режима и 4 ожидаемых отказа | 44 (8 — отказы) | — |
| DJ2: claims/containers/mute/auth | 54 | 8 |
| DJ2: ванильные границы | 229 / 111 сценариев | 162, включая 150 блоков |
| DJ2: эффекты мира TF | 300 / 73 сценария | 8 |
| DJ2: сортировка инвентарей | 220 | 9 |
| DJ2: owner reset/recovery | 78 | 8 |
| Мир Core 0.2.11 → Core 0.3.0 + DJ2Fix 0.1.0 | 13 / два старта | 10 |
| Допроверка строгого профиля, спавна и могил | 74 / два старта | 10 |
| Допроверка RTP | 50 | 8 |
| Повторные подключения к полной DJ2 | 47 попыток | 9 |

После перехода старого изолированного мира сохранились Drasl/UUID, семь предметов,
12 уровней, личный дом и team claim. Посторонний не смог сломать блок, владелец смог.
Старый снимок остался byte-identical. Это замена серверной интеграции при той же
DJ2 2.23.4, не полная миграция modpack. Здоровые опыты завершились без fatal/OOM;
изменённый JAR отдельно получил ожидаемый отказ по pin. Состав и повторяемость сборок
прошли 14 проверок; физическая сверка подтвердила очистку 29 собственных scopes.

Spawn/RTP suites дополнительно повторены на той же паре; строгий community profile
включил обе возможности на двух стартах. [Результаты и диагностика входа](SERVER_LOGIN_DIAGNOSTICS.md),
[отдельный протокол](validation/split-policy-reconnect-2026-11-06.json).
Реализации mute, RTP, spawn, claim domain и recovery connections byte-identical
старому контролю. Последние строки таблицы дополняют первоначальную приёмку разделения.

Локальные отчёты минимального Forge находятся в `.local/core-split-<режим>-<id>/`:
`report.json`, `catalog.json`, `server-output.log`, `export/world-after.tar`.
У намеренно отказавших стартов может не быть мира; их собственное состояние
экспортируется отдельно перед очисткой. Сессии/учётные данные из лабораторий
публиковать нельзя.

Отдельный крайний случай #102: после отклонённого FML mod list минимальный сервер
иногда закрывает следующий протокольный вход того же UUID до LoginSuccess.
Это отказ соединения, не обход допуска или краш сервера. Независимый контроль
без Core воспроизвёл запись LoginSuccess в состоянии PLAY; исправление пока не принято.
Полная DJ2 прошла 47 попыток без этого симптома. Исчерпывающая reconnect-приёмка
других сборок не заявляется.
Общие незакрытые задачи #29/#33/#34/#49 сохраняют своё покрытие и ограничения.
