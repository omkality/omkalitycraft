# Переносимые релизы и автообновление

Игрок скачивает первоначальный дистрибутив один раз, распаковывает его в доступную для
записи папку и запускает `OmkalityCraft`. Дальше подписанное обновление проверяется при старте.

## GitHub Releases для игроков

Публичный Release/prerelease содержит готовый лаунчер, который игрок может скачать
и запустить. Срезы исходников/API для разработки отдельными Releases не публикуются:
для них есть Git-история, ветки и при необходимости неизменяемые теги.

Вручную прикрепляем только проверенные дистрибутивы для заявленных ОС и материалы
проверки целостности/лицензий. Windows-дистрибутив — portable ZIP с `.exe`, `_internal`
и ресурсами лаунчера; один `.exe` из него отдельно не распространяется. Backend/API,
`.git`, дерево исходников репозитория, тестовые данные, сервер, миры, модпак, Core и
учётные данные в пользовательский архив не входят. Необходимые лицензии зависимостей
остаются в дистрибутиве. Сборки Minecraft/Java устанавливаются механизмом лаунчера.

На VPS/CDN и в GitHub Release размещается один и тот же проверенный архив версии,
с совпадающими байтами/SHA256. Имя TUF target может включать hash prefix; это не
другая сборка. GitHub служит дополнительным местом скачивания лаунчера; доверие
автообновления остаётся у TUF, а не у названия GitHub Release или ссылки `latest`.
Описание публичного релиза ориентировано на игроков: изменения лаунчера, требования,
известные ограничения и правильный файл для скачивания.

GitHub автоматически добавляет `Source code (zip)` / `Source code (tar.gz)` из Git-тега
публичного репозитория. Это архивы самой платформы, не наши дистрибутивы и не содержимое
portable ZIP; отдельно исходники проекта туда не загружаем. Такое поведение описано в
[документации GitHub](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).
Эта политика не скрывает исходники существующего публичного монорепозитория.

Ранее созданный source-only prerelease `v0.3.0-dev8` переведён в черновик по уточнению
владельца. Его Git-тег сохранён без изменения. Первый публичный дистрибутив требует
настроенных публичных auth/API/CDN, рабочих ключей и проверки установки/входа/обновления.
Предпросмотры с loopback-адресами остаются локальными тестовыми артефактами.

## Структура переносимой папки

```text
OmkalityCraft.exe / OmkalityCraft    первоначальная программа запуска
_internal/                         её библиотеки
app_versions/                      загруженные версии лаунчера
instances/<profile>/               Minecraft, моды, Java, игровые файлы
cache/downloads/                   незавершённые загрузки сборки
userdata/                          сессия, журналы, временные файлы, кеш TUF
```

Новая версия извлекается в отдельную папку и не перезаписывает работающую программу.
Новый процесс должен открыть интерфейс и подтвердить одноразовую проверку здоровья.
При ошибке используется последняя подтверждённая версия, затем первоначальная.
Неудачный релиз запоминается до выхода исправленного. При недоступном CDN остаётся
рабочая копия и видимое сообщение. Подписи и сроки действия ради загрузки не обходятся.

## Модель доверия

`python-tuf` проверяет root/targets/snapshot/timestamp, SHA256, длины, срок действия
и откат метаданных. Первоначальный дистрибутив содержит публичный корень доверия.
ZIP ограничен по размеру/числу файлов; обход папок, символические ссылки и пути личных
данных не допускаются. Здоровье означает запуск окна, а не отсутствие всех ошибок релиза.

Приватные ключи хранятся **вне** публичного репозитория обновлений/CDN, Git и дистрибутива.
Команда выпуска проверяет размещение. Тестовые ключи в `.local` не являются готовой
эксплуатационной процедурой: перед публикацией нужны резервная копия ключей и отдельное
хранение root/targets для выпуска. Подпись Windows/macOS — отдельная задача; TUF её не заменяет.

Корень по умолчанию действителен 3 года, targets/snapshot — 90 дней, timestamp — 30 дней.
Издатель обновляет метаданные до истечения, даже без изменений кода: тот же архив и версия
могут быть выпущены повторно для обновления метаданных. Изменение содержимого требует новой версии.
Ротация root выполняется отдельно с сохранением последовательности версий и подписей.
Прежние versioned metadata и архивы не удалять при публикации нового набора.

## Подготовка приложения

Первый `omk release launcher` создаёт локальный репозиторий и ключи. Для начального корня
можно использовать маленький тестовый ZIP; он не должен становиться публичным дистрибутивом.
В CI такую изолированную подготовку выполняет `scripts/smoke_bundle.py --prepare`.

После создания корня:

```powershell
uv run python scripts/build_launcher.py --output .local/portable-build --root-metadata .local/update-repository/metadata/1.root.json --auth-url https://AUTH-ORIGIN --api-url https://CDN-ORIGIN
uv run python scripts/smoke_bundle.py --bundle .local/portable-build/OmkalityCraft
uv run omk release launcher --repository .local/update-repository --keys-dir .local/update-keys --archive .local/portable-build/OmkalityCraft-0.3.0.dev1-windows-x64.zip --version 0.3.0.dev1 --entrypoint OmkalityCraft.exe --platform windows-x64
```

Адреса — заполнители. Публичные хосты эти команды не создают.
HTTP разрешён только для loopback. На Linux/macOS entrypoint не имеет `.exe`.
Каждая сборка создаётся на своей ОС. Версии используют PEP 440.

Сборщик копирует разрешённые исходники и публичные ресурсы, создаёт конфигурацию адресов
внутри дистрибутива. На Windows ограничивается PATH упаковщика, чтобы не включать чужие
ICU/Qt DLL из инструментов разработки. Используется PyInstaller onedir без временной
распаковки приложения в системный temp.

Проверенные файлы размещаются под `CONTENT_ROOT/updates/{metadata,targets}`.
API предоставляет только чтение `/updates/metadata/...` и `/updates/targets/...`.
Consistent snapshots используют неизменяемые имена архивов с SHA256 и версии метаданных.
Сначала публикуются архивы и versioned metadata, последним — timestamp.
Команды подготовки не развёртывают сервисы и не меняют рабочий игровой сервер.

## Релизы модпака

Подготовленная папка `files` не содержит миров, токенов или старого OmkalityCore:

```powershell
uv run omk release pack --files .local/prepared-pack/files --launch-profile .local/prepared-pack/launch.json --private-key .local/pack-signing.pem --public-keys launcher/assets/release-keys.json --output .local/prepared-pack/manifest.json --pack-id dj2 --version 2.21.3-omk.1 --minecraft 1.12.2 --platform windows-x64
```

Публичный ключ сборки попадает в лаунчер до её распространения.
Контент размещается под `CONTENT_ROOT/releases/<profile>/<platform>/`:
`manifest.json` и `files/`. Описание подписано Ed25519, каждый файл имеет SHA256 и длину.
При прерывании сохраняется история прежних описаний для корректного удаления старых
управляемых модов после продолжения. Неизвестные установщику файлы не удаляются.
Конфиги из manifest управляются релизом; сохранения, карты и личные параметры исключены.

Тестовый DJ2 использовал **Temurin JRE 8.0.472+8 Windows x64** из локального архива старого
лаунчера. Исходный скачанный архив Java не переиздавался; файлы закреплены SHA256 в manifest.
Перед публичной раздачей нужны проверенные исходные дистрибутивы Java для каждой платформы
и сведения об условиях распространения содержимого сборки.

Новые внешние артефакты:

- authlib-injector **1.2.8**, build 56:
  https://authlib-injector.yushi.moe/artifact/56/authlib-injector-1.2.8.jar
  SHA256 `9c7f4343e6c82034958ffb48c14a2cb0c85928be7283103ce17da00c6d5a7b10`.
- Конфигурация логирования Mojang 1.12.2:
  https://piston-data.mojang.com/v1/objects/bd65e7d2e3c237be76cfbef4c2405033d7f91521/client-1.12.xml
  SHA1 `bd65e7d2e3c237be76cfbef4c2405033d7f91521`; SHA256 — в тестовом manifest.
- Rubik Medium: точные commit/SHA256 и лицензия записаны в
  `launcher/assets/fonts/provenance.json` и `OFL.txt`. Картинки сборок — собственные SVG.

Версии библиотек и сборщика закреплены `uv.lock`. Payload, приватные ключи и ZIP не входят в Git.


## Начальные настройки клиента

`launch.client_defaults` подписывается вместе с manifest. Готовый фрагмент DJ2 и происхождение
его настроек — в `profiles/client-defaults/`. До подписания добавьте настоящий адрес в `servers`
и объедините фрагмент с launch-profile. Публичного адреса пока нет. `initial_configs` поддерживает
только разрешённые JSON-конфиги JourneyMap 5.7, создаёт отсутствующие файлы и не управляет
исследованными картами/точками. `options.txt` и `servers.dat` аккуратно объединяются с личными
настройками; прежние байты сохраняются в `.omk-defaults-backups` внутри сборки.
