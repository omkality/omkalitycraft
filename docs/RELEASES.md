# Переносимые релизы и автообновление

Игрок скачивает ZIP для своей ОС, распаковывает целиком и запускает
`OmkalityCraft.exe` или `OmkalityCraft`. Дальше лаунчер проверяет обновления
при запуске. [Последний релиз для Windows x64, Linux x64 и macOS Apple Silicon](https://github.com/omkality/omkalitycraft/releases/latest)

## GitHub Releases для игроков

Прикрепляйте проверенные ZIP лаунчера с парными `.zip.sha256` и
`.release.json`. Архив содержит приложение, встроенный runtime, сведения
о компонентах и лицензии. Игровая сборка и Java загружаются отдельно с API/CDN.
Тег `launcher-v<версия>` указывает на исходники, из которых собран лаунчер.
Для источника автообновления используйте URL конкретного тега и ZIP.

В переносимой папке `_internal/` содержит библиотеки лаунчера,
`app_versions/` — его обновления, `userdata/` — сессию и журналы,
`instances/dj2/` — игру, `cache/downloads/` — незавершённые загрузки.
Переносите папку целиком и храните `userdata/` в частном доступе.

## Предрелиз для проверки владельцем

Публикуйте сборку из `dev` отдельным предрелизом по тегу вида
`launcher-v0.3.5-dev.1`. Дайте прямую ссылку на версионный ZIP.
Флаг `Prerelease` и параметр `make_latest=false` сохраняют прежний стабильный
выпуск по ссылкам `releases/latest/download/`. Подписанные цели TUF продолжают
указывать на стабильную версию. После публикации проверьте оба канала.
Перенос в `master` выполняется после согласования владельцем.

## Сборка и проверка

Запускайте сборщик на целевой ОС из зафиксированной ревизии. Укажите доверенный
публичный корень TUF, HTTPS-адреса авторизации и API, а также проверенные
минимальные поколения игровых профилей. Аргументы показывает
`uv run python scripts/build_launcher.py --help`.

Сборщик формирует portable ZIP, контрольную сумму и список файлов с SHA-256.
Перед публикацией проверьте материалы точного архива и справку о лицензиях.

```console
uv run --no-sync python scripts/smoke_bundle.py --prepare
uv run --no-sync python scripts/release_materials.py --archive <archive.zip>
uv run --no-sync python scripts/smoke_bundle.py --archive <archive.zip>
```

Для smoke-теста используется отдельно собранный архив с тестовым корнем
и loopback-адресами. Проверка запускает упакованный лаунчер и проверяет
распаковку и передачу управления. Для выпуска дополнительно проверьте
тот же комплект с рабочими адресами, публичным корнем, чистой установкой,
входом в игру и обновлением с предыдущего лаунчера.

Архивы с `OmkalityCraft.app` проверяйте на macOS через
`uv run --no-sync python scripts/smoke_bundle.py --finder-archive <archive.zip>`.
Проверка распаковывает ZIP в пустую папку, открывает приложение через Launch
Services и ждёт записи о первом рисовании окна в локальном журнале.
Приложение создаёт `userdata/`, `instances/` и папку загрузок рядом с
`OmkalityCraft.app`. Распаковывайте ZIP в папку, доступную для записи.

## Публикация обновления лаунчера

1. Подготовьте TUF-цель командой `omk release launcher` для каждой платформы.
   Передайте `--repository`, `--keys-dir`, `--archive`, `--version`, `--platform`,
   `--entrypoint` и `--github-asset-url`. Имя файла —
   `OmkalityCraft-<версия>-<платформа>.zip`, entrypoint на Windows —
   `OmkalityCraft.exe`, на Linux — `OmkalityCraft`, для архива с приложением
   macOS — `OmkalityCraft.app/Contents/MacOS/OmkalityCraft`.
2. Прикрепите версионные архивы к черновику GitHub Release. Туда же загрузите
   побайтовые копии под постоянными именами `OmkalityCraft-windows-x64.zip`,
   `OmkalityCraft-linux-x64.zip` и `OmkalityCraft-macos-arm64.zip`.
   После публикации стабильной версии проверьте ссылки
   `releases/latest/download/` из README и соответствие архивов
   подписанным размерам и SHA-256.
3. Разместите те же архивы и новые версионные метаданные в
   `CONTENT_ROOT/updates/{targets,metadata}`. Публикуйте `timestamp.json`
   последним. Сохраняйте прежние версионные файлы.
4. Запустите старый лаунчер и проверьте, что обновление открывается, а
   `userdata/` и `instances/` сохранены.

TUF проверяет подписи, сроки действия, версии метаданных, размер и SHA-256.
При недоступности GitHub загрузка того же подписанного архива начинается
заново с VPS. При неуспешном запуске сохраняется последняя рабочая версия.
Подписание ключами TUF выполняется офлайн. До истечения метаданных
обновите их даже при прежней версии программы. Штатные сроки — 30 дней
для timestamp, 90 дней для snapshot/targets и 3 года для root.

## Релизы модпака

1. Подготовьте клиентский набор `files/` для каждой платформы. Исключите
   личные данные, сохранения и серверные моды.
2. Подпишите `manifest.json` через `omk release pack`. Укажите профиль запуска,
   платформу, новую версию, `--generation` и совместимый
   `--minimum-launcher-version`. `--snapshot-root` сохраняет проверенный
   набор для будущего восстановления. [Снимки релизов](CLIENT_RELEASE_SNAPSHOTS.md)
3. Разместите манифест и файлы под `CONTENT_ROOT/releases/dj2/<платформа>/`.
   Проверьте установку, продолжение скачивания и вход для этого комплекта.

Лаунчер проверяет подпись и SHA-256 каждого файла. Первое поколение ограничено
встроенным минимумом, обновление — последним принятым поколением. Для отката
выпустите прежнее содержимое с **новым бо́льшим поколением**. Если набор требует
более новую версию лаунчера, сначала опубликуйте и проверьте обновление TUF.
[Установка подписанной сборки](SIGNED_PACK_INSTALL.md)

Начальные настройки и запись `Divine Journey 2 RU` задаются в профиле запуска.
Настройки карты применяются к отсутствующим файлам. При запуске игры
удалённая запись нашего сервера возвращается, личные серверы сохраняются.
[Клиентские настройки](../profiles/client-defaults/README.md)
