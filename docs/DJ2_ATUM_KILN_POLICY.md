# Согласование реестра печи Atum в DJ2 2.23.4

В холодном запуске DJ2 2.23.4 клиент мог отклоняться при входе:
`atum:kiln_recipes / atum:redstone_ore_redstone`. Совпадающие версии модов
не гарантировали одинакового реестра. Это отдельная проблема Atum, обнаруженная
при графической проверке перевода; подмена версии мода или отключение проверки
реестров её безопасно не решают. Задача: #175.

## Причина и изменение

Установленный Atum 2.0.20 автоматически переносит рецепты обычной печи в свою.
Его фильтр проверяет только последнее имя OreDictionary у результата.
У редстоуна сервер видел `dustRedstone, alloyBasic`, а клиент —
`alloyBasic, dustRedstone`. В результате только сервер добавлял спорный рецепт.
В наблюдении с обеих сторон было по 1284 обычных рецепта печи, но 133 и 132
ключа реестра Atum.

Штатный API `mods.atum.Kiln.blacklist("minecraft:redstone")` исключает результат
`minecraft:redstone` из автоматического переноса в печь Atum. В DJ2 уже есть
пример использования того же API для другого материала. Это небольшой скрипт
CraftTweaker в [общем дополнении клиента и сервера](../profiles/pack-overlays/dj2-2.23.4/README.md).
Политика соответствует уже задуманному исключению пыли из печи Atum.

После изменения с обеих сторон получены одинаковые 132 ключа. Удалён ровно
`atum:redstone_ore_redstone`, других изменений набора ключей не обнаружено.
Обычные рецепты печи сохранены: сверены число и наблюдавшиеся входы/выходы
редстоуновых рецептов; настоящая печь в игре переплавила руду в редстоун.
Редстоун как предмет не запрещается. Полное равенство входов/выходов всех
рецептов Atum этим опытом не доказывалось.

Проверки выполнены в изолированном Linux Docker и графическом клиенте Windows.
Сначала узкий read-only наблюдатель подтвердил причину на обеих сторонах.
Затем новый холодный стенд без диагностического мода, с прежней строгой
политикой 257 модов, успешно принял клиента. Обычный выход, повторный вход
без зависшей плашки, завершение клиента и сервера прошли без ошибки.
Стенды и их временные тома удалены после сохранения диагностики.

## Новый мир и обновление сохранения — разные проверки

Forge сохраняет `atum:kiln_recipes` в `level.dat`. В копии старого лабораторного
мира был лишний ID; установка политики привела к штатному отказу загрузки
с одной отсутствующей записью. Автоматического подтверждения не было.
Это ожидаемый защитный отказ, а не успешная миграция и не падение JVM.
Исходная лабораторная копия не изменена.

Мир, созданный уже с политикой, отдельно перенесён из остановленной копии
в новый Docker volume: повторный холодный старт и остановка прошли без ошибки.

Поэтому дополнение предназначено для **следующего кандидата с новым миром**.
Миграция уже существующего мира без политики остаётся отдельным условием
приёмки #175/#171. Нельзя объявлять произвольное включение/удаление этого
скрипта безопасным обновлением или возвратом версии.

Перед будущим изменением игровых данных нужны остановленный сервер,
контрольная копия мира и связанных данных, точный состав клиента/сервера
и отдельная проверка перехода на копии. Возврат должен восстанавливать
согласованный checkpoint; одного возврата Git-коммита недостаточно.

## Источники и ограничения

Проверено поведение установленного и закреплённого JAR Atum 2.0.20.
Аналогичный точный ID ранее описан в [upstream issue Atum #177](https://github.com/TeamMetallurgy/Atum2/issues/177).
Рекомендация авторов для другого расхождения OreDictionary есть в
[Atum #71](https://github.com/TeamMetallurgy/Atum2/issues/71#issuecomment-477843572).
Наш скрипт не меняет OreDictionary, не обновляет JAR и не обходит FML.

Пины и результаты: [машиночитаемый протокол](validation/dj2-atum-kiln-policy-2026-11-14.json).
Это не приёмка всей сборки, всех рецептов, перевода или всех ОС. Игровой
manifest, релизы лаунчера и VPS этим изменением не затронуты.
