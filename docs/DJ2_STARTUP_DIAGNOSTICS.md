# Диагностика непостоянного старта DJ2

Для текущего DJ2 проверяется небольшой конфигурационный обход: отключение
`optimizeFMLRemapper` в FermiumASM 5.24. Сам первоначальный триггер Mixin не исправлен
в upstream-коде. Диагностический агент тоже может влиять на порядок загрузки классов;
это учитывается при сравнении и требует игровых прогонов без него.

## Среда и память

Полный DJ2 запускается **на ПК владельца в Linux Docker**, не в GitHub Actions.
CI проверяет Python/Qt, Drasl и сборку/старт дистрибутива; многогигабайтный Forge
в CI не запускается. Текущий локальный Forge-контейнер ограничен 6 ГиБ памяти
и 4 CPU; Java получает `-Xms1G -Xmx4G`. Образ Temurin Java 8 закреплён digest
в `omk/dj2_linux_lab.py`. Это ограничения процесса, а не обещание производительности
арендованных vCPU, диска и внешней сети. Нагрузку игроков/фабрик проверять отдельно.

Отчёт теперь содержит `linux_container_outcome`: фактический лимит памяти/CPU,
`oom_killed`, `running` и `exit_code` Docker. В startup-lab такие же поля есть
для отдельных стартов. `java_oom_logged` и `native_allocation_failure_logged`
показывают соответствующие сигнатуры в ограниченном серверном логе.

`OOMKilled=false` само по себе не исключает Java OOM: JVM может исчерпать heap
и завершиться без убийства контейнера. Поэтому нужны одновременно Docker state,
журнал JVM/Forge и crash-report, если он существует. В исходном no-holder отчёте
оставалось около 1,5 ГиБ свободной памяти в выделенном heap; `OutOfMemoryError`
не был причиной зарегистрированного исключения.

При новом пойманном no-holder сбое контейнер **ещё работал**, `OOMKilled=false`,
Java/native OOM-сигнатур не было. Последующий код 143 получен при остановке
неудавшегося стенда, а не является доказательством OOM. Новые отчёты отдельно
помечают `lab_cleanup_stop_requested` / `lab_cleanup_docker_stop_requested`.
Снимок Docker state до очистки может содержать `running=true, exit_code=0` даже
при уже обнаруженном `LoaderExceptionModCrash` — это не успешный старт.

## Что установлено

В воспроизведённых падениях до ThaumcraftFix/ItemElementalShovel появляется
сообщение Mixin об исключении `DeobfuscationTransformer` из обработки метаданных.
В просмотренных успешных контрольных стартах такого сообщения нет.

Точечный replay на настоящем Forge 14.23.5.2860 подтвердил: передача `ItemBlock`
до деобфускации в `ItemBlockTransformer` воспроизводит тот же `no holder field`;
после деобфускации тот же преобразователь проходит. Обычная загрузка класса в JVM
при этом может быть правильной: ошибка возникает в отдельном проходе метаданных
Mixin. Поэтому одного итогового crash-report недостаточно — нужен предыдущий лог.

Это подтверждает механизм пропущенной деобфускации, **не первоначальную причину**
ложного/реального повторного входа. Ошибка AE2 при завершении сервера вторична.
Контроль A–B–A выполнен на одном новом клоне сохранённого сбойного volume:
исходное `true` ранее дало сбой на втором старте; с `false` прошли **6 стартов**;
после возврата `true` тот же no-holder вернулся на **первом старте**. Образ, JAR,
heap, CPU и Console-agent SHA256 оставались одинаковыми. Это существенно сильнее
одной удачной серии, но не доказывает отсутствие всех других сбоев.
Исходный сервер/конфиг и сохранённые сбойные volume не меняются.

## Применение обхода

`omk/dj2_startup_policy.py` готовит **новую остановленную копию** сервера:
меняет только `B:optimizeFMLRemapper`, сохраняя остальные байты/переносы строк.
Для текущего DJ2 default — `false`. Отсутствующая, слишком большая или неоднозначная
конфигурация отклоняется; настройка не добавляется молча в неизвестную версию мода.
Лаборатории, использующие `_copy_server`, получают эту настройку автоматически.
Рабочая папка сервера не обновляется и публичный сервер этим действием не развёртывается.

Операторский override — `OMK_DJ2_OPTIMIZE_FML_REMAPPER=false` (default), только точные
`true` / `false`. Пример: [deploy/dj2-startup.example.env](../deploy/dj2-startup.example.env).
`true` оставлен для контрольных экспериментов; он возвращает проблемную оптимизацию.
Forge не читает эту env сам: переменная используется Python при подготовке копии.
Без production Compose это ещё не готовый адаптер развёртывания VPS.

При `dj2-startup --evidence-run` после подготовки копируется прежний evidence-конфиг:
его значение сохраняется для воспроизведения исходного сбоя, вместо применения
env-политики поверх доказательств. Все эксперименты выполняются на новом volume;
источник подключается только для чтения. Console/ASM агенты в обычные игровые
стенды и профиль игроков не добавляются.

Без startup observer повторены **4 полных старта** и **93 игровые проверки** отката
области на свежем Linux volume: вход, контейнеры/NBT, соседние изменения, undo/redo,
сущности и ограничения частичного снимка, перезапуск и работа восстановленной печи.
Завершение — код 0, `OOMKilled=false`, экспорт мира и удаление только своего volume.
Это регрессия существующего лабораторного отката; известные ограничения WorldEdit
по сущностям и неполному архиву сохраняются. Длительная нагрузка фабрик/игроков отдельно.
Дополнительный свежий стенд без observer подтвердил вход полноценного Windows DJ2
на Linux Forge после обхода; сервер затем штатно остановлен и его volume удалён
после экспорта. Это не тест графического клиента Linux/macOS.
[Обезличенные результаты](validation/dj2-startup-workaround-2026-11-01.json).

Первичные исходники для сопоставления с установленным байткодом:
[Forge FieldRedirectTransformer](https://github.com/MinecraftForge/MinecraftForge/blob/1.12.x/src/main/java/net/minecraftforge/fml/common/asm/transformers/FieldRedirectTransformer.java),
[Mixin LaunchWrapper service](https://github.com/SpongePowered/Mixin/blob/0.8.7/src/launchwrapper/java/org/spongepowered/asm/service/mojang/MixinServiceLaunchWrapper.java).

## Воспроизводимый стенд

```text
uv run python -m omk lab dj2-startup --help
uv run python -m omk lab dj2-startup --server-source PATH --agent AUTHLIB_JAR --core PRIVATE_CORE_JAR --mods-json MODS_JSON --java JAVA8 --compiler ECJ_JAR --boots 3 --trace-mode console
```

Пути задаются явно, как для других DJ2-стендов. Проверяются точные SHA256 ECJ 3.26.0,
ASM 5.2, LaunchWrapper 1.12 и Forge 14.23.5.2860; версии/источники записаны в отчёт.
Неправильный артефакт отклоняется до Java-компиляции. Оригинальные JAR и Core в Git
не добавляются. Компилятор/игра не загружаются автоматически этим тестом.

`--boots` ограничен 1–12. По умолчанию создаётся новый loopback-стенд без старых
миров/учётных данных. Необязательный `--evidence-run HEX_RUN_ID` разрешает **только**
read-only копирование ранее созданного Linux lab volume с совпавшей ownership-меткой.
Работающий сервер-источник отклоняется; команда не останавливает его ради копии.
После копирования всё выполняется на новом собственном volume с отдельным Drasl.

| Режим | Что делает | Ограничение |
| --- | --- | --- |
| `console` (default) | Только JDK: наблюдает вывод, при нужном сообщении сохраняет стек, heap и стеки других потоков загрузки классов | Не преобразует игровые классы и не загружает внешний ASM; всё равно является наблюдателем |
| `exclusions` | Перехватывает только выбор исключения/цели метаданных Mixin | Инструментация может изменить порядок загрузки |
| `full` | Записывает поля/хеши ItemBlock до/после преобразователей, повторный вход и исключение | Самый заметный эффект наблюдателя; успешный запуск с ним не считается исправлением |

Console-режим дополнительно проверяет, что настоящий вывод Forge прошёл через
наблюдатель. Стек сохраняется один раз; имена потоков и значения аргументов
не записываются. Снимок heap — free/committed/max в момент сигнала, не пик RAM
всего контейнера и не атомарный снимок параллельного GC.

Артефакты находятся в `omkalitycraft/.local/startup-trace-lab-<id>/`:

- `progress.json`, `report.json` — ход проверки, результаты, ресурсы и хеши fixture;
- `server-output.log` и ротации — ограниченный stdout/stderr Forge;
- `boot-N.log` — снимок журнала отдельного старта;
- `trace-N/trace.txt` — наблюдения агента;
- `trace-N/*.class` — только в полном режиме, локальные снимки байткода;
- `export/world-after.tar` — экспорт мира при штатном завершении.

Полный агент ограничивает запись trace приблизительно 1 МиБ, class dumps — 16 МиБ
на старт (плюс несколько инструментированных классов загрузчика). Console-снимок
ограничен количеством потоков/кадров и длиной строк. stdout имеет ротацию 3 × 8 МиБ;
число дополнительных `boot-N.log` ограничено `--boots`. Docker log — 3 × 10 МиБ.
Старые лаборатории/сбойные volume автоматически не стираются: это отдельные
артефакты исследования, их место учитывать в бюджете ПК.

`ok=true` означает **завершённое наблюдение**, в том числе поимку ожидаемого сбоя.
Для доступности смотреть `all_boots_clean`, `same_failure_reproduced` и каждый старт.
Поле `root_cause_fixed` этим инструментом всегда остаётся `false`.

Не публиковать сырые `.class`/миры/полные серверные каталоги: они могут содержать
чужой байткод и закрытые данные. В репозиторий помещаются исходники наблюдателя и
проверенная обезличенная сводка. Агент не входит в лаунчер/manifest игрока, не ставится
на публичный сервер и не меняет политику авторизации.
