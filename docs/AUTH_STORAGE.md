# Постоянное состояние Drasl и проверка восстановления

Drasl локально и на будущем VPS использует один Linux runtime:
[`service.yaml`](../deploy/auth/service.yaml), образ `omkalitycraft-drasl:4.0.0-omk.2`,
один процесс и именованный Docker volume на `/var/lib/drasl`. База находится на
Linux-файловой системе Docker, не в Windows bind mount. В tmpfs остаётся только `/tmp`.
Версии upstream, два patch и сборочные проверки закреплены в
[описании образа](../deploy/drasl/README.md).

## Запуск постоянного экземпляра

Это шаблон будущего развёртывания, не команда миграции существующих аккаунтов.
До публичного использования нужны HTTPS/reverse proxy, rate limits, внешняя копия
бэкапов, мониторинг диска и проверка доступности домена (#38). Docker Desktop
использует Linux VM; ядро, диск, маршрутизация, TLS и доступный RAM на VPS могут
отличаться. Общий Compose устраняет расхождение контейнерной конфигурации, но не
заменяет финальный smoke на выбранном VPS.

```powershell
New-Item -ItemType Directory -Force .omk-admin | Out-Null
$env:OMK_AUTH_URL = 'http://127.0.0.1:25586' # На VPS: реальный HTTPS origin.
$env:OMK_AUTH_ADMIN = 'omk_owner' # Зафиксировать до первого аккаунта.
$env:OMK_AUTH_INTERNAL_PORT = '25585'
uv run omk auth configure --output .omk-admin/drasl.toml
$env:OMK_AUTH_CONFIG = (Resolve-Path .omk-admin/drasl.toml).Path
$env:OMK_AUTH_HTTP_PORT = '25586'
docker compose -p omk-auth -f deploy/auth/compose.yaml build --pull
docker compose -p omk-auth -f deploy/auth/compose.yaml up -d --no-build --pull never
```

Linux использует тот же Compose, переменные задаются через `export`/приватный
`--env-file`. Пароли/токены в эти переменные не помещаются. `configure` валидирует
origin, имя владельца, сроки и порт, создаёт TOML без секретов и **не перезаписывает**
существующий файл. После смены переменных конфиг нужно явно пересоздать/проверить;
порт `ListenAddress` обязан совпадать с `OMK_AUTH_INTERNAL_PORT`. Домен, имя проекта
Compose и набор DefaultAdmins нельзя менять как случайную настройку теста.
Сгенерированный конфиг и `operator.toml` хранятся отдельно от тома и резервируются
приватно вместе с описанием образа/параметров запуска.

Обычные `stop`, `down` и пересоздание контейнера сохраняют том
`omk-auth_drasl-state`. **Не применять `down --volumes`, `volume rm/prune` к этому
экземпляру.** Запуск с новым Compose project name создаст другую базу — это не
потеря старой базы и не способ её восстановления.

| Переменная | По умолчанию |
|---|---|
| `OMK_AUTH_URL` | `http://127.0.0.1:25586`, HTTP разрешён только на loopback |
| `OMK_AUTH_ADMIN` | `omk_owner` |
| `OMK_AUTH_HTTP_PORT` / `OMK_AUTH_INTERNAL_PORT` | `25586` / `25585` |
| `OMK_AUTH_TOKEN_EXPIRE_SECONDS` | 2592000, 30 суток |
| `OMK_AUTH_TOKEN_STALE_SECONDS` | 86400, сутки до обновления токена |
| `OMK_AUTH_MIN_PASSWORD_LENGTH` | 12 |
| `OMK_AUTH_CPUS` / `OMK_AUTH_MEMORY` / `OMK_AUTH_PIDS` | 1 / 384m / 128 |
| `OMK_AUTH_GO_MEMORY` | 300MiB, мягкая цель Go GC, не лимит процесса |
| `OMK_AUTH_TMP_SIZE` | 32m |
| `OMK_AUTH_LOG_SIZE` / `OMK_AUTH_LOG_FILES` | 10m / 3, драйвер Docker `local` |
| `OMK_AUTH_STOP_TIMEOUT` | 20s |

Корень контейнера read-only, capabilities сняты, no-new-privileges; запись разрешена
в state volume и ограниченный `/tmp`. Логи ротируются. `DRASL_DEBUG` принудительно
пустой: upstream считает даже строку `false` включением debug и может писать секреты.
384 MiB — принятый лимит маленького стенда, не доказанная ёмкость публичного сервиса.
Несколько реплик Drasl над одним SQLite volume **не поддерживаются этим профилем**.

## Что резервировать

Весь `/var/lib/drasl`: `drasl.db`, возможные `drasl.db-wal`/`drasl.db-shm`,
`key.pkcs8`, `skin/`, `cape/` и остальное состояние. Потеря ключа подписи — это
потеря прежней идентичности auth-сервиса, а не просто кеша. Пароли хешированы,
но бэкап содержит действующие секреты и закрытый ключ: только владелец, без Git,
публичных архивов и диагностических пакетов; для внешнего хранения — шифрование.

Первый проверенный способ — короткая остановка **своего** Drasl, проверка exit/OOM,
архив всего состояния, SHA-256/инвентарь файлов и `PRAGMA integrity_check`.
Не копировать отдельно живой `.db`: SQLite предупреждает о несогласованной копии
во время транзакции и необходимости сохранять WAL/journal вместе с базой.
[Документация SQLite](https://sqlite.org/howtocorrupt.html#_backup_or_restore_while_a_transaction_is_active).
Именованный volume переживает удаление контейнера, но сам по себе не является
резервной копией. [Жизненный цикл Docker volume](https://docs.docker.com/engine/storage/volumes/#a-volumes-lifecycle).

`auth_state_archive` — ограниченный offline helper стенда: до 128 MiB/10000 файлов,
потоковое копирование, `.partial`, проверка хеша и всех TAR-путей до записи,
отказ от ссылок/дубликатов/перезаписи непустого назначения. Он не определяет
производственное расписание и retention. Для VPS объём/ротация/свободный резерв
рассчитываются совместно с игровыми мирами и журналами (#38).

## Восстановление без возвращения отозванного доступа

Старый снимок может вернуть старые пароли, приглашения, браузерные/API/игровые
токены и состояние до бана. Поэтому проверенный аварийный сценарий консервативен:

1. Исходный том сохранить; снимок распаковать в **новый пустой** том. Проверить
   хеш, инвентарь и SQLite. Повреждённая копия не допускается к запуску для игроков.
2. Запустить копию без опубликованных портов. Игровые серверы при реальном
   восстановлении тоже закрыты: уже подключённого игрока auth reset не отключает.
3. В приватном staging сменить пароль/API/Minecraft credential владельца.
   Остальные аккаунты закрыть и сменить их секреты; все старые приглашения отозвать.
   Передать секреты через stdin, не argv/env/логи. Если credential владельца из
   снимка недоступен — остановиться для отдельного восстановления, не публиковать копию.
4. Остановить staging, обнулить браузерные токены offline адаптером для проверенной
   схемы Drasl 4.0. Сбой любого этапа оставляет копию изолированной.
5. Проверить прежние API/game/refresh/join/password/invite, сохранить UUID/скины/ключ
   подписи, затем открыть сервис. Обновить приватный credential оператора.
   Игрокам выдавать доступ заново через проверенную owner recovery после разбора
   актуальных банов/жалоб. Других администраторов восстанавливать отдельно вручную.

Это именно аварийный restore, а не обычное обновление/перезапуск. При штатном
перезапуске пользователю повторный вход не нужен. Полностью восстановить историю
банов, появившуюся **после** последней копии, сама старая БД не может; автоматическое
открытие всех восстановленных аккаунтов намеренно не делаем. При будущей привязке
OIDC/почты процедуру отзыва нужно расширить и снова принять.

## Повторить локальную проверку

```powershell
docker compose -f deploy/auth-lab/compose.yaml build --pull
docker pull python:3.14.2-slim@sha256:1a3c6dbfd2173971abba880c3cc2ec4643690901f6ad6742d0827bae6cefc925
uv run omk lab auth-storage
```

Только свежие ресурсы с уникальными именами и меткой владения; чужие volume не
принимаются. Используется **deployment entrypoint**, переопределяются только
изолированный том/конфиг/loopback-порт/имя проекта. Проверяются чистое пересоздание,
инъекция SIGKILL без OOM, UUID/пароль/скин/подпись/игровая сессия, offline snapshot,
новый том, карантин без host ports и повторный доступ после owner reset. Все свои
контейнеры останавливаются, свои тома удаляются; приватный backup/report остаются в
`.local/auth-storage-<run>/` (в lab — одна ограниченная копия на прогон).
Это проверка auth по настоящему HTTP, не графического Minecraft. Отдельный
`dj2-account-recovery --operator-workflow` проверяет подключения Forge.

Этот сценарий включён в Linux CI, а локально выполняется на Docker Desktop.
Существующие игровые миры и рабочие аккаунты в нём не используются.
