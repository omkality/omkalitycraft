# Восстановление аккаунта: проверка Drasl и игрового подключения

Задача #35. Ниже сохранена исходная лабораторная проверка Drasl; новая утилита
описана в конце. Приёмка восстановления целиком ещё не завершена. Рабочие аккаунты,
миры и лаунчер не менялись; новый интерфейс игрока не добавлялся.

## Что различаем

- Одноразовое приглашение разрешает регистрацию. После потребления оно не
  управляет доступом уже созданного аккаунта и не заменяет бан.
- UUID аккаунта Drasl отличается от UUID игрового профиля. Восстанавливаем
  существующий аккаунт, сохраняя профиль, инвентарь, команду, приваты и дома.
- Игровой bearer token из переносимого лаунчера не является API token владельца.
  Для административного PATCH нужен отдельный Drasl admin credential.
- Отзыв токенов запрещает следующие проверки авторизации. Уже установленное
  игровое подключение обслуживает Minecraft; ему требуется отдельное отключение.

В закрытом тесте admin PATCH меняет пароль с `resetApiToken=true` и
`resetMinecraftToken=true`. Проверяются два прежних игровых клиента, API credential,
старый/новый пароль, отказ настоящего Forge-входа по старому токену, забывание
отозванного входа настоящим `AccountService`, блокировка/разблокировка и повторный
сброс. Игрок не получает OP. Management credentials/пароли остаются в памяти
теста; переносимые game tokens записываются только в свежие папки стенда.

## Результат 6 ноября 2026

DJ2 2.23.4 / Core 0.2.9 прошёл **44 native серверных/HTTP условия** за один старт.
Reset и lock отдельно оставили уже вошедшего игрока подключённым: он получил
контрольное сообщение после операции. Явный console kick действительно отключил
его. Старые refresh/validate/join отвергнуты; после unlock прежние токены не ожили.
Вход с новым паролем прошёл настоящий Forge handshake, сохранил UUID и рабочий
home. Повторный сброс отверг предыдущий пароль и снова сохранил инвентарь/уровни.

**8 независимых проверок** остановленного архива подтвердили SHA, те же UUID,
семь изумрудов, 12 уровней, владельца команды, единственный исходный claim и home.
Файлы reader не менял. Server stop чистый, fatal=false / OOM=false; собственные
volume/auth удалены после экспорта. Среда: закреплённый Linux Java 8u504, 4 CPU /
6 ГиБ container / 4 ГиБ heap. Графическая игра/полный restart здесь не проверялись.

Три ранние попытки не приняты: ожидание FTB UI-notification как chat (6 условий),
ошибочное имя поля результата probe (22), неверный NBT-тип Count (24). Во всех
случаях Minecraft остановлен чисто, без fatal/OOM. В последнем случае reader
подтвердил сохранность вещей: в этой сборке Count — int, Slot — byte. Исправлены
проверки, игровые данные не правились. Принят полный свежий повтор на финальном коде.

Focused unit/lifecycle: Windows и Linux Docker по 76 passed. Полный Windows unit
suite до последнего исправления NBT-fixture: 715 passed / 6 skips; на финальном
коде повторён focused набор. Это mocked lifecycle, не дополнительные game tests.
[Обезличенное доказательство с точными commit/hash](validation/dj2-account-recovery-2026-11-06.json).

## Повторение стенда

```powershell
uv run omk lab dj2-account-recovery --server-source PATH_TO_APPROVED_SERVER --agent PATH_TO_AUTHLIB_INJECTOR --core PATH_TO_PRIVATE_CORE --mods-json PATH_TO_EXPLICIT_LAB_MOD_LIST
```

Нужны заранее проверенные DJ2/Forge/Core JAR, Docker и свободные loopback-порты
25576/25586, общие с остальными игровыми стендами. Команда создаёт случайные
собственные Compose project/volume и новые временные Drasl аккаунты. Она не
выбирает работающий сервер и не принимает UUID реального игрока. После игры
требуются чистый stop, отсутствие fatal/OOM, проверенный export и auth cleanup.
Неудавшийся сценарий не становится успешным из-за чистого завершения процесса.

Локальные материалы: `.local/account-recovery-<id>/report.json`, `status.json`,
`server-output.log`, `export/world-after.tar`. Там есть приватные игровые данные;
не публиковать каталоги целиком. В stdout/report нет токенов, паролей и HTTP bodies.
Unit-тесты моделируют ошибки lifecycle/сети; настоящий Forge/Drasl проверяется
отдельным запуском этой команды. Графический клиент здесь не запускается.

## Порядок будущей административной операции

1. По доверенной переписке установить владельца. Получить существующий account
   UUID и все связанные игровые UUID; сформировать проверяемый план всех серверов.
2. Заблокировать аккаунт и подтвердить состояние: это закрывает гонку нового входа
   во время восстановления. При неизвестном результате запроса не объявлять успех.
3. Сгенерировать новый пароль, изменить его и отозвать API/Minecraft credentials.
   Не пересоздавать профиль и не менять UUID. Секрет не попадает в аргументы,
   конфигурацию лаунчера, журналы или обычный JSON-отчёт.
4. Через проверенный серверный адаптер отключить все подключения связанных UUID
   на всех серверах проекта и подтвердить результат. Одного Drasl PATCH мало.
5. Разблокировать только после успешной сверки. При недоступном сервере или
   неоднозначном результате оставить операцию незавершённой и аккаунт закрытым.
   Новый пароль передаётся владельцу приватно; повтор после сбоя требует явного
   восстановления операции, а не бесконтрольной генерации новых паролей.

Этот исходный порядок реализуется следующей утилитой; её отдельная проверка
не подменяется историческим console kick. Почта/Telegram-авторизация не добавляются.

## Утилита владельца

`recover-account plan --username НИК` находит ровно один существующий аккаунт,
показывает account UUID, все игровые UUID и серверы. Аккаунт не меняется. План
привязан к origin Drasl и полной текущей конфигурации серверов; изменения требуют
разбора, а не тихого применения к другому профилю. Восстановление admin-аккаунтов
этой командой запрещено. Уже заблокированного игрока новый план не разблокирует:
не смешиваем восстановление с баном.

```powershell
uv run omk admin --config .omk-admin/operator.toml recover-account plan --username PlayerName
uv run omk admin --config .omk-admin/operator.toml recover-account run --account ACCOUNT_UUID
uv run omk admin --config .omk-admin/operator.toml recover-account status --account ACCOUNT_UUID
# Только после проверки незавершённой операции:
uv run omk admin --config .omk-admin/operator.toml recover-account resume --account ACCOUNT_UUID
```

UUID берётся из плана; это UUID аккаунта Drasl, который может отличаться от игрового.
`run` сначала проверяет доступность всех серверных консолей, затем блокирует аккаунт,
меняет пароль и отзывает API/Minecraft tokens. После отключения игровых UUID и
повторной сверки аккаунта/всех консолей отправляет unlock. Новый случайный пароль
показывает **один раз в stderr приватного интерактивного терминала**, отдельно от
обычного JSON результата. Перенаправленный терминал отвергается до изменений.
Пароля нет в журнале, аргументах процесса или настройках лаунчера. Терминал/SSH
может записываться самим владельцем: это не защита от его записи экрана.

Журнал `.omk-admin/recovery/ACCOUNT_UUID.json` ограничен 64 КиБ и перезаписывается
по этапам атомарно; на POSIX после замены синхронизируется каталог. Один файл на
аккаунт, максимум 1000 файлов перед отказом создания нового. Общий audit.jsonl
использует существующую ротацию. Пароли не сохраняются. Файловая блокировка
`.omk-admin/recovery.lock` запрещает одновременные операции этой утилиты и
освобождается ОС при закрытии процесса; удалять lock-файл вручную не требуется.

При обычной ошибке после начала изменений утилита пытается снова закрыть аккаунт
и записывает, удалось ли подтвердить lock. **Потерянный ответ не доказывает lock
или unlock.** Сначала `status` и проверка сервиса; повторный `run` не заменяет
`resume`. Явный `resume` создаёт новый пароль и заново отзывает секреты: ранее
показанный/потерянный пароль не восстанавливается. Успешную операцию нельзя
повторить через resume; для нового случая нужен новый plan.

### Настройка серверных консолей

В приватном operator.toml каждому реально развёрнутому серверу из `[servers]`
нужен `[servers.ID.recovery]` из [шаблона](../deploy/operator.example.toml).
Инвентарь владельца обязан включать **все серверы проекта**; утилита не может
обнаружить сервер, которого в конфигурации нет. Отсутствующий/недоступный адаптер
останавливает операцию. Не включать ещё не развёрнутый GTNH как готовый сервер.

Текущий адаптер `omk-core112-rcon-v1` требует серверный OmkalityCore 0.2.10 с
подтверждённой возможностью обработки незавершённых подключений. Старый сервер
отвергается до блокировки/смены пароля. `list uuids` — вспомогательный контроль;
одного списка игроков недостаточно. Авторитетная сверка читает сами сетевые
подключения, включая уже авторизованные, но не закончившие Forge handshake.
Закрытие и проверка выполняются узким серверным адаптером в серверном потоке.
Цель — UUID; ещё не идентифицированные входы закрываются по подтверждённому имени
этого профиля. Идентифицированный другой UUID по совпадению имени не закрывается.
Интерфейс доступен только RCON, не игроку. Неизвестный формат или ошибка не
считаются пустым онлайном. Произвольные команды/селекторы/`stop` из этой утилиты
не отправляются. Это не замена системы игровых прав и не приёмка GTNH 1.7.10.

RCON включается только при развёртывании выбранного сервера: `enable-rcon=true`,
сильный уникальный `rcon.password`, отдельный `rcon.port`. Docker публикует его
**только на 127.0.0.1**; порт нельзя открывать в интернет. RCON не шифрует данные.
Утилита запускается на том же хосте/через SSH; для удалённого SSH-туннеля оператор
явно задаёт его loopback-порт. Не подключать недоверенные контейнеры к игровой сети.
Пароль конcоли хранится в отдельном JSON `{"password":"СЕКРЕТ"}` внутри
`.omk-admin`, mode 600 на Linux/macOS. Ни в аргументах, ни в обычном env-дистрибутиве
лаунчера его нет. Эти изменения не применяются автоматически к рабочим серверам.

### Принятая локальная проверка и её границы

На 0.2.9 сценарий с задержанным Forge handshake подтвердил вход после сброса;
операция, смотрящая только `list uuids`/`kick`, не принята. На 0.2.10 тот же сценарий
закрыл соединение с явной причиной восстановления, после чего новый пароль
прошёл полный Forge-вход. Финальная приёмка — **73 native условия и 8 независимых
проверок** вещей/уровней/home/claim. Даже временно выданная тестовому игроку OP
не дала вызвать служебный интерфейс; OP снята до восстановления. При os._exit(73)
до выдачи пароля journal остался на незавершённом этапе; повтор без resume
отклонён. Resume создал новый секрет и позволил настоящий Forge-вход с тем же UUID.
Все свои серверные/auth scopes остановлены/очищены, fatal/OOM=false.
[Хеши, условия, ранние непринятые попытки](validation/dj2-owner-recovery-2026-11-06.json).

Windows unit: 829 passed / 6 skipped; Linux Docker: 119 passed. Однократная выдача
пароля отдельно от JSON/audit проверена CLI unit-тестом с изолированными данными;
в настоящем сервисном тесте секрет принимает только callback в памяти.
LabPlayer не отрисовывает игру и не доказывает клиентскую совместимость. Эта
проверка относится к DJ2 1.12.2; GTNH 1.7.10 требует собственного адаптера/приёмки.

Журнал и Drasl не образуют общую транзакцию. После смерти процесса около unlock
нельзя обещать, что аккаунт точно остался закрытым: проверяем этап, не объявляем
операцию успешной и явно продолжаем её с новой сменой секрета/отзывом токенов.
