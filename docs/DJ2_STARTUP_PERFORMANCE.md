# DJ2: время запуска клиента — 9 ноября 2026

**Решение владельца после сравнения:** выигрыш недостаточен для дополнительного
риска. Дополнительный transformer cache не внедряем; дальнейшее ускорение
загрузчика сейчас не планируем. #89 закрыта как `not planned`. Измерения ниже
сохраняются как история исследования, а не как очередь на внедрение.

Задача [#89](https://github.com/omkality/omkalitycraft/issues/89). Это исследование
старта Java → главное меню, не изменение рабочего профиля и не приёмка игры в мире.
Переписывание Python-лаунчера на Rust не устраняет обнаруженную работу внутри JVM.

## Условия и точка измерения

- Windows, i7-14700KF, 64 ГБ RAM, локальный SSD; одна копия Minecraft одновременно.
  Остальные программы/контейнеры владельца сохранены. Это замеры одного ПК,
  без перезагрузки и очистки файлового кеша Windows, не оценка всех компьютеров.
- DJ2 2.23.4 с существующим русским/визуальным overlay, Forge 14.23.5.2860,
  Temurin 8u472-b08, heap 6 ГБ, начальный heap 512 МБ, G1GC.
  VintageFix 0.7.0 / FermiumASM 5.31; авторские скрипты и ресурсы сохранены.
- Отдельный portable root без аккаунтов и миров игрока; MCP-мод исключён.
  Использованы `GameRunner.command`, фиктивная локальная сессия и отдельные логи.
  Проверки/скачивание файлов до создания JVM и авторизация на сервере не измеряются.
- Основная точка — штатная запись VintageFix `Game launch took`, сопоставленная
  со временем создания Java-процесса. Universal Tweaks завершает свой таймер раньше:
  его запись не выдаётся за достижение главного меню.
- Только в отдельном профилировочном запуске — read-only Java sampler, интервал
  200 мс, стек главного потока и heap. Проверка `currentScreen` включалась уже
  после штатной отметки, не инициировала классы Minecraft во время загрузки.
  Получен `lumien.custommainmenu.gui.GuiCustom`; точность сравнения — секунды.
  Профилировочный прогон исключён из сравнения обычных запусков.
- Захват окна Computer Use давал таймаут. Окончание загрузки подтверждено
  игровым состоянием/штатным событием, не визуальной проверкой каждого кадра.
  Штатный выход выполнялся через закрытие окна, проверялись лог остановки и exit 0.

Исходные хеши, отдельные результаты, ограничения и проверки:
[машинный протокол](validation/dj2-startup-performance-2026-11-09.json).
Сырые логи/стековые выборки и runtime остаются в игнорируемой `.local`, не в Git.

Первый запуск отличается сразу несколькими локальными кешами и состоянием ОС;
разницу с повторным нельзя целиком приписывать одному файлу VintageFix.
Два запуска кандидата и обратные контроли показывают выигрыш порядка 15–21 с
на этом ПК. Малое число повторов и внешние сетевые запросы ограничивают вывод;
это не обещание такого же процента каждому игроку.
Медиана трёх обычных повторов — 147.924 с, двух запусков кандидата — 129.769 с:
разница 18.155 с / 12.27%. Сборщик `collect_output`/`BoundedLog` отдельно проверен
через настоящий pipe: существенного замедления в этом опыте не обнаружено.

## Где проходит время

В 380 из 746 выборок до конца загрузки стек содержал загрузку/преобразование
классов (LaunchClassLoader/ASM/Mixin). Это пересекающиеся стеки, не независимые
проценты CPU отдельных модов. JEI занимал около 16 с по собственному таймеру;
Groovy-скрипты не оказались главным длительным этапом.

В 31 выборке главный поток ждал сеть: 23 из них — список плащей Galacticraft,
остальные — SerializationIsBad, HammerCore и Industrial Foregoing. Проверка
закреплённого Galacticraft 4.0.7 показала синхронный запрос с connect/read timeout
по 10 с. `Override Capes=false` не устраняет безусловный вызов загрузчика списка.
Защитный мод SerializationIsBad ради скорости не отключался.

Суммарные stop-the-world паузы G1 — около четырёх секунд, полного GC не было.
Это не весь расход времени GC и не доказательство бесполезности любых JVM-настроек.
Но оснований вслепую увеличивать RAM/начальный heap или менять Java не найдено.

## Кеши и обновления

Штатные `jar_discoverer_cache`, dynamic resources/background item bake,
resourcepacks и textures уже включены в VintageFix. В текущем подписанном
контенте нет чужого `jarDiscoverer.cache`; первый клиент создаёт собственный.
[Назначение этих опций у автора VintageFix](https://github.com/embeddedt/VintageFix/wiki/Config-options).

У закреплённого VintageFix 0.7.0 ключ discovery-кеша — путь JAR + `lastModified`,
не SHA256. Сам лаунчер независимо проверяет SHA256 модов. Его обычная проверка
и repair не должны постоянно стирать локальный discovery-кеш. Обновление файла
тем же именем через downloader даёт новую дату; смена пути также меняет ключ.

Unit/integration тест с временным HTTP CDN проверяет обычную установку, repair
удалённого мода и обновление как с тем же, так и с новым именем JAR. Локальный
cache sentinel сохраняется, управляемые моды заменяются. Это проверка владения
файлами и timestamp, не парсера бинарного кеша VintageFix.

Нативный fault-test: после штатной остановки сохранена исходная копия кеша,
в тестовой папке вместо неё записан обрезанный двухбайтовый файл. VintageFix
обнаружил ошибку, сохранил ровно эти байты как `.errored`, создал новый кеш
больше 20 МБ и достиг меню; следующая загрузка прочла новый файл без этой ошибки.
Оба клиента закрылись с exit 0. Fault-прогон занял 147.661 с: пересоздание не
объясняет всю разницу первого запуска. Интервал от загрузки discovery-кеша до
обнаружения модов — примерно 13.1 с при fault и 10.3 с в одном обычном контроле;
это небольшой одиночный контроль, не устойчивый процент ускорения.

## Решение по кандидату

Проверялся только встроенный opt-in `vintagefix.transformerCache` в уже имеющемся
VintageFix 0.7.0, без нового загрузчика, нового мода или изменения рецептов.
Кеш добавляет примерно 142 МБ на диске и использует память; это другой механизм,
чем штатный discovery-кеш. Счётчики подтвердили повторное использование результатов
преобразования классов. Выключение флага возвращает обычный режим.

**В рабочем профиле флаг не включён.** Перед внедрением нужны собственная
инвалидация по runtime/mod/config identity, тесты обновления/отката, входа/выхода,
рецептов/JEI, моделей и всех важных миров. Кеширование преобразований нельзя
признать совместимым со всей сборкой по одному достижению меню.

Измеримая разница есть; по решению владельца сохраняем проверенный режим
и возвращаемся к обязательным задачам. Реализация кандидата не планируется.
Перенос на Rust, смена Java/Forge, снятие защит и удаление квестовых модов не нужны.
Новые версии оптимизаторов в этом сравнении не устанавливались.

## Исключённые попытки и оставшаяся работа

Первая тестовая копия ошибочно не содержала авторскую папку `groovy` и открыла
предупреждение InWorldCrafting. Авторский `disablepopup.groovy` намеренно убирает
его; рецепты используют InWorldCrafting. Два запуска неполной копии исключены,
мод не удалялся. Новый input preflight проверил наличие всего подписанного payload
с двумя известными различиями visual-кандидата (удалённый oauth и Client 0.1.1).
43 файла папки `groovy`, 130 файлов `scripts` и ресурсы сверены с источником.

Одна подготовка cache fault отказала до записи: оставшийся процесс Crash Assistant
был ошибочно принят за игру. Следующий запуск использовал целый кеш и учтён как
дополнительный обычный контроль. Фоновые процессы не дают оснований считать fault
выполненным. Отказ переименования открытой папки логов также не обходился.

Загрузка мира, полная игровая регрессия кандидата, Linux/macOS и слабые ПК
не проверялись. #89 закрыта без внедрения; server Core/DJ2Fix, рабочие миры, manifest,
публичные player releases и серверные Docker-службы не изменялись.
Все десять принятых клиентов завершены; в полной копии нет crash-report или
`hs_err`, исходные config/mods и тестовый набор модов повторно сверены по SHA256.
Оставшийся Crash Assistant неполной исключённой копии закрыт; файлы опыта сохранены.

Проверки изменения репозитория: focused install/game/mod policy — 44 passed /
2 skipped; Ruff и Black по всему публичному Python-коду, `git diff --check`.
