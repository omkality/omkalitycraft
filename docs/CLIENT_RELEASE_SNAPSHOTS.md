# Сохранение файлов клиентских релизов

Это необязательный этап локальной подготовки через существующую команду
`omk release pack`. Он сохраняет подписанный манифест **и проверенные байты**
клиентских файлов. Одного старого манифеста недостаточно для восстановления,
если исходную папку уже перезаписали новой сборкой.

Хранилище не переключает CDN, лаунчер или игровой сервер. Оно не является
резервной копией миров, Drasl, инвентарей, серверных конфигов или баз данных.
Автоматическая публикация и согласованный откат всего сервера остаются в #171.

## Включение

Добавьте `--snapshot-root <отдельная-папка>` к обычной команде подготовки:

```text
uv run omk release pack --files <подготовленные-client-files> --launch-profile <launch.json> --private-key <offline.pem> --public-keys <public.json> --output <manifest.json> --pack-id dj2 --version <новая-версия> --minecraft 1.12.2 --platform windows-x64 --snapshot-root <private-client-releases>
```

Путь можно передать переменной **окружения процесса** `OMK_RELEASE_SNAPSHOT_ROOT`.
Явный аргумент имеет приоритет. Без аргумента и переменной сохранение выключено.
Команда не загружает `.env` автоматически; для отдельного файла конфигурации
используйте `uv run --env-file <файл-владельца> omk release pack ...`.

| Переменная | По умолчанию | Ограничение |
| --- | --- | --- |
| `OMK_RELEASE_SNAPSHOT_MAX_BYTES` | 34359738368 (32 ГиБ) | 1…1099511627776 байт |
| `OMK_RELEASE_SNAPSHOT_RESERVE_BYTES` | 1073741824 (1 ГиБ) | 1…1099511627776 байт |
| `OMK_RELEASE_SNAPSHOT_MAX_COUNT` | 64 | 2…1024 комплектов |

Для разных ОС хранятся отдельные полные комплекты. Это дополнительные файлы,
не дедупликация: учитывайте их вместе с мирами, логами, бэкапами и CDN. Значение
32 ГиБ — ограничитель по умолчанию, не рекомендация резервировать столько на VPS.
Нужный бюджет зависит от измеренного размера подготовленных клиентов.

## Порядок сохранения

1. Проверяются подпись, пути, принадлежность хранилища и файловая блокировка.
2. Проверяются сохранённые комплекты, общий бюджет и свободный резерв диска.
3. Только перечисленные в манифесте файлы копируются в новый `pending-<uuid>`.
   Источник не изменяется; жёсткие ссылки не используются. Каждый файл сверяется
   по размеру и SHA256 после копирования. На POSIX права исполняемых файлов
   выставляются по подписанному описанию перед `fsync`; права владельца исходной
   машины и специальные биты не копируются.
4. Подписанный манифест записывается и комплект независимо проверяется ещё раз.
   Готовая папка получает имя SHA256 содержимого манифеста.
5. Только затем выходной манифест заменяется через временный файл в той же папке.

Пример структуры:

```text
private-client-releases/
  owner.json
  lock
  <64-символьный-digest>/
    manifest.json
    files/...
```

Повторное сохранение того же содержимого возвращает уже проверенный комплект.
Другие байты под теми же `pack_id`, платформой и версией не принимаются: нужен
новый номер версии. Старые комплекты не перезаписываются и не удаляются при
переполнении бюджета. Хранилище создаётся только в новой папке; существующая
произвольная папка автоматически не принимается под управление.

Хранилище, исходник, выходной манифест и ключи должны иметь раздельные пути.
Символические ссылки и junction внутри управляемых файлов отвергаются.
Подготовленная клиентская папка заранее очищается от секретов и личных данных:
подписант отвечает за состав манифеста, автоматического распознавания секретов нет.
В публичный Git эти комплекты и ключи не добавляются.

## Ошибка, прерывание и возврат

Ошибка копирования удаляет только временный каталог текущей попытки. Ранее
сохранённые комплекты и прежний выходной манифест остаются. Если файл манифеста
не удалось заменить после сохранения, готовый комплект остаётся; повторная
команда может использовать его без повторного копирования.

После принудительного завершения процесса может остаться `pending-<uuid>`.
Новая запись остановится до ручного разбора; автоматической очистки чужого или
незавершённого каталога нет. Проверка конкретного старого комплекта продолжает
работать. Для внутренней проверки есть `ReleaseStore.verify(digest)`; отдельная
админская команда не добавлялась. Доверенные публичные ключи старых поколений
нужно сохранять, иначе их подписи нельзя будет проверить.

При возврате исправления скопируйте сохранённые байты в отдельную папку подготовки
и используйте её как вход для **нового** подписанного релиза. Нельзя указывать
внутреннюю папку хранилища одновременно как источник новой записи.
Не понижайте минимальную безопасную версию лаунчера ради
отката. Текущий API всё ещё раздаёт `releases/<pack>/<platform>/files`: это
хранилище само по себе не делает опубликованный URL неизменяемым и не устраняет
гонки переключения CDN. До автоматизации нужны согласованные клиент/сервер,
проверенная совместимость сохранений и отдельная репетиция восстановления.

Проверки используют искусственные подписанные файлы, файловые ошибки, блокировку,
лимиты, повреждение и реальное завершение процесса копирования. Linux Docker
также проверяет чтение сохранённого комплекта с readonly-тома. Повторная подпись
старого содержимого под новой версией проверена с сохранением executable-флагов
и минимума лаунчера, в том числе при подготовке на Linux-томе `noexec`.
Сборщик читает биты прав файла, а не доступность его запуска на машине подготовки.
Это не тест
Minecraft, отказа питания или восстановления рабочего VPS. Файлы синхронизируются
через `fsync`; каталоги — на POSIX. Полная устойчивость NTFS к потере питания
этим опытом не подтверждена. Хранилище рассчитано на локальный управляемый диск,
не на враждебный процесс с теми же правами или непроверенный сетевой filesystem.
