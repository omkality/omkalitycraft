# Модовые привязки и безопасная точка ресурсного сброса

Для остановленного Docker source доступна дополнительная **read-only** проверка:

```console
uv run omk admin --config .omk-admin/operator.toml resource-resets inspect --server dj2 --dimension -18000 --preflight
```

Предварительно нужна [настройка owner inspection](RESOURCE_RESET_INSPECTION.md).
Общие owner lock, runtime/ownership checks и checkpoint до/после сохраняются.
Worker не имеет сети, Docker socket и записи в source. Команда ничего не вайпает,
не отвязывает предметы и не запускает сервер. Подробный JSON предназначен только
владельцу: примеры содержат пути playerdata и NBT, не публиковать его игрокам.

## Выбор точки

Используется сохранённый спавн **основного мира**, затем соседние точки в пределах
заданного поиска. Постоянных координат вроде `8 241 8` в алгоритме нет.
Нужны уже сохранённые TerrainPopulated/LightPopulated чанки, штатный серверный
приват `omk_spawn`, неподвижная сохранённая граница мира и читаемый FML registry.
Числовые block ID берутся из конкретного save; поддержаны массивы NEID Add/Add2.

Площадка 3×3 должна иметь пол из небольшого списка обычных полных vanilla-блоков,
три свободных уровня воздуха и отступ от границы. Песок, гравий, магма, жидкости,
полублоки и неизвестные модовые блоки не принимаются. Рядом не должно быть
сохранённых entities/tile entities. Отсутствующий чанк не генерируется, блоки не
ставятся, постройки не удаляются. При отсутствии точки возвращается `found=false`;
повреждённый/неподдерживаемый формат приводит к отказу проверки.

Это консервативная **offline-геометрия**. Она не моделирует последующее движение
мобов, взрывы, mod events и все варианты collision boxes. Перед настоящей
эвакуацией всё ещё нужна повторная нативная проверка в Forge под maintenance.
Чтение server claims вместе с authority inspection не заменяет проверку защиты
в работающей игре.

## Почему удаления папки мира недостаточно

| Механизм установленной DJ2 2.23.4 | Что установлено / что проверяет этот этап |
|---|---|
| RFTools 7.73 + McJtyLib 3.5.4 | `data/TPDestinations.dat` хранит dimension → приёмник, а Charged Porter — только **числовой ID** приёмника. Проверяются registry, основной `target`, `target0…7` Advanced Porter и `destId` передатчиков в сохранённых записях. Неизвестный ID тоже блокирует подготовку: удаление registry не должно скрывать оставшийся предмет. |
| Ender Utilities 0.7.15 | `tag.Target.Dim` и вложенные сохранённые NBT-ссылки, в том числе предметы в контейнерах. Штатный API умеет удалить Target, сохранив предмет и остальные теги. |
| Mekanism 9.8.3.390 | Нативная сериализация Frequency сохраняет имя/владельца/public, **не activeCoords**. Частоту команды удалять не требуется. Полный тест реальных рамок/перехода после восстановления сети ещё нужен. |
| WR-CBE 2.3.2.33 | `RedstoneEther/fmap.dat`, `node1.dat`, `node2.dat`, глобальные `dimMap.dat`, `fprop.dat`, `gprop.dat` — redstone-хранилища, не привязки игрока к порталу. Считаются отдельно после проверки SHA мода; байты сохраняются. Это не новая миграция WRCBE shared state. |
| Остальные механизмы | Общий проход ищет dim/dimension-поля и известные 4-компонентные координаты в сохранённых NBT, inventories, TileEntities и Entities всех **сохраняемых** миров. Это эвристическая диагностика, а не доказательство полного покрытия. |

Приёмник RFTools нельзя удалять отдельно от привязанных предметов: штатный
Charged Porter при исчезнувшей цели может применить отрицательный эффект.
Убирать нужно только привязку к сброшенному миру, сохранять заряд/остальные
ссылки и **монотонный lastId**, чтобы старый ID не достался новому приёмнику.
Живой receiver может зарегистрироваться повторно; окончательная процедура
должна работать с остановленной копией и барьером запуска.

В установленном pack есть и другие кандидаты для нативных тестов: Ender IO
Travel Anchors/Staff of Travelling, Draconic Evolution Dislocator, Blood Magic,
Botania, Extra Utilities 2, Actually Additions, AE2, Thaumic Augmentation,
RFTools Dimensions, обычные и сюжетные порталы/ракеты. Их конкретные переходы,
вложенные нестандартные сериализаторы и shared caches **этим этапом не приняты**.
Отдельные `.astral` и другие неизвестные форматы также не становятся проверенными
из-за отсутствия находок. Ограничения квестовых предметов не добавлялись.

Версии/SHA модов и происхождение закреплены в
[`reset-preflight.json`](../profiles/server-defaults/dj2/reset-preflight.json),
первичный полный inventory — в
[`dj2-2.23.4-client.json`](../profiles/upgrade-inputs/dj2-2.23.4-client.json).
После смены артефакта проверка откажет до пересмотра адаптера.

## Настройка без коммитов

| Переменная окружения owner-процесса | По умолчанию | Допустимо |
|---|---:|---:|
| `OMK_RESET_LANDING_RADIUS` | 16 блоков | 0–32 |
| `OMK_RESET_LANDING_VERTICAL` | 8 блоков | 0–32 |
| `OMK_RESET_LANDING_CHUNK_BUDGET` | 32 | 1–256 |
| `OMK_RESET_REFERENCE_CHUNK_BUDGET` | 100000 | 1–1000000 |

Также действуют [существующие лимиты helper/мира/таймаута](COLD_BACKUPS.md).
Поиск ограничен по размеру Anvil/NBT, числу чанков/узлов/находок. Политика, SHA
профиля/артефактов и полного world inventory включены в результат. Повторное
чтение обнаруживает изменение источника. Для большого предгенерированного мира
лимит прохода нужно выбрать по фактическому количеству сохранённых чанков;
превышение даёт отказ, а не неполный «успех».

Внутренний [data staging](RESOURCE_RESET_STAGING.md) принимает `position:"auto"`:
использует эту точку и требует отсутствия **известных** ссылок/opaque records.
Доказательство включается в замороженный план; его изменение запрещает stage.
Ручная позиция остаётся прежним внутренним data-only режимом для лабораторий.
Даже чистый preflight оставляет `coverage_complete=false`,
`portal_adapters_reviewed=false`, `landing_verified=false`, `ready_for_start=false`.
`can_stage_data` разрешает только подготовку изолированной копии, не owner wipe.

## Проверка в Linux Docker

Нативная лаборатория использует полную DJ2 2.23.4, прежние Core 0.3.5 / DJ2Fix
0.1.3 и отдельный gated test-only observer. Игрок авторизуется через отдельный
Drasl и Forge-протокол; графического клиента в этом опыте нет.

Блокируется сохранённый спавн, создаются настоящими сериализаторами resource/main
link crystals, charged porters и RFTools destinations. Проверяются обнаружение
ссылок и соседняя площадка, выборочная нативная отвязка с сохранением энергии и
ID, data stage со свежим backup, затем вход offline-игрока в новую копию.
Независимый аудит stopped TAR сравнивает NBT предметов, обе группы привязок,
монотонность ID и все остальные сохранённые байты на этапе stage.

Реальные работающие receiver/transmitter-блоки в этом опыте не строятся,
фактическое использование всех телепортеров не заявляется. Ошибки ранних
тестовых фикстур не считаются крашами сборки. Итоговые факты и хэши — в
[обезличенном протоколе](validation/dj2-resource-preflight-2026-11-09.json).

maintenance/start barriers, прерывание/recovery и owner lifecycle. Только после
их приёмки можно открывать команду рабочего сброса. VPS пока не требуется.
