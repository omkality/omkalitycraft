# Эндер-сундук и привязки Ender Utilities при сбросе мира

Принят отдельный серверный сценарий полной DJ2 2.23.4 в Linux Docker,
11 ноября 2026. Графическая проверка клиента этим сценарием не заменяется.

При сбросе ресурсного мира недостаточно обработать предметы, которые игрок
держит при себе: они могут лежать в его эндер-сундуке. Адаптер остановленной
копии теперь учитывает стандартное поле `EnderItems` в сохранении игрока.
Это дополнение к [этапу обычного Inventory](RESOURCE_RESET_ENDERUTILITIES.md).

## Граница формата

`enderutilities-0.7.15-player-location-target-v2` обрабатывает `Inventory` и
стандартные **27 слотов EnderItems (0–26)** в канонических player `.dat` и `.dat_old`.
В обоих хранилищах допущены только location crystals tier 0 и их модули в
Ender Porter. Выбранный и невыбранный модули проверяются одинаково.

Удаляется только `Target` нужного измерения. Предмет, заряд, выбранный модуль,
цели других миров и остальные поля сохраняются. Пустое или отсутствующее
EnderItems не создаётся заново; наличие Inventory для обработки EnderItems
не обязательно. Неизвестная схема списка, повтор слота или слот вне 0–26
приводят к отказу до записи. Обычные слоты брони/offhand не разрешаются
в эндер-сундуке.

Артефакт остаётся Ender Utilities 0.7.15 из официального server pack DJ2 2.23.4:
`enderutilities-1.12.2-0.7.15.jar`, SHA256
`c0a604aac57853f76f16e21958b02f4d6adbc543c20dda67eb1088ca91ba618c`.
Источник и остальные pins — в
[`reset-preflight.json`](../profiles/server-defaults/dj2/reset-preflight.json).
Изменение JAR запрещает допуск без пересмотра адаптера.

## План и ограничения

Preflight теперь `dj2-2.23.4-forge112-reset-preflight-v3`. Старые планы v1/v2
нужно строить заново; stage сверяет текущий proof со всем замороженным планом
и требует свежий проверенный backup текущего остановленного мира.
Ручной data-only режим с явной позицией по-прежнему не включает отвязку.

Сумки внутри EnderItems, ForgeCaps, мировые контейнеры/entities, другие устройства
и tiers кристаллов этим этапом не допускаются. Их обнаруженные ссылки остаются
блокирующими. Пустой результат эвристического прохода не доказывает полного
покрытия всех модовых сериализаторов.

Это внутреннее приготовление **новой копии**, а не рабочий owner wipe.
`ready_for_start=false`, `portal_adapters_reviewed=false`, `ready_for_players=false`.
Allowlist вайпа не расширяется: принят ресурсный сценарий `-18000`.
Online-эвакуация, maintenance/start/cutover barrier, прерывание/recovery и
оставшиеся портальные адаптеры остаются в #32/#41.

## Проверки данных

14 новых синтетических условий дополняют прежнюю приёмку: оба края диапазона
слотов, EnderItems без Inventory, невыбранные модули/заряд/другая цель,
неподдерживаемые слоты/схемы и старый допуск v1. Проверено преобразование обеих
записей игрока, неизменность source и отказ до записи при изменении proof.
Геометрия/допуск в filesystem unit-фикстуре подменены явно; настоящий preflight
и доступ к сундуку относятся к отдельному игровому опыту.

Фокус адаптера: 61 passed; Linux Docker data/filesystem: 143 passed;
Windows unit/UI: 1385 passed / 12 skipped, Ruff/Black.
Тест EnderItems без Inventory сначала воспроизвёл отсутствие обработки, затем
прошёл после изменения. Эти числа не означают графическую игровую приёмку.

## Нативный сценарий

Использованы Core 0.3.5 / DJ2Fix 0.1.4, отдельный Drasl и два аккаунта без OP.
Игровой актор — survival; gated test-only observer создаёт контрольные предметы,
площадки и сундук, читает состояние, но не выполняет переходы вместо Porter.
Открытие сундука, переносы и использование предметов выполняются игровыми пакетами.

1. В стандартном эндер-сундуке первого аккаунта находятся два Porter,
   два кристалла и контрольные предметы; второй аккаунт у того же блока видит
   свои три алмаза. Перед reset проверена нативная отвязка в обоих хранилищах.
2. Игрок остаётся в ресурсе. После остановки fresh backup и preflight находят
   12 допустимых ссылок: по три в Inventory/EnderItems каждой записи `.dat`/`.dat_old`.
3. Auto stage эвакуирует игрока и удаляет только эти Target. Меняются обе записи
   игрока и resource spawn claims; остальные **301 retained файл побайтно прежние**,
   включая запись другого аккаунта. 19 старых ресурсных файлов исключены
   только из новой копии. Файлы: 323 → 304; после игры в новом ресурсе — 348.
4. В новой копии второй аккаунт снова видит свои алмазы. Первый получает оба
   Porter обычным переносом из сундука. У отвязанного использование не меняет
   положение/инвентари/заряд; основная цель работает со штатной стоимостью 5000.
5. Обычный `/resource` создаёт новый мир без прежней контрольной площадки.
   Очищенный модуль заново привязывается sneak + block use, переходы работают,
   затем оба Porter возвращаются в сундук.
6. После полного перезапуска сохранены выбранные модули, новые/основные цели
   и заряд. Предметы снова получены из сундука, использованы между мирами
   и возвращены. Сохранились здоровье 20, опыт 12, оба контрольных набора
   предметов и ровно четыре Porter суммарно в двух хранилищах.

Итог: **81 native условие, 107 independent условий, восемь серверных переносов,
три чистых старта/stop**, без OOM и серверного crash-report. Независимый аудит
не импортирует production-адаптер или transformer. Свои контейнеры и game/auth
volumes всех четырёх scopes очищены после экспорта; чужие службы не менялись.

Protocol-fixture не моделирует клиентский инвентарь: transaction prediction
confirmations для переносов отрицательные. Результат каждого переноса подтверждён
серверными сохранениями до/после, полным типизированным содержимым предмета и
счётчиками. Графический GUI и корректность клиентского предсказания этим опытом
не принимаются. Состояние Hard/PvP также не проверялось.

Три ранних опыта исключены из полной приёмки. В первых двух лаборатория
взаимодействовала до завершения подтверждения/согласования движения; итоговый
observer ждёт очищенное серверное teleport-pending состояние в конце тика.
В третьем перенос состоялся, но сравнение ошибочно требовало сохранения порядка
полей compound NBT. Итоговый аудит сохраняет типы, все значения, порядок списков
и количество предметов, учитывая неопределённый порядок полей compound.
Отдельные controls обнаруживают изменение заряда и лишний предмет.
Эти отказы фикстур не являются крашами сборки.

[Обезличенный протокол](validation/dj2-enderchest-reset-2026-11-11.json).
Java-моды, рабочие миры, manifests и player releases не менялись. Владелец
по-прежнему получает только inspection, рабочий wipe не включён. VPS пока не нужен.
