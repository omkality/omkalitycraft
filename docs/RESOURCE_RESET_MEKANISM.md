# Mekanism: физические телепорты после ресурсного сброса

Продолжение [preflight](RESOURCE_RESET_PREFLIGHT.md) и
[проверки RFTools](RESOURCE_RESET_RFTOOLS.md) для #32. Проверены существующие
физические рамки и восстановление частной сети после полной остановки сервера.
Рабочая owner-команда сброса по-прежнему не включена.

## Стенд и реальные действия

Полная DJ2 2.23.4, Forge 14.23.5.2860, Mekanism 9.8.3.390, прежние Core 0.3.5 /
DJ2Fix 0.1.3. Сервер и persistent Drasl — в отдельных Linux Docker volumes;
сервер ограничен 4 vCPU / 6 ГиБ, heap 4 ГиБ. Это функциональная проверка, а не
оценка вместимости VPS. Образы, JAR и исходный server pack закреплены в
[обезличенном протоколе](validation/dj2-mekanism-reset-2026-11-09.json).

Отдельный приватный observer работает только с lab-флагом и миром `lab-world`.
Он строит обычные блоки, задаёт владельцев/частоты через native API и наблюдает
серверное состояние. Он не подменяет `onUpdate` и не выполняет переход вместо
Mekanism. Один тестовый аккаунт использует настоящий Forge/игровой протокол;
второй нужен для отдельного владельца частоты. Это не графический клиент:
клиентские моды и отрисовка этим опытом не проверяются.

Созданы четыре настоящие рамки: основная и ресурсная на одной частной частоте,
другая основная частота того же владельца и одноимённая частота другого аккаунта.
Разделение частот проверено по native владельцам и адресатам. Это не утверждение
о запрете чужому игроку физически войти в рамку: такое разрешение отдельно не
тестировалось.

Игровым аккаунтам OP не выдаётся. Закреплённый PlaneFix при старте добавляет
известного fake-оператора `[Minecraft]`; существующая строгая lab-проверка
проверяет каждую запись и удаляет только его. Неизвестная запись или человеческий
аккаунт приводят к отказу. После каждого из трёх стартов проверен пустой список.
Это подготовка лаборатории, а не новая настройка рабочего сервера.

## Что подтверждено

Первый полный проход выполнен в creative. Он подтвердил работоспособность сети,
но не считается проверкой отсутствия урона. Второй полный проход повторён в
survival: серверное состояние и сохранённый `playerGameType=0` проверены отдельно.
Для воспроизводимости на стенде отключены мобы и установлена peaceful; приёмку
рабочих Hard/PvP это не заменяет.

- Неполная рамка отказывает в переходе; восстановленная рамка без энергии также
  отказывает. При штатной максимальной энергии обычный world tick переносит
  игрока из основного мира в ресурсный. Заряд уменьшается; баланс не менялся.
- Обычный movement packet выводит игрока из рамки и возвращает в неё. После
  штатного сброса native cooldown/didTeleport игрок возвращается в основной мир.
- После полной остановки и нового старта сохранены имена и владельцы устройств.
  При загрузке исходных чанков обычные тики восстанавливают два активных адреса;
  межмировой переход снова работает. Принудительная загрузка исходного чанка —
  часть фикстуры, а не доказательство работы незагруженных адресатов.
- Игрок уходит в ресурсный мир обычной `/resource` с действующими задержками/КД,
  затем выходит. Остановленный source получает свежий проверенный backup.
  В новой копии исключается старое ресурсное измерение, а offline-игрок получает
  замороженную безопасную точку у сохранённого основного спавна.
- После старта candidate у основной рамки остаётся один активный адрес — она
  сама. Старого ресурсного адресата нет: находящийся в рамке игрок остаётся в
  основном мире, за проверенное окно заряд не расходуется.
- Другая основная рамка подключается native API к сохранившейся частной частоте.
  Обычный tick снова переносит игрока, теперь внутри основного мира. Одноимённая
  частота второго владельца остаётся отдельной. В survival на четырёх сохранённых
  контрольных точках переходов здоровье равно 20, creative выключен.

В каждом полном проходе — 52 зарегистрированные проверки, включая повторные
проверки исправности observer; это не 52 разных игровых сценария. Всего шесть
штатных стартов/остановок в двух проходах, без OOM и обнаруженного server crash.
Ранние ошибки подготовки исключены из приёмки и перечислены в протоколе.

## Что действительно хранит Mekanism

Tile NBT сохраняет частоту: имя, `ownerUUID`, `publicFreq`. Список активных
координат не сериализуется в частоту. Он восстанавливается при загрузке и тиках
физических устройств. Поэтому глобально удалять частные частоты для этого
проверенного случая не требуется: это уничтожило бы полезные основные привязки.

Есть и файлы `data/<owner>_TeleporterFrequencyHandler.dat`. После `save-all flush`
в работающем survival-сервере в двух файлах видны три ожидаемые частные частоты.
В остановленных снимках обоих проходов их `freqList` уже пуст, но владельцы и
частоты устройств сохранены; штатный restart действительно восстановил сеть.
Точный порядок native reset/save здесь полностью не трассировался. Сохранность
неиспользуемых имён частот без физических устройств этим опытом не доказана.
Утилита stage не очищает эти файлы и сохраняет их побайтно.

## Независимая проверка сохранений

Отдельный reader TAR/Anvil/NBT не использует преобразователь сброса или preflight
для подтверждения результата. Сравниваются четыре снимка: первая остановка,
остановка перед reset, новая data-копия до запуска и её итоговое сохранение.
В survival — 46 проверок, в creative-пилоте — 40.

- В каждой последовательности 325 → 348 → 329 → 346 файлов. Между source и
  staged изменены ровно два: player NBT offline-игрока и ресурсная группа в
  файле server claims спавна. Остальные 327 retained файлов побайтно совпадают;
  Исключены 18 файлов старого ресурсного измерения и его корневой generation marker.
- Инвентарь, опыт, capabilities и остальные неэвакуационные поля игрока
  совпадают. Сохранение второго аккаунта побайтно совпадает.
- Основной регион со всеми тремя рамками и оба файла частных частот побайтно
  совпадают. Native block IDs/metadata подтверждают настоящие teleporter/frame,
  а Tile NBT — точные частоты и разных владельцев.
- Из server claims удалена только группа измерения `-18000`, основные claims
  сохранены. Итоговое сохранение подтверждает новую основную точку игрока и
  отсутствие старой ресурсной рамки.

## Оставшиеся условия #32

Переносимый телепортер и его реальные пакеты, public-частоты, незагруженные
адресаты/anchor upgrades и все контейнеры/capabilities отдельно не приняты.
Ender Utilities и остальные модовые сети, production transport adapters,
online-эвакуация и повторная проверка точки под maintenance, start/cutover barrier,
прерывание/recovery остаются следующими условиями.

`portal_adapters_reviewed=false`, `ready_for_start=false`, `ready_for_players=false`.
Core/Fix и рабочие миры не менялись; нового backup writer или расписания нет.
Свои пять scopes, девять game volumes и пять auth volumes очищены после экспорта;
другие проекты и постоянный UI-preview сохранены. VPS для этого этапа не нужен.
