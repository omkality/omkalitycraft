# Входная точка для аудита первого запуска DJ2

**Закрытый VPS работает, допуск игроков в новый мир впереди.** Статус на 21 ноября
2026. Основной трекер и актуальные критерии находятся в [#41](https://github.com/omkality/omkalitycraft/issues/41).
Владелец провёл аудит перед переносом. Решения и исправления находятся в
[PR #261](https://github.com/omkality/omkalitycraft/pull/261) и последующих PR.

## Состояние первого выпуска

- Для первого выпуска выбраны Windows x64 и Linux x64. Из
  [GitHub prerelease dev18](https://github.com/omkality/omkalitycraft/releases/tag/launcher-v0.3.0.dev18)
  клиенты скачали готовую DJ2 2.23.4 с VPS по доверенному HTTPS на IPv4.
  Обычный вход и автообновление подтверждены на Windows и Ubuntu 24.04 под WSL2.
  Приёмка на физическом Linux и macOS запланирована отдельно.
- По S1 автоматическая передача отчётов о сбоях отключена в лаунчере, в том
  числе для старой очереди. Локальная диагностика сохраняется. По S2
  подписанное поколение и сохранённый минимум используются при установке,
  а сборкам dev18 задан минимальный порог поколения 4 для новой установки.
  [Логи](LOGGING.md) · [Подписанные сборки](SIGNED_PACK_INSTALL.md)
- По E1 есть закрытая приёмка dev18 с загрузкой и игровым входом на VPS.
  Запуск локальных архивов 0.3.0 и переход на них через тестовый TUF
  подтверждены. С публичной раздачи в пустые папки скачано подписанное
  поколение 4, сверены 5 968 файлов Windows и 5 935 файлов Linux.
  На обеих платформах сохранена стартовая тема Stronghold.
  Приёмка точного стабильного GitHub-комплекта и нового мира
  остаётся в [#36](https://github.com/omkality/omkalitycraft/issues/36).
- Drasl, закрытое управление через TUI/SSH и метрики уже работают на VPS.
  Одноразовая регистрация подтверждена через HTTPS. Холодный снимок с диска
  владельца проверен, Forge запустил отдельную копию из архива с тем же хешем.
  Полный эксплуатационный возврат и ротация остаются в
  [#33](https://github.com/omkality/omkalitycraft/issues/33).

Для #181 отдельно принят Linux/WSLg singleplayer-контроль моделей и рецепта 9×9:
59 ID/count/meta, 143 360 пикселей двух GUI, 142 cold-NBT условия, нативные
wrong/correct/output действия, все 226 JAR прежние, client exit0. Это не новая
приёмка Linux Drasl/multiplayer, готового portable profile или всей GUI-матрицы;
macOS и BetterQuesting progression остаются открытыми.
[Точная область и pins](DJ2_RESOURCE_MODELS.md).

Закрытый выпускной профиль использует DJ2 2.23.4, Forge 1.12.2, Core 0.3.12,
DJ2Fix 0.1.8 и Client 0.1.8. Версии исходников в
[`versions.json`](../mods/forge-1.12.2/versions.json) могут быть новее
развёрнутого комплекта.

**Область [#220](https://github.com/omkality/omkalitycraft/issues/220) принята на 0.1.8:**
19 native случаев и 379 независимых проверок, затем новый полный Windows GUI
с Linux Forge/Drasl: 93 условия, 31 состояние/30 postconditions. Обычный клиент
без MCP вошёл после чистого restart того же мира без server observer, отрисовал
HUD/инвентарь и штатно завершился. Оба client exit 0; 58 независимых cold-проверок
и полный typed-NBT counter всех 31 снимка подтвердили сохранность. Ранние
ошибочные попытки частной обвязки не засчитаны. Произвольные модовые машины,
автокрафт, смерть/crash recovery и Linux/macOS GUI остаются отдельной приёмкой;
#41/#36 и общий допуск игроков этим не закрываются.
[Границы и доказательства](DJ2_ITEM_CUSTODY.md) обязательны для аудита.

Приватный Windows-кандидат 2.23.4-omk.2-rc.2 закрепляет полный клиентский состав
подписью: настоящий install/upgrade/kill/repair и обычный вход/ресурсный мир
приняты в [SIGNED_PACK_INSTALL](SIGNED_PACK_INSTALL.md). Отказ из-за пропущенного
JED исправлен в составе; гонка приватного exit-observer и независимая cold-проверка
описаны отдельно. Это не финальная матрица мира/выпуска или активация player release.
Следующий кандидат `2.23.4-omk.3-rc.1` добавляет только русский ключ кнопки Forge;
его обычный вход/UI/штатный выход и файловый возврат новыми подписанными
поколениями приняты отдельно в [DJ2_LANGUAGE_BUNDLE](DJ2_LANGUAGE_BUNDLE.md).
Все остальные прежние файлы и flags сохранены, новый exit-observer прошёл чисто.
GTNH не объявляем готовой. Стабильность и полнота перевода важнее свежести версии.
Все серверные acceptance выполняются в изолированных Linux Docker labs.

Обычные переносы вещей, крафт/печь, добыча, reconnect и restart отдельно
проверены с этими Core/Fix: 41 контрольный этап / 32 native click confirmations,
шесть именованных NBT-маркеров и 106 независимых проверок сохранений.
[Сохранность и ограничения](GAME_TEST_MATRIX.md#обычные-действия-и-сохранность-предметов).
Это серверный protocol scope, а не выполнение модов/рендер GUI полноценным клиентом.

## Закрытый перенос на VPS

Запускайте команды из корня проверенного checkout. Подставьте абсолютные пути
к копиям приватных конфигов. Сохраните привязку прежних имён проектов к томам.
Последовательность и миграция шаблонов описаны в [deploy/README.md](../deploy/README.md).

1. Сохраните deployment SHA, digest образов, конфиги, список mounts, исходный
   Drasl-том и валидный cold backup мира. Проверьте роль/имя и назначение томов
   по [карте хранилищ](PROJECT_STORAGE.md). Восстановите копию мира на отдельный
   target по [OWNER_RESTORES](OWNER_RESTORES.md) и сверяйте результат через
   `restores verify`.
2. Подготовьте конфиг Drasl по [AUTH_STORAGE](AUTH_STORAGE.md). Проверьте
   `docker compose -p omk-auth --env-file <auth.env> -f deploy/auth/compose.yaml config --quiet`,
   затем тем же префиксом выполните `up -d --build`. Убедитесь, что
   `omk-auth_drasl-state` монтируется в `/var/lib/drasl`, а приватный TOML
   подключён read-only. Проверьте auth из сети, которой должен пользоваться клиент.
3. Подготовьте env API по [шаблону](../deploy/api/example.env). Укажите
   `OMK_API_CONTENT_SOURCE` как абсолютный существующий каталог. Проверьте
   `docker compose --env-file <api.env> -f deploy/api/compose.yaml config --quiet`,
   затем тем же префиксом выполните `up -d --build`. Проверьте loopback
   `/health`, `/servers/status` и чтение выбранного контента. Источник
   `/data/content` сверяйте локально, внутри контейнера он read-only.
4. Поднимите проверенный профиль Forge DJ2 с его Java, приватной сетью и
   mount игрового мира по [профилю сервера](OWNER_MAINTENANCE.md). Проверьте
   игровой порт из нужного сегмента. После штатного сохранения и остановки
   запустите эту же копию и проверьте загрузку прежнего мира и состояния.
5. Для метрик выполните запуск из [RESOURCE_HISTORY](RESOURCE_HISTORY.md),
   для входного прокси используйте подготовку из [OWNER_INGRESS](OWNER_INGRESS.md).
   Сначала держите игровой вход закрытым для внешних игроков. Метрики и private
   upstream проходят по отдельным сервисам. Доступ извне проверяйте через выбранный
   ingress после приёмки закрытого стека.

При откате ограничьте игровой вход, выполните штатную остановку затронутого сервиса
и верните последний принятый image/config. Сохраняйте исходные тома и резервные копии.
Если менялся формат данных, сначала подтвердите восстановление в отдельный том,
затем переключите mount на принятую копию. Для уже принятого поколения сборки
подпишите нужное содержимое новым поколением и новой версией.

Подписанный клиентский возврат отдельно проверен с реальным хранилищем и
HTTP-источником: новая версия с прежними байтами, отсутствующий/повреждённый
файл, повторная попытка, сохранение личных файлов и сессии. Это не согласованный
возврат серверного мира/БД; границы — в `CLIENT_RELEASE_SNAPSHOTS.md` и #171.

Файловая подготовка серверного runtime + мира по выбранному snapshot принята
отдельно: [PROJECT_STAGE](PROJECT_STAGE.md). Сохраняются auth/access quarantine
и запрет boot; это не закрывает полный запуск/возврат приложения в #171.
Поверх этой копии [PROJECT_POLICY](PROJECT_POLICY.md) переносит текущие access,
RCON/network и известные FTB authority с полным файловым readback. Его отдельная
приёмка на native payload не включает candidate boot/gameplay; producer/journal
и общий application return остаются в #171.
Последующий [PROJECT_RETURN](PROJECT_RETURN.md) связывает обе файловые фазы
owner journal и проверен настоящими Forge/Drasl actors: historical/current
inventory/home/claim/access и отдельный возврат pre-change state после намеренного
отказа в приёмке. Есть независимые cold NBT/current-source проверки. Это explicit
loopback lab; внешний production lifecycle/ingress и несовместимые данные ещё
не приняты. Новый producer [PROJECT_EXPORT](PROJECT_EXPORT.md) требует настоящий
`ReleaseStore` и явный pack для schema 2: подписи/полный клиентский состав
проверяются до и после capture. Это не build attestation и не ретроспективная
приёмка прежних schema-2 lab references; перед promotion нужен отдельный контроль
сохранённых snapshots, trust policy и совместимости сервера/мира/клиента.
Последующий file-only опыт связал этот реальный client ref с raw/current-policy
journal и новым process verify на закрытой копии: все game hashes/modes, intent,
PvP/Hard/OP/NBT приняты. Это не новый game lifecycle, live authority или promotion;
границы — в [PROJECT_RETURN](PROJECT_RETURN.md).

Для существующего single-source [ingress](OWNER_INGRESS.md) отдельно принята
загруженная backup-политика: точный FTB artifact/config на диске, disabled/no-running
ответы на одном boot Core и повтор перед подтверждением открытия. Два реальных
старта одного Docker container, ordinary actor и cold backup проверены; старый
план без proof требует явной отмены. Это один дополнительный барьер #171/#33,
не общий candidate promotion или полный post-boot OP/FTB authority.

DJ2Fix 0.1.5 отдельно убирает автоматический startup-grant PlaneFix при
spawn-protection=0 и FTB spawn claims. Native AE2 matrix/restart и отрицательные
boot controls приняты в [DJ2_AE2_BOUNDARIES](DJ2_AE2_BOUNDARIES.md). Старые OP
не удаляются; полный controller/post-boot authority #171 всё ещё требуется.

Core 0.3.9 дополнительно подтверждает пустой loaded OP-список на том же boot;
ingress сверяет его с ops.json до intent и при verify. Старые open plans без
proof требуют закрытого cancel/нового plan. Это узкая часть post-boot authority;
полный controller и FTB permissions #171 остаются отдельными требованиями.

Книжный #174 закрыт по последующим протоколам: 447 статей без ошибок сборки,
4566 измеренных текстовых блоков без непустых глифов ниже реальной страницы,
проверенные ссылки/динамические поля и ресурсный возврат. Это не ручной просмотр
каждой страницы и не прохождение всех рецептов. Ранние разделы «остаток приёмки»
в книжных документах сохраняют историю; не повторяем принятые сценарии без
связанных изменений, воспроизводимого сбоя или явно непокрытого случая.

Названия документов выше проверяются при обновлении этой входной точки. Порядок
развёртывания и acceptance не следует восстанавливать по старой записи changelog.
Точные протоколы находятся в `docs/validation/`; их ограничения так же важны,
как число пройденных проверок.

## Условия первого запуска

- [#33](https://github.com/omkality/omkalitycraft/issues/33) — холодная копия
  мира и Drasl, зашифрованная копия вне VPS, проверенное восстановление
  с актуальными полномочиями и подтверждённый запас диска. Для первого запуска
  применяется ручной порядок. Календарный планировщик на паузе.
- [#36](https://github.com/omkality/omkalitycraft/issues/36) — точные архивы
  Windows/Linux, подписи, установка, обновление и обычный вход с повторным
  подключением. На Windows проверяем игру со звуком. Повтор обрыва LoginSuccess
  или сбоя OpenAL на обычном пути препятствует допуску.
- [#38](https://github.com/omkality/omkalitycraft/issues/38) — эффективная
  конфигурация VPS, приватное управление, мониторинг, ограниченный игровой
  вход и подготовленный стабильный выпуск. Перед допуском сверяем принятые
  исправления FTB, пустой список OP, права обычного игрока, Hard и границы.

Итоговая приёмка и момент первого запуска ведутся в #38. История сводной задачи
сохранена в [#41](https://github.com/omkality/omkalitycraft/issues/41).

После первого запуска остаются точечный откат базы (#34), журналы действий и
чата (#52/#58), расследование минимального Forge и OpenAL (#102/#163),
расширенная матрица FTB (#29/#105), аналитика реальной нагрузки (#146) и
универсальный возврат изменений (#171). Испытанные исправления и ручной путь
восстановления входят в первый профиль. [Задачи после запуска](https://github.com/omkality/omkalitycraft/milestone/2)

## Оставшаяся последовательность для запуска

1. Принимаем точные архивы, обычный вход, перезапуск и ручное восстановление на
   отдельной копии. Готовим один согласованный профиль клиента и сервера.
2. После приёмки владелец выполняет финальный вайп Основного мира через TUI
   с проверенной копией и подтверждением. Игровой вход остаётся закрыт.
3. Проверяем новый мир, Hard, отсутствие OP, границы и вход обычного игрока.
   После этой проверки открываем вход первым игрокам и публикуем принятые архивы.

Доверенный HTTPS на IPv4 подходит для первого выпуска. Переход на домен и
массовая предгенерация отложены. Календарный планировщик остаётся на паузе.
