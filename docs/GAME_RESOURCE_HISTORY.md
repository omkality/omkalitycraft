# Игровые показатели Forge 1.12.2

> Историческая приёмка Core JSON producer. Текущий backend описан в
> [RESOURCE_HISTORY.md](RESOURCE_HISTORY.md); Python reader/SQLite удалены.
> Opt-in producer Core 0.3.8 остаётся для совместимости, новый deployment его не включает.

Общий серверный Core **0.3.7** умеет выпускать приватный снимок состояния для
Python collector. Интеграция не зависит от DJ2, FTB, имени измерения или GUI.
DJ2Fix/Client для этого не меняются. Нет игровых команд, RCON, JMX-порта или
HTTP endpoint. По умолчанию producer выключен.

## Показатели и их смысл

- `observed_tps` — фактически наблюдаемое число завершённых серверных тиков
  относительно монотонного времени. Используется скользящее окно с default
  60 секунд. Первый замер неизвестен. На прогреве окно короче; при редких замерах
  берётся ближайшая опорная точка перед границей окна. `interval_ms` сообщает
  реальную длину окна; после долгой остановки она может превышать nominal window.
  Catch-up ограничен сверху 20 TPS. Это не расчёт `1000 / MSPT`.
- `tick.{samples,mean_ms,p95_ms,max_ms}` — реальные значения из штатного
  `MinecraftServer.tickTimeArray`, последние 100 завершённых тиков. Начальные
  незаполненные элементы не превращаются в нулевые тики. p95 — nearest rank.
- `dimension.<id>.{samples,mean_ms,p95_ms,max_ms}` — такие же окна из Forge
  `worldTickTimes`, только для загруженных измерений. Это затраты тика самого
  измерения, а не отдельные TPS каждого мира. Число ID ограничено; есть
  `dimension_count` и явный `dimensions_truncated`.
- `online` — число серверных игроков в текущем PlayerList. Имена/UUID игроков
  в этот файл не включаются.
- `heap_used_bytes`, `heap_committed_bytes`, `heap_max_bytes` — MemoryMXBean,
  а не размер всего Java-процесса. Max может отличаться от числа в `-Xmx`:
  например, отдельный контроль того же Java 8 при `-Xmx4G` дал 3817865216 байт.
- `gc_collections_total`, `gc_millis_total` — накопленные показатели GC MXBeans.
  Отрицательные/неподдержанные значения остаются неизвестными. Это приблизительное
  суммарное время работы GC, **не список stop-the-world пауз и не p95 пауз**.
  Python рассчитывает скорость только между новыми снимками того же запуска
  по uptime JVM. Повторное чтение файла не добавляет ещё один GC interval.

Часовой `max` от `tick.p95_ms` — максимальный из наблюдавшихся p95 коротких окон,
**не p95 всех тиков за час**. По таким замерам нельзя обещать, что были замечены
абсолютно все короткие лаги. В частности, частота collector должна соответствовать
частоте producer. Окно TPS позволяет не терять наблюдённую остановку сразу после
следующего короткого нормального интервала.

Источник реализации окон — закреплённый Forge 14.23.5.2860, а поведение MXBeans
определяет [Java 8 GC API](https://docs.oracle.com/javase/8/docs/api/java/lang/management/GarbageCollectorMXBean.html).

## Запись и остановка

На END server tick снимаются только ограниченные числовые данные. Файловая запись
идёт отдельным daemon worker с очередью на **один** ожидающий снимок. Новое состояние
может заменить ещё не записанное старое. Игровой поток не ждёт fsync. JSON до
64 KiB публикуется атомарной заменой `current.json`; частичный `.pending` не читается.

В выделенной папке допускаются только `current.json`, `.pending`, `.writer.lock`.
На Linux каталог 700, файлы 600, symlink/hardlink не допускаются. Lock удерживается
writer до конца работы; отдельный guard защищает повторное открытие того же inode
в одной JVM. Другой server producer не должен использовать эту папку.

При недоступной записи старый полный файл остаётся на месте; ошибка выводится
ограниченно, без исходных значений/путей и без прекращения игровых тиков. После
устранения причины worker продолжает запись. Его очередь/набор временных файлов
не растут. Стандартная остановка пытается опубликовать новый `running=false`
с новой sequence; ожидание writer ограничено одной секундой. Такой снимок —
последнее сообщение producer, **не доказательство завершения процесса или backup**.

Неожиданное завершение JVM может не оставить терминальный снимок. Collector
отмечает источник устаревшим после TTL. Пока свежесть не истекла, данные означают
последнее наблюдение, не мгновенный health сервера. Это диагностический поток,
не admission barrier и не механизм обнаружения всех рестартов между опросами.

## Env и Docker

| Переменная | Default | Допустимо |
|---|---|---|
| `OMK_GAME_METRICS_ENABLED` | `false` | `true` / `false` |
| `OMK_GAME_METRICS_INTERVAL_SECONDS` | `30` | 5–300 |
| `OMK_GAME_METRICS_TPS_WINDOW_SECONDS` | `60` | 5–3600, не меньше interval |
| `OMK_GAME_METRICS_MAX_DIMENSIONS` | `32` | 1–64 |
| `OMK_GAME_METRICS_DIRECTORY` | `omk-metrics` относительно working directory | Отдельная папка producer |

Параметры проверяются без молчаливого исправления ошибок. Если профиль требует
`core.metrics`, а producer выключен или не может инициализироваться, требования
профиля не выполняются. Runtime I/O failure после запуска не крашит игру.

Пример env: `deploy/metrics/game-producer.example.env`. На VPS используем отдельный
volume, смонтированный writable в game как `/run/omk-metrics`, и **тот же volume**
readonly в collector как `/gamefeeds/dj2`. Не монтируем для этого весь game/auth
volume. Оба процесса должны иметь разрешение на private файл — в принятом lab
оба работают как UID 10001. Права всего игрового каталога ради collector не ослабляем.

К базовому Compose collector можно добавить `game-feed.example.yaml`; это только
readonly mount существующего внешнего volume. Overlay не поднимает Minecraft,
не создаёт working VPS и не меняет его настройки. Владелец предварительно
подготавливает volume с корректными владельцем/правами и подключает его к game.

`config.game.example.json` показывает optional секцию `games`. `profile` должен
**точно** совпадать с `id` в `config/omkalitycore-profile.properties`, а `core_version`
— с producer. Значение `dj2-2.23.4` в примере требуется заменить фактическим ID;
имя карточки лаунчера не является ID server profile. TTL `max_age_seconds` лучше
оставлять не меньше двух-трёх интервалов producer; default примера 90 секунд.
До четырёх game источников; общие caps payload/числа метрик коллектора сохраняются.

## Чтение и корреляция

Collector проверяет формат, профиль/версию, UTC timestamp, boot/sequence/uptime,
диапазоны чисел, tick windows и список измерений. Невалидный или недоступный источник
получает `game.<id>:unavailable`, устаревший — `game.<id>:stale`. Их online/TPS/heap
не записываются как ноль. Свежий terminal snapshot даёт только `running=0` и age,
без ложного активного online/TPS. Новый boot начинает baseline GC заново.

В существующей приватной SQLite подробная запись связывает host/cgroup и игровые
показатели по одному collection timestamp; собственный `sampled_at_ms` producer,
boot, sequence и фактическая age сохраняются в metadata `games`. Это разнесённые
во времени наблюдения, не атомарный snapshot ОС и игры. Рабочие показатели доступны
тому же read-only `hourly_report`, что и host metrics; новых omk-команд нет.

Часы работы с игроками можно отличать по online, а restart/stale — по boot/state/age.
Расширенная автоматическая привязка к backup/preload/reset и отдельный отчёт по
активным интервалам остаются в #146. Во время стартовой загрузки Forge до
FMLServerStartedEvent producer ещё не выдаёт игровые показатели. Не объявляем
это время «сервер простаивает» по отсутствию файла.

Настоящий VPS, длительная игра и запас под вторую сборку проверяются на этапе #38.
Локальный пустой сервер этого не доказывает. Адаптер не меняет генерацию, квесты,
права FTB, аутентификацию, исходники DJ2Fix/Client или клиентские manifests.
