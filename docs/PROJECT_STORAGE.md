# Общий учёт томов и бюджет проекта

```console
uv run omk admin --config .omk-admin/operator.toml storage estate
```

Команда собирает **все серверы из текущего backups.toml** и явно перечисленные
общие тома проекта. Это расширение [отчёта одного сервера](OWNER_STORAGE.md),
доступное только владельцу. Оно возвращает JSON, не меняет данные и не управляет
сервисами. Содержимое БД, файлов скинов, ключей, конфигов и логов не читается.

## Явный реестр общих томов

Скопируйте [образец](../deploy/storage-volumes.example.toml) в
`.omk-admin/storage.toml` с правами `600` на Linux/macOS. Родительская папка
остаётся `700`. Запишите точные существующие Docker volume name, ownership label
и его значение. Для стандартного auth Compose с project `omk-auth` пример:

```toml
schema = 1
[volumes.auth]
volume = "omk-auth_drasl-state"
label = "com.docker.compose.project"
owner = "omk-auth"
```

`auth` обязателен: аккаунты и ключ подписи нельзя молча пропустить в общем учёте.
Дополнительные роли — `content` (CDN/launcher payload), `reports` (приватная
диагностика) и `exports` (временные приватные выгрузки). Только named volumes;
произвольные host paths и каталог Docker daemon в helper не передаются.

Тома не создаются, не усыновляются и не получают labels ради проверки. При
отсутствующем реестре, отсутствующем томе или несовпадении ownership — отказ.
Общие тома обязаны отличаться от всех source/store/reset/restore и друг от друга.
Labels подтверждают явный выбор владельца, а не защищают от другого администратора
Docker. Не удаляйте и не пересоздавайте эти ресурсы параллельно с owner-командами.

Source/store и текущие reset/restore targets берутся из прежних приватных
конфигураций. Список серверов, не имеющих backup-настройки, возвращается как
`unconfigured_servers`; они не считаются проверенными. `missing_shared_roles`
показывает ненастроенные дополнительные роли. Неперечисленные старые/orphan volumes
автоматически не сканируются и не удаляются.

## Как считается бюджет

Используется тот же [план через OMK_STORAGE_*](WORLDS_AND_STORAGE.md). Все серверы
делят один проектный бюджет; каждой сборке не выделяется ещё один полный диск.
Планируемая ёмкость не подменяется огромным виртуальным диском Docker Desktop.
Если объявленные 200 ГиБ больше измеренного filesystem, это явно отмечается.
Маркетинговые 200 GB и 200 ГиБ различаются; реальную ёмкость VPS нужно измерить.

| Данные | Бюджет |
| --- | --- |
| Все активные миры | `worlds` |
| Managed store и старые pack backups | `backups` |
| Предыдущие/отклонённые/частичные поколения, reset/restore targets, exports | `staging` |
| Game logs, crash reports, reports | `logs` |
| Shared content | `content` |
| Runtime/прочие source-файлы, auth и неразобранный занятый объём | `system` |

По каждой категории возвращаются logical/allocated bytes и консервативный
`charged_bytes`: для каждой исходной группы берётся большее из двух значений.
Таким образом, sparse-файл не выглядит бесплатным, а служебные blocks каталогов
не теряются. Это оценка, не filesystem quota.

Общий Linux filesystem учитывается один раз независимо от числа mounts.
`available_bytes` — минимум наблюдений до/после каждого обхода, `below_reserve`
сравнивает его с проектным резервом `OMK_STORAGE_RESERVE_GIB` (default 24 ГиБ).
У старого per-server отчёта резерв по-прежнему берётся из `OMK_BACKUP_RESERVE_BYTES`;
оба интерфейса показывают свою политику, не изменяя её.

`unattributed_or_reserved_bytes` — разница между total, доступным остатком и
учтёнными allocated blocks. Она включает неразобранные данные ОС/Docker/других
проектов и filesystem-reserved blocks. Этот объём консервативно добавляется к
`system.unattributed_charge_bytes`. Команда **не утверждает**, что прочитала и
классифицировала Docker images/cache/container logs или всю ОС.

Для одного общего раздела `observed_within_limits` проверяет категории, ёмкость
и свободный резерв. Для нескольких filesystem он остаётся false:
`single_filesystem_budget_evaluable=false`, нужен отдельный план распределения
бюджетов по разделам. Свободные остатки разных дисков не складываются в фиктивный
общий резерв. `host_disk_complete=false`, `enforced=false` и
`admission_approved=false` сохраняются всегда.

### Лимиты будущих операций

`budget.declared_operation_limits` отдельно сравнивает настройки **текущего
процесса CLI**: сумму per-server `OMK_BACKUP_MAX_BYTES`, сумму world caps и
staging одной операции с проектными бюджетами. Например, два лимита по 48 ГиБ
несовместимы с общим backup-бюджетом 48 ГиБ, даже если архивов пока мало.

Для двух серверов лимит по 24 ГиБ укладывается в такой общий backup-бюджет, но
конкретное распределение нужно выбирать по измеренным мирам. Отчёт не читает
прошлую policy существующих stores и не мигрирует её: изменение env не меняет
уже созданное хранилище автоматически. Один global lock здесь защищает от
параллельных штатных owner-команд, а не доказывает отсутствие внешних writers.

## Изоляция и точность

Pinned Linux helper: без сети, Docker socket и capabilities, rootfs и все
учитываемые тома read-only с `volume-nocopy`. Перед/после проверяются точные
конфигурации и identity томов. Shared scanner ограничивает суммарные entries и
depth теми же `OMK_STORAGE_MAX_ENTRIES` / `OMK_STORAGE_MAX_DEPTH`.
CPU/RAM/timeout берутся из прежних helper env; неограниченного обхода нет.

Symlink/hardlink/special file, пересечение roots, превышение лимита и обнаруженное
изменение во время обхода дают отказ без частичного успешного отчёта. Лучше
проверять в тихом окне. Метаданные повторно сверяются, но это не атомарный снимок
работающих Minecraft/SQLite и не проверка целостности резервной копии. Команда не
останавливает Drasl/сервер ради результата.

## Приёмка и оставшаяся работа

На десяти свежих Linux Docker volumes выполнена настоящая CLI: две отдельные
копии принятых DJ2 экспортов, два backup store, reset/restore, реальный Drasl и
shared payloads. 38 условий, 7700 файлов. Количество/байты сверены независимо,
все SHA до/после прежние; секреты и содержимое файлов в отчёт не попали.
Drasl после повторного запуска сохранил аккаунт, скин и ключ подписи. Собственные
контейнеры/тома удалены после проверки. Вторая копия — проверка учёта нескольких
серверов, **не приёмка GTNH**; Minecraft в этом прогоне не запускался.

Дальше #33 требует выбрать и принять один periodic writer/scheduler, согласовать
запас перед каждой записью, retention и encrypted off-host copy. Этот отчёт не
меняет FTB Backups и не включает второе расписание. Бюджетное наблюдение нельзя
использовать вместо backup/restore proof или разрешения на запуск игроков.
