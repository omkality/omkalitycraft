# Подписанная установка и обновление клиента

Промежуточная приёмка [#49](https://github.com/omkality/omkalitycraft/issues/49),
4 ноября 2026. Проверен локальный кандидат `2.23.4-omk.1-rc.1`, без переключения
рабочего профиля 2.21.3. Это не публичный выпуск или миграция серверного мира.
[Точные результаты и хеши](validation/dj2-signed-install-2026-11-04.json).

## Повторяемая команда

```powershell
uv run omk lab pack-install --source-release <source-directory> --target-release <target-directory> --public-keys <trusted-public-keys.json>
```

Каждая входная папка содержит `manifest.json` и `files/`. Манифесты должны иметь
проверяемые подписи, одинаковые pack ID/платформу и соответствовать текущей ОС.
Для отрицательного сетевого контроля нужен изменённый файл больше 384 КиБ;
для repair — хотя бы два JAR в подписанной папке `mods/`.

Входы читаются и проверяются по SHA256. Команда создаёт новый каталог
`omkalitycraft/.local/pack-install-<id>/`, поднимает HTTP только на loopback и
устанавливает две собственные копии. Существующие instances, миры и сессии
игроков не используются. Учётные записи не создаются, Minecraft не запускается.
Вместо настоящих миров/сессий здесь явно помеченные тестовые файлы.

`--target-cdn http://127.0.0.1:<port>` позволяет проверить чистую установку через
уже запущенный настоящий API. Допустим только loopback. Подписанный digest
должен совпасть с локальным target; HTTP-фикстура при этом всё равно отдельно
создаёт контролируемый обрыв обновления. Команда сама не развёртывает API.

Отчёт — `report.json`; `ok` относится только к указанным условиям установки.
`accepted_player_release=false`, `minecraft_started=false`. Тестовые копии и
частичные файлы сохраняются для разбора, автоматического удаления нет. Требуется
свободное место на source + две target-копии и резерв 512 МиБ.

## Результат на полной DJ2

Кандидат содержит **5 274 файла / 741 838 782 байта**, включая 223 авторских
клиентских JAR и приватный клиентский адаптер 0.1.0. При сборке сверены все
ожидаемые bytes/hash. 137 изменённых игрой конфигов восстановлены из закреплённого
авторского ZIP с проверенными policy; каталоги игрока и runtime-кеши не упакованы.
Подпись кандидата создана временным лабораторным ключом, который не сохранялся.
Он явно добавлен только в ключи этого стенда вместе с ключом старого выпуска.
Рабочие ключи доверия/подписи не менялись.

| Условие | Результат |
| --- | --- |
| Полный исходный подписанный клиент 2.21.3-omk.4 | Установлен, SHA256 всех файлов проверены |
| Три коротких HTTP-ответа при обновлении | Частичный файл 384 КиБ сохранён, состояние incomplete, история source сохранена |
| Новый экземпляр установщика после отказа | Range докачка с 393 216 байт; финальные hashes всех 5 274 файлов совпали |
| Очистка предыдущего выпуска | 1 113 прежних подписанных файлов удалены только после успешной загрузки target |
| Личные данные | options/FOV/render distance, изменённая JourneyMap, собственная запись сервера, тестовые saves/screenshots/userdata сохранены |
| Repair | Удалённый мод и повреждённый мод той же длины восстановлены ровно двумя скачиваниями |
| Повторная проверка здоровой установки | Ни одного скачивания |
| Чистая установка через Linux API | Тот же signed digest, все hashes совпали, installed |
| Нет сети при запросе манифеста | Запрос завершается ошибкой, предыдущие готовые файлы не повреждаются |

Всего пройдены 22 условия. Чистая установка использовала настоящий Linux API:
Granian 2.8.6, два workers, 1 CPU / 512 МиБ, read-only контент. Лимит 10 000 req/s
задан исключительно для локальной проверки множества мелких файлов; это не
нагрузочная приёмка или предложенная production-настройка. API остановился с
exit 0 / OOM false; удалены только его собственные контейнер и тестовый тег.

Первый полный прогон дошёл до 17 условий, но чистая установка получила 404:
в Docker-фикстуре забыли CONTENT_ROOT, и API использовал пустую папку по умолчанию.
Этот прогон не принят и сохранён. В повторе заранее проверены правильный
read-only корень и точный подписанный манифест; критерии установки не ослаблялись.

## Настоящий клиент после обновления

Именно обновлённая папка установщика затем запущена штатным GameRunner на Windows
с вложенной Java и Drasl + authlib-injector. Без probe и диагностического JVM-флага
клиент вошёл на новый Linux Forge-сервер с неизменённым Core 0.2.8. На F2-кадре
наблюдались HUD без зависшей плашки, контрольные предметы и пользовательская
**круглая JourneyMap с сеткой**. Значения не вернулись к square/no-grid defaults.
Семь предметов/12 уровней дополнительно подтверждены серверным запросом.

После штатного server kick выполнено наблюдение и осмотр F2-экрана, затем обычное
закрытие клиента. Клиент/сервер завершились с exit 0, server OOM false; новых или
перезаписанных reports и task/fatal markers нет. Мир собственного стенда экспортирован
до удаления volume, тестовая авторизация остановлена. Это не обычный клик выхода
без probe: отдельное условие [#65](https://github.com/omkality/omkalitycraft/issues/65)
остаётся открытым. Игровой renderer Linux/macOS не проверен этим Windows-запуском.

## Ошибка манифеста и запуск

При исследовании выявлен прежний fallback контроллера: ошибка CDN или подписи могла
привести к использованию cached release. В 0.3.0.dev9 перед подготовкой/запуском
обязателен успешный запрос актуального подписанного манифеста. При отказе игра не
стартует, файлы и запомненная сессия сохраняются. Это подтверждено отдельными
Qt-тестами для сетевого отказа и ошибки подписи.

Сетевой отказ показывает короткое сообщение о соединении, с кнопкой «Повторить»
для установленной сборки. Текст предупреждения помещается в минимальном окне
1020×680. Повторный клик снова проверяет манифест; дополнительных действий с
аккаунтом не требуется. Это поведение официального лаунчера; серверная проверка
совместимости остаётся самостоятельной границей.

## Оставшиеся границы

- Short-body контроль выше не был kill процесса. Дополнительный настоящий kill
  описан ниже; физическое отключение питания и гарантии fsync этим не проверены.
- Sentinel saves не являются проверкой конверсии серверных миров или старых
  игровых аккаунтов. Отдельный порядок [миграции](PACK_UPGRADES.md) сохраняется.
- Перевод, JEI/квесты, остальные серверные регрессии и клиентские Linux/macOS
  требуют собственной приёмки. Профиль, payload и публичный выпуск не переключены.

## Аварийное завершение процесса установщика

В 0.3.0.dev10 добавлен отдельный режим:

```powershell
uv run omk lab pack-install --hard-kill --source-release <source-directory> --target-release <target-directory> --public-keys <trusted-public-keys.json>
```

Он создаёт собственную папку `.local/pack-process-<id>/` и дочерний Python-процесс,
останавливает HTTP-поток после первой части изменённого файла, принудительно завершает
только этот дочерний процесс и запускает новый. Существующие instances не используются.
Нужен изменённый файл от 1 МиБ; `--target-cdn` с этим режимом не совмещается.
Файлы и журналы стенда остаются в его папке; план содержит только loopback URL и
публичные ключи, паролей и игровых токенов нет. Minecraft не запускается.

На полной 2.21.3 → 2.23.4 пройдены **15 условий**: Windows TerminateProcess дал exit 1,
сохранились 262 144 байта `.part` и состояние incomplete. Новый процесс докачал с этой
отметки и завершился с exit 0. Проверены hashes всех 5 274 файлов, история source,
очистка прежних файлов только после успеха и сохранность личных файлов. Это реальный
процесс ОС, но не потеря питания, не принудительное завершение самой игры и не тест
файловой системы VPS. [Результаты](validation/pack-recovery-minimum-2026-11-04.json).

## Подписанная минимальная версия лаунчера

Новый формат манифеста `schema=2` обязательно содержит `minimum_launcher_version`.
Это подписанное Ed25519 поле; удалить или изменить его без ключа нельзя. Сравнение
версий учитывает dev/rc/stable, а не сравнивает строки. До изменения папок и запуска
Java проверка выполняется в HTTP-клиенте, Installer и GameRunner. При недостаточной
версии показывается короткое предупреждение с предложением перезапустить лаунчер;
сессия и скачанные файлы остаются. При сетевом отказе cached pack не запускается.

На полном подписанном манифесте проверены принятие совместимого минимума и отказ
для будущего `9999.0` без скачивания artifacts. Сам payload rc.1 не менялся; лабораторный
вариант только метаданных получил имя rc.2, отдельно от проверенного игрового rc.1.
Сохранённый reader dev9 из точного Git commit принял исходный schema 1 и отверг
корректно подписанный schema 2. Это проверка reader, не запуск старого compiled GUI.

Первым публикуется и проверяется совместимый лаунчер через TUF, затем pack manifest
с новым минимумом. [Команда выпуска](RELEASES.md) по умолчанию ставит текущую версию.
Legacy schema 1 читается для существующих локальных выпусков и не содержит такого
требования. Старые предварительные лаунчеры до dev9 с cached fallback не объявляются
безопасными задним числом; публично они не выпускались.

Минимум ограничивает официальный лаунчер и не является удалённой аттестацией клиента.
Он не заменяет серверную проверку аккаунта/модов. Подпись pack сама по себе не
обеспечивает свежесть при подаче прежнего корректного манифеста: нужны доверенный
HTTPS/CDN и отдельная политика совместимости сервера; TUF защищает обновления
лаунчера. Публичное развёртывание и остальные условия #38 ещё не приняты.
