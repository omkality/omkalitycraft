# WR-CBE: последний тик после выгрузки менеджера

3 ноября сценарий повторён на [DJ2 2.23.4 / Core 0.2.8](DJ2_CORE_UPGRADE.md)
с MixinBooter 10.7: 67 проверок, три старта / два restart и чистое завершение.
Для этой версии стенд требует явный `--pack-version 2.23.4` и её точные pins;
default 2.21.3 и прежние результаты ниже сохраняются.

На отдельном Linux DJ2 обнаружен `NullPointerException` в `WREventHandler.worldTick`:
во время остановки `onWorldUnload` обнуляет `RedstoneEtherAddons.serverManager`,
после чего оставшийся START callback обращается к нему через `processSMPMaps`.
Forge при этом может завершиться с кодом **0**. Первоначальное наблюдение и исходный
артефакт сохранены в [записи от 1 ноября](validation/dj2-wrcbe-shutdown-crash-2026-11-01.json).
Это не установленный OOM и не подтверждённый краш обычного перехода между измерениями.

## Исправление в приватном Core 0.2.6

Узкий late Mixin через уже установленный MixinBooter пропускает callback, только если:

- сторона серверная и фаза START;
- менеджер WR-CBE уже отсутствует;
- сервер существует и больше не работает (`isServerRunning=false`).

Обычные тики, END, сохранение/выгрузка миров и работа устройств остаются на штатном
пути WR-CBE. Ошибка отсутствующего менеджера при работающем сервере не скрывается.
Неподдерживаемые версии/хеш WR-CBE или несовпадение точки внедрения останавливают
инициализацию. Нет перехватчика всех NPE, отключения мода или изменения рецептов.

JAR WR-CBE и MixinBooter исходного DJ2 не менялись; Core остаётся приватным.

## Как проверяем

Новый CLI создаёт свежую копию модов/конфигов без старых миров и аккаунтов. Forge
работает в Linux Docker: 6 ГиБ RAM, 4 CPU, heap 4 ГиБ, закреплённый Java 8 image
из [SERVER_CONTAINERS.md](SERVER_CONTAINERS.md). Порты loopback; Drasl одноразовый.

```text
uv run omk lab dj2-wrcbe --server-source PATH_TO_DJ2 --agent PATH_TO_AUTHLIB_1_2_8 --core PATH_TO_CORE_0_2_6 --mods-json PATH_TO_VERIFIED_CLIENT_MODS --probe PATH_TO_OMK_WRCBE_LAB_PROBE --cycles 3
```

Для контроля старого поведения — та же команда с Core 0.2.5 и `--baseline`.
Если возникает естественная гонка, baseline завершается ошибкой проверки чистого выхода;
это ожидаемое воспроизведение дефекта, а не зелёный результат. Журнал/volume сохраняются.
`--cycles` допускает 1–5 запусков; один запуск не является проверкой перезапуска.
До создания Drasl/сервера проверяются обязательные файлы и хеши внешних артефактов.

Отдельный диагностический мод существует только в стенде, требует явный lab JVM flag
и `level-name=lab-world`. Он создаёт реальные ForgeMultipart передатчик/приёмник,
проверяет частоту 321 и её имя. Настоящие redstone blocks включают/выключают передатчик;
проверяется состояние приёмника, затем сохранение после полного restart. Итоговый CLI
после restart также выключает и вновь включает питание: сохранённый `active=true`
сам по себе не доказывает, что восстановилась рабочая связь.
Последний протокольный игрок выходит из Nether непосредственно перед `stop`.

Чтобы не полагаться на случайное расписание гонки, пробник после настоящей выгрузки
менеджера на остановке вызывает настоящий обработчик WR-CBE с START/END событием.
Это **контролируемый повтор callback**, не утверждение, что естественная гонка случилась
в каждом прогоне. Baseline должен получить NPE в START; исправленный — штатный возврат.
Дополнительно менеджер на мгновение обнуляется в серверном потоке при работающем сервере:
ожидаемый NPE перехватывает сам пробник, а прежний объект безусловно возвращается в `finally`.
Так проверяется, что исправление не маскирует ошибки активного сервера.

## Артефакты и границы

2 ноября 2026 предварительный исправленный стенд прошёл **47 проверок / 3 старта**:
физическое включение/выключение передатчика, состояние приёмника, одинаковые частоты,
имя частоты, сохранность после двух restart, START/END и отрицательный контроль живого
менеджера. Все три остановки чистые, без OOM. Этот прогон использовал ранний локальный
драйвер того же сценария; итоговый публичный CLI проверен отдельно усиленным сценарием ниже.

Контроль с Core 0.2.5 выполнил 23 проверки до остановки и **воспроизвёл естественный
краш** через `FMLCommonHandler.onPreWorldTick` → `WREventHandler.worldTick:170`.
Процесс снова вернул 0, но журнал помечен fatal и volume сохранён. Отдельно записаны
четыре контролируемых START callback с тем же NPE; четыре END callback штатные.
Исходный сбойный report не переписан в успешный результат.

Итоговая команда CLI (источник `7a141b6`) прошла **67 проверок / 3 старта и 2 restart**,
в том числе повторное физическое выключение/включение передатчика после каждого
restart с изменением состояния приёмника. Все 12 контролируемых START/END пар после
dispose обработаны без ошибки; три настоящие остановки чистые. Мир экспортирован,
временная авторизация удалена, собственный volume удалён после экспорта.
[Сравнение baseline/исправления, все проверки и хеши](validation/dj2-wrcbe-shutdown-2026-11-02.json).
Локальные unit/UI: 513 passed, 3 Windows symlink skips; Ruff/Black прошли. Сборка Core
повторяет SHA256; пробник и чужие зависимости в Core не попадают, неверный compile
artifact MixinBooter отклонён до исполнения компилятора.

Обычный `omk lab dj2-rtp` с этим Core, **без OmkWrcbeLabProbe**, повторно прошёл
50 проверок RTP/прав/измерений/переподключения/конкурирующих запросов и чистый stop.
[Отчёт регрессии](validation/dj2-rtp-core-0.2.6-2026-11-02.json). Это дополнительная
проверка штатного запуска, а не повтор всех тестов спавна/могил или проверка VPS.

`omkalitycraft/.local/wrcbe-status.json` показывает фазу. В новом
`omkalitycraft/.local/wrcbe-shutdown-<id>/` сохраняются `report.json`, журналы каждого
цикла и `export/world-after.tar`. Штатно собственный volume удаляется только после
экспорта и подтверждения чистого выхода по журналу; при фатальном сбое Forge volume
сохраняется. Ошибка отдельного assertion при чистом stop может оставить только экспорт,
поэтому точный результат очистки всегда записан в report.
Существующие серверы/миры не подключаются. Пробник не попадает в Core или лаунчер.

Проверяются конкретный lifecycle-дефект и базовая беспроводная связь. Полноценный
графический клиент, все карты/снифферы/джаммеры, сложные сети, длительная нагрузка,
аварийный kill/потеря питания и GTNH этим сценарием не покрыты. Готовность всего
DJ2 к открытию остаётся отдельным [трекером #41](https://github.com/omkality/omkalitycraft/issues/41).
