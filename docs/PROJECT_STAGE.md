# Подготовка файлов выбранного серверного выпуска

`omk.project_stage` продолжает [закрытый project export](PROJECT_EXPORT.md).
Внутренний Linux API подготавливает **полный runtime и мир** в новом приватном
каталоге. Он использует существующие проверки TAR/ZIP и копирование файлов
`linux_world_restore`; новых CLI, зависимостей, фоновых служб и расписания нет.

Это файловая подготовка для #171. Даже проверенный результат оставляет
`quarantine_required=true`, `boot_allowed=false`, `ready_for_players=false` и
`current_policy_reconciled=false`. Он не принимается существующим world-only
cutover как разрешение заменить runtime или запустить сервер.

## Выбор и полномочия владельца

До вызова controller держит общий owner lock, проверяет labels/владение новым
томом и отсутствие других пользователей target. Source монтируется readonly;
его подлинность уже проверена существующим транспортным receipt. Существующий
мир, auth volume и установленный сервер не являются target.

Выбор содержит две независимо сохранённые ссылки:

- `release_identity` выбранного schema-2 экспорта: Git commit, runtime/image,
  клиентские manifest refs и объявленный контракт сохранений;
- `project_sha256` — SHA256 **точного `project.json` выбранного снимка**. Один
  runtime может иметь разные снимки мира, поэтому identity выпуска недостаточно.

Ожидаемые ссылки получают из доверенного плана/проверенного transport receipt,
а не вычисляют из неизвестного каталога перед его проверкой. Schema 1 остаётся
читаемым резервным форматом, но этот API не принимает его за выбранный выпуск.
Происхождение Git-кода, подписи клиентов и совместимость данных остаются
обязанностью controller; формат строки контракта этого не доказывает.

Source и target — отдельные абсолютные пути без ссылок и пересечения. Target
должен уже существовать, быть пустым и приватным (`0700` на Linux). План связывает
operation ID, оба пути, выбор, имя мира, настройки, количества/размеры и digest
обоих инвентарей. Перенос source/target требует нового плана, не редактирования
старого журнала. Входные dict отделяются от сохранённых данных плана.

## Внутренний API

```python
expected = project_stage.plan(
    source, target,
    operation=operation_id,
    world=world_name,
    selection=trusted_selection,
    settings=frozen_export_settings,
)
# Controller сохраняет expected до запроса записи.
result = project_stage.stage(source, target, expected=expected)
# После потерянного ответа — проверка тем же independently saved expected:
result = project_stage.verify(source, target, expected=expected)
```

`plan` только читает: проверяет точный внешний набор девяти файлов, binding
выпуска, все внутренние TAR/ZIP bytes и выбранный корень мира. Runtime и мир
не должны пересекаться. Сохраняются регистр Linux-путей и обычные runtime mode
bits; links, hardlinks, дубликаты, traversal и конфликты file/directory отказывают
существующими guards. Общий инвентарь ограничен прежними 20000 путями; ZIP мира
сохраняет собственную прежнюю политику имён.

`settings` — те же шесть замороженных export limits, включая free reserve.
Параметры исходного capture описаны в [PROJECT_EXPORT](PROJECT_EXPORT.md#бюджеты).
Перед копированием повторно проверяется место: распакованные runtime + world,
4096 байт на файл, запас записей и reserve. Это preflight, не filesystem quota;
общий allocator/retention нескольких операций остаётся в #33.

`stage` повторно связывает source с планом и требует всё ещё пустой target.
Сначала пишет/fsync `.omk-project-stage-plan.json`, затем создаёт `game/` и
копирует файлы через прежний проверенный copier с `xb`, hash readback и fsync.
Runtime получает прежние mode bits, файлы мира — `0600`. После копирования
повторно проверяются source, все файлы/режимы и точный layout. Только затем
публикуется `.omk-project-staged.json`.

Auth/operator TAR **не извлекаются**. Внутри runtime могут оставаться старые
игровые access/RCON/config значения: их наличие в точной копии не разрешает
использовать их вместо актуальной политики. Для явного DJ2/FTB adapter есть
отдельный [current-policy этап](PROJECT_POLICY.md); он также не разрешает boot.
До candidate boot нужна проверка совместимости. Drasl не откатывается
вместе с контентом, отозванные доступы не должны оживать.

## Отказ и повторная проверка

- Обрыв процесса или ENOSPC до записи результата оставляет план/частичные файлы
  для диагностики. Ни `stage`, ни `verify` не достраивают и не принимают их.
  Нужна новая явно выделенная область; автоматического удаления старой нет.
- Если процесс завершился после durable receipt, новый процесс может проверить
  прежний `expected`. Успех не требует повторной распаковки и не меняет файлы.
- Неверная selection, другой исправный снимок того же runtime, изменённый план,
  лишние файлы/пустые каталоги, изменения bytes/modes или потерянный receipt
  отказывают. Числа вместо JSON boolean не считаются равными флагам допуска.
- При отказе нет остановки/запуска Docker, переключения ingress, установки
  поверх старой копии, сброса прав или изменения аккаунтов.

Защита рассчитана на сериализованные действия владельца и отдельные mounts,
не на враждебный процесс с тем же доступом к файловой системе/Docker.

## Проверки и границы

Linux Docker: 104 focused tests, из них 44 новых и 60 existing export tests.
Windows: 9 переносимых проверок нового API; 35 Linux filesystem scenarios
пропускаются явно. Это не игра в Minecraft на Windows/Linux/macOS.

Отдельный процессный опыт использует сохранённые настоящие DJ2 payload bytes:
2319 runtime-файлов, 317 файлов мира, 528012910 байт и 34 группы имён с отличием
регистра. Исходный schema-1 export сначала отвергнут без записи. Для consumer
на **отдельной копии** подготовлены явно синтетические schema-2 metadata;
это не приписывание происхождения исходному backup и не новый production release.
Исходные девять файлов остались побайтно прежними.

В Linux, 1 CPU/256 MiB, source readonly и без сети, процесс прерван через
`os._exit(23)` после полного receipt и `os._exit(24)` после первого файла.
Новый readonly-процесс подтвердил полную копию и отказал partial/retry без
изменений. Это реальные прерывания Python-worker, не SIGKILL Minecraft/потеря
питания. Auth/operator не извлекались; свои helpers/тома удалены после проверки.

Полный producer/journal, актуальная политика доступа, запуск/rejoin/gameplay,
поздний отказ кандидата, promotion и возврат после реальной игры остаются #171.
Публикация player manifest/Release, VPS и календарь не включаются.
[Обезличенный протокол](validation/project-stage-2026-11-15.json).
